# 知识图谱抽取性能优化

## 目标

在保持证据可追溯、Schema 约束和图谱事实质量的前提下，把知识图谱构建从“逐切片深度串行抽取”升级为可分级、可并发、可增量的后台流水线。

默认“标准模式”在相同 DeepSeek 服务和同一台部署机器上，对当前 6 个 DOCX、208 个切片的固定基准集达到 15 分钟内完成；上传和向量检索不等待图谱构建完成。

## 已确认事实

- 文件二进制大小不是主要工作量指标，图谱耗时由有效文本、切片数、实体密度、请求 tokens 和并发共同决定。
- 当前基准集包含 6 个 DOCX，共 208 个图谱抽取单元。
- 每个单元平均正文上下文仅 1,480 字符，但每次重复发送 36,511 字符的完整 Ontology/Schema 快照。
- 当前单次模型调用平均输入 15,728 tokens、输出 7,287 tokens。
- 当前模型调用中位延迟约 94-101 秒，平均约 96-100 秒，单元总耗时与模型耗时仅相差约 1 秒，因此 PostgreSQL、解析和候选写入不是主要瓶颈。
- 当前没有模型重试或 JSON 解析失败，慢不是错误恢复造成的。
- 当前每个 Chunk 建立一个 GraphExtractionUnit，并携带前后相邻 Chunk；提示词没有约束“只抽取中心 Chunk”，同一事实可能在相邻单元重复生成。
- Provider 请求未设置最大输出 tokens。
- Worker 使用数据库 claim、租约和独立 worker_id，支持并发消费，但当前缺少统一的并发额度、速率限制和自适应退避配置。
- 图谱物化结果先落为草稿事实；通过系统验证的事实随后自动计划并激活发布，无需人工逐条审核。

## 需求

### R1 构建模式

知识库图谱配置提供三个版本化构建模式：

- fast：只覆盖高价值章节和核心实体关系，优先低延迟。
- standard：默认模式，全文覆盖、证据绑定、相关 Schema 路由和受控并发。
- deep：完整 Schema、扩展上下文和更严格的系统校验，用于高价值或疑难文档。

模式必须固化到 GraphExtractionJob 的策略快照中，任务执行期间不受后来配置变化影响。

### R2 中心内容与批处理

- v1 单元在过渡阶段只能抽取 c0 的事实，前后邻居只用于名称消歧和指代解析。
- v2 按同一标题路径把连续 Chunk 组成 4-6 个 Chunk 的 Section Batch，每个 Chunk 只作为主抽取内容出现一次。
- 每条实体和关系仍必须绑定到明确的 context_ref 和原文证据，不得因批处理降低证据定位精度。
- 表格、列表和标题边界不得被不安全地跨段合并。

### R3 Schema 路由

- Job 继续保存完整冻结 Ontology 快照用于审计和验证。
- 每次模型请求只发送与当前 Section Batch 相关的实体类型、关系类型和属性约束。
- Schema 路由优先使用确定性关键词、类型描述和现有向量能力，不新增一次同等级大模型调用。
- 路由置信度不足、模型输出引用未提供类型或验证覆盖不足时，自动以扩大后的 Schema 子集重试；最终可回退完整 Schema。
- 路由不得允许模型生成冻结 Ontology 之外的类型。

### R4 输出预算

- Provider 增加可配置的最大输出 tokens。
- Prompt 明确限制每批最大实体数、关系数、单条证据长度和重复别名数量。
- Standard 模式目标输出预算为 2,500-4,000 tokens，必须通过基准测试确定最终值。
- 输出达到截断边界、JSON 不完整或事实密度过高时，把 Batch 拆小重试，不接受不完整 JSON。

### R5 并发与限流

- 默认 Standard 模式最大并发为 4，可按 Provider 和知识库配置覆盖。
- 并发必须使用有界队列或 Semaphore，不通过无限增加进程实现。
- 对 429、超时和 Provider 5xx 执行指数退避、抖动和并发降级。
- 记录 Provider 当前并发、排队时间、调用延迟、tokens、429、重试和失败率。
- 多 worker 继续使用现有数据库 claim 和租约，不允许同一单元被重复提交。

### R6 缓存与增量

- 缓存键至少包含库范围、内容指纹、Schema 子集哈希、Prompt/Parser/Policy 版本和模型配置哈希。
- 未变化的 Section Batch 在相同安全范围和策略下复用语义抽取结果，并重新绑定当前 Revision 的 Evidence。
- 内容、Schema、模型或策略任一变化时不得误命中旧缓存。
- 缓存不得跨库泄露敏感事实；清理策略遵循现有抽取原始输出保留策略。
- 重新上传仅重算发生变化的 Section Batch，之后重新执行文档级聚合、验证和物化。

### R7 任务进度与可观测性

- 任务页展示模式、完成 Batch/总 Batch、有效吞吐、实时并发、预计剩余时间和 Provider 限流状态。
- 排队时间与实际处理时间分开显示。
- 任务进度区分“抽取完成”和“自动发布完成”；只有自动发布完成后，合格事实才算已进入可用图谱。
- 监控统计不得保存 Prompt、原文、API Key 或模型完整原始输出。

### R8 兼容与安全

- 已创建的 v1 Job 按原快照完成，不在执行中迁移。
- 新策略通过版本号和 feature flag 启用，支持按知识库灰度。
- Evidence、候选验证、Schema 约束、发布快照、审计和回滚边界保持不变。
- 人工审核不是发布前置条件；生产任务中通过验证和置信度门槛的事实自动发布，未通过的候选继续排除或保留待处理。

## 验收标准

### 性能

- 固定基准集：当前 6 个 DOCX、208 个 Chunk、相同模型服务和部署机器。
- Standard 模式冷缓存端到端完成时间不超过 15 分钟，连续 3 次运行至少 2 次达标，最慢一次不超过 20 分钟。
- Standard 模式热缓存、内容完全未变化时不超过 3 分钟。
- 平均每个原始 Chunk 的模型输入 tokens 相比当前基线下降至少 60%。
- 模型调用次数相比当前 208 次下降至少 70%。
- 429 比例低于 1%，终态失败率低于 0.5%。

### 质量

- 建立人工复核 Gold Set，覆盖普通段落、表格、列表、跨句关系、别名和无事实段落。
- Standard 模式实体与关系综合 F1 相对当前 Deep 基线下降不超过 2 个百分点。
- Evidence quote 可在绑定的 Chunk 中逐字定位，证据绑定有效率为 100%。
- Schema 外类型接受数为 0。
- 同一事实的重复候选数相比当前基线下降至少 50%。

### 产品行为

- 上传和向量检索在图谱构建期间可正常使用。
- 页面刷新后仍能恢复任务进度和 ETA。
- 用户可查看任务使用的 Fast/Standard/Deep 模式。
- 图谱抽取和物化完成后，通过系统验证的实体与关系自动进入新发布版本并立即可用。
- 部分成功任务也应自动发布其中已验证通过的事实，失败单元不得阻塞正确结果进入图谱。
- 自动发布失败不得回滚或删除已经物化的草稿事实；重试必须幂等，不得产生重复实体、关系或重复生效的发布。
- 用户在检索或浏览中发现错误后，通过现有治理和更正流程修改，并生成新的发布版本；不设置强制的发布前人工审核环节。
- 灰度关闭后，新任务立即恢复 v1/Deep 策略，已运行任务不损坏。

## 暂不纳入

- 更换 PostgreSQL、对象存储或图数据库。
- 强制逐实体、逐关系的发布前人工审核工作流。
- 跨知识库共享抽取缓存。
- 对图片、音频和视频增加新的多模态实体抽取能力。
- 仅以 DOCX/PDF 文件 MB 数作为 SLA。

## 关键决策

- Standard 为新知识库默认模式，现有知识库保持原策略，需显式灰度切换。
- 质量门禁优先于速度目标；质量未达标的优化项不得进入默认模式。
- 先完成基准、观测和质量保护，再启用 Schema 路由、并发和批处理。
- 大文件采用后台异步和增量结果，不承诺同步等待完成。
- 当前规划无阻塞产品决策；实施必须在用户审阅并明确批准本规划后开始。
