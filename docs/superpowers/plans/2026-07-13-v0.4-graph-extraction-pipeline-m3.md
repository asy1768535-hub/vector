# v0.4 Graph Extraction Pipeline M3 Implementation Plan

> **Status:** Approved as the M3 execution contract on 2026-07-13. Implementation has not started.
>
> **Authority:** `2026-07-10-v0.4-graph-extraction-pipeline.md`, the completed M2 plan, the v0.3 graph
> specification, and the v0.2 evidence specification, in that order.

## Goal

Create the non-active staging and audit foundation consumed by M4 and M5:

```text
M2 parsed payload + immutable Context mapping
-> Entity/Relation Occurrence audit rows
-> Job-level Entity/Relation Candidate rows
-> exact server-side Evidence Claim resolution
-> separate Entity/Relation Candidate Evidence rows
-> Merge/Conflict review rows
-> nullable formal-graph provenance columns
```

M3 creates exactly Migration `0022` from `0021`. It does not implement `normalization_v1`, Candidate key generation,
Candidate aggregation, ontology/schema validation, conflict detection, confidence scoring/routing, Unit claim/poll,
retry/recovery, Worker orchestration, Materializer writes, trigger hooks, cleanup workers, public APIs, or Migration
`0023`.

M3 may persist manually constructed Candidate/Evidence rows in tests, but no production path creates active or draft
formal graph facts. M4 owns deterministic Candidate construction and validation. M5 owns runtime orchestration and
formal graph materialization.

## Planning Decisions

1. Master Section 11 is authoritative for `0022`; this plan only makes table names, fields and constraint names
   executable.
2. The Master already requires Entity/Relation Occurrence in the pipeline but previously detailed only Entity
   Occurrence. The companion Master amendment freezes `graph_relation_occurrences` with stable relation `ordinal`,
   endpoint Entity Occurrence FKs and a Relation Candidate FK.
3. Candidate Evidence uses two physical tables. A polymorphic `candidate_type + candidate_id` table is forbidden.
4. Candidate Evidence Binding is in M3 because it depends only on M2 Context/Evidence contracts. Candidate state
   routing based on its result remains in M4.
5. Formal provenance columns are nullable and inert in M3. Only M5 may populate them while materializing facts.
6. No API key, Context text, raw Provider output or model-provided UUID/span enters Candidate keys or Evidence
   resolution.

### Candidate Fields

`graph_entity_candidates` contains:

```text

```

`graph_relation_candidates` contains:

```text

source_candidate_id, relation_type_key, target_candidate_id,
proposed_properties, candidate_key,
matched_relation_id, materialized_relation_id,

normalization_score, final_confidence,
ontology_validation_status, has_conflict,
status, review_reason, validation_errors,
created_at, updated_at, purged_at
```

Candidate statuses are exactly `extracted`, `aggregated`, `validated`, `pending_review`, `rejected`, `materialized`
and `superseded`. Confidence values are nullable and, when present, in `[0, 1]`. Relation support mode is exactly
`single_evidence` or `evidence_group`; ontology validation status is nullable and limited to `valid`, `warning`,
`invalid` and `boundary_unclear`.

Before purge, Entity Candidate names and proposed JSON payloads are non-null; Relation Candidate proposed properties
are non-null. At purge, name/normalized name/aliases/properties/external hints/review reason/validation errors are
cleared. Candidate IDs, keys, types, hashes, statuses, scores and formal-match IDs remain for audit.

### Occurrence Fields

`graph_entity_occurrences` contains:

```text
id, job_id, extraction_unit_id, local_ref, entity_candidate_id,
model_confidence, raw_payload, created_at, purged_at
```

`graph_relation_occurrences` contains:

```text
id, job_id, extraction_unit_id, ordinal,
source_entity_occurrence_id, target_entity_occurrence_id, relation_candidate_id,
model_confidence, raw_payload, created_at, purged_at
```

`local_ref` is unique only within a Unit. Relation `ordinal` is the zero-based index in the strictly parsed relation
array and is unique within a Unit. Occurrence raw payload is nullable and must be null after purge. Confidence remains
bounded. M3 does not create Occurrences from Provider output; M4 creates them atomically with deterministic Candidates.

### Candidate Evidence Fields

Both Candidate Evidence tables have the same fields except for their typed Candidate FK:

```text
id, job_id, extraction_unit_id, candidate_id,
claim_key, context_ref, quote_text, quote_hash,
resolved_evidence_id, resolved_document_id, resolved_document_revision_id,
resolved_chunk_id, resolved_block_id, resolved_source_span,
candidate_matches, evidence_type, evidence_quality_score,
validation_status, validation_error,
created_at, purged_at
```

The stable keys are:

```text
quote_hash = SHA256(verbatim UTF-8 quote)
claim_key = SHA256(canonical_json({
  candidate_id,
  extraction_unit_id,
  context_ref,
  quote_hash
}))
```

`validation_status` is exactly `valid`, `ambiguous` or `invalid`:

- `valid`: exactly one stable Candidate Match; all resolved fields except `resolved_block_id` are non-null; Evidence
  type and quality score are non-null.
- `ambiguous`: at least two stable Candidate Matches; every resolved field, Evidence type and score are null.
- `invalid`: Candidate Matches is `[]`; every resolved field, Evidence type and score are null.
- purged: quote text, source span and validation error are null and Candidate Matches is `[]`; a previously valid row
  may retain non-sensitive resolved scope IDs, Evidence type and score.

Candidate Matches are sorted by `evidence_id`, `source_span.start`, `source_span.end` and contain only:

```text
evidence_id, document_id, revision_id, chunk_id, block_id, source_span
```

`pending_review`, `rejected` or `superseded`.

`graph_extraction_conflicts` contains:

`conflicting_fields` stores stable field names and value hashes, never raw conflicting values. Raw values belong only
in purgeable `details`. Conflict status is exactly `open` or `superseded`; at least one Entity or Relation Candidate ID
must be present. M4 owns key creation and conflict insertion.

## Evidence Binding Contract

Create `app/services/graph_candidate_evidence.py`:

```python
resolve_evidence_claim(db, *, job, unit, snapshot,
                       context_ref: str, quote: str) -> EvidenceClaimResolution
create_entity_candidate_evidence(db, *, job, unit, candidate,
                                 snapshot, context_ref, quote)
create_relation_candidate_evidence(db, *, job, unit, candidate,
                                   snapshot, context_ref, quote)
```

Rules:

1. `context_ref` must exist. Job, Unit, Snapshot, Candidate, mapped Chunk and every loaded Evidence row must share
   library/document/revision scope. Unknown refs are Unit protocol errors; cross-scope rows are Unit security errors.
2. Iterate every mapped `evidence_id`; never substitute `primary_evidence_id` for a quote match.
3. Search the exact case-sensitive quote, with no whitespace normalization or fuzzy repair. Find every occurrence,
   including overlapping occurrences.
4. Search `EvidenceUnit.text_quote`; when null, use the validated
   `DocumentRevision.normalized_text[source_start:source_end]` slice. Missing searchable text produces no match.
5. Server source spans use `{"start": n, "end": n, "coordinate_system": "evidence_text_v1"}`. Model spans are
   never accepted.
6. `table_row`/`sheet_row` Evidence, or Evidence backed by a `table`/`sheet_row` Block, maps to `table_cell`.
   Pure heading/structure Evidence is not materializable. Other text-bearing Evidence maps to `direct_statement`.
7. One materializable hit is `valid`; two or more are `ambiguous`; zero is `invalid`. Candidate-level invalid or
   ambiguous results do not fail the Unit.
8. Persistence is idempotent by typed Candidate + Unit + `claim_key`. A matching non-purged row is returned;
   mismatched or purged rows are not silently overwritten or rebuilt.
9. These functions insert Candidate Evidence only. They do not change Candidate status/scores, create Conflicts,
   update Unit/Job state, or write formal graph tables.

## Definition Of Done

- All eight staging/audit tables match ORM and DDL, including purge and Candidate Evidence state checks.
- Entity and Relation Candidate Evidence remain physically separate and Evidence-rooted.
- Exact quote resolution searches every mapped active same-scope Evidence and never trusts model IDs/spans.
- Formal provenance additions are nullable, backward-compatible and inactive until M5.
- Candidate invalid/ambiguous outcomes never become Unit failures in M3 code.
- M2, M1, v0.3 and full regressions plus Ruff pass.
- M3 completion is recorded before M4 planning begins.
