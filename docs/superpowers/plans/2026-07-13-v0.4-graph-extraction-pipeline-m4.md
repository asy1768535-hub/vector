# v0.4 Graph Extraction Pipeline M4 Implementation Plan

> **Status:** Proposed for review on 2026-07-13. No M4 production code has been written.
>
> **Authority:** `2026-07-10-v0.4-graph-extraction-pipeline.md`, the completed M3 plan, the v0.3 graph
> specification, and the v0.2 Evidence specification, in that order.

## Goal

Implement the deterministic Candidate rule layer consumed by the M5 Worker and Materializer:

```text
M2 strict parsed payload + M3 exact Evidence resolver
-> atomic Unit Occurrence/Candidate staging
-> deterministic Job-level Candidate aggregation
-> shared pure graph shape validation
-> exact Entity matching and stable review records
-> confidence component calculation
-> hard Candidate routing to validated / pending_review / rejected
```

M4 does not claim or finish Units, orchestrate Job stages, call a Provider, retry or rerun Jobs, materialize formal
Entity/Relation rows, expose APIs, trigger extraction, clean sensitive payloads, or create Migration `0023`. M4 uses
the tables created by Migration `0022`; no ORM or DDL change is expected.

M4 never writes `materialized`. A Candidate that passes M4 remains `validated`; M5 alone writes formal graph rows
and then changes the Candidate to `materialized`.

## Planning Decisions

1. `normalization_v1` is exactly the existing v0.3 `strip + casefold + whitespace collapse` rule. It does not add
   NFKC, full/half-width conversion, pinyin, edit distance, vectors, synonym expansion or automatic aliases.
2. `graph_schema_validator.py` remains the single owner of Entity/Relation properties, Attribute Definition and
   Relation Constraint rules. v0.3 database wrappers and v0.4 Candidate validation call the same pure functions.
3. Occurrence and Candidate staging is a caller-owned short transaction. Service functions may `flush`, but never
   `commit` or `rollback`.
4. Job-level aggregate values are always recomputed from all non-purged Occurrences in stable order. They are never
   incrementally merged into the current Candidate payload and never depend on which Unit commits first.
5. Candidate validation uses the Job's frozen ontology snapshot. Entity matching queries formal graph rows, but only
   exact `normalization_v1` name/active-alias matches are eligible; fuzzy or semantic matching is forbidden.
6. Property conflicts, Entity merge ambiguity and endpoint replay mismatch create stable Conflict rows. Merge
   ambiguity also creates one Merge Candidate per suggested formal Entity.
7. Hard routing wins over arithmetic confidence. Invalid input is rejected; ambiguity, conflict, unclear boundaries
   and Evidence Groups require review even if the weighted score is high.
8. Candidate-level rejection/review is a successful M4 evaluation result. M5 must not convert it into a Unit failure.
   Database, scope, replay-integrity or malformed-snapshot failures remain infrastructure/protocol errors.

- do not add HTTP schemas, routes, CLI commands, background loops or third-party dependencies.

Configuration and permissions:

- reuse the Job's frozen normalization/confidence versions and policy snapshot; add no environment variable;

## Key Flow

1. M5 will pass one already parsed `GraphExtractionPayload` plus scoped Job/Unit/Snapshot rows into M4.
2. M4 stages Entity Candidate skeletons and Entity Occurrences first, so every Unit-local Relation endpoint resolves to
   a Job-level Entity Candidate key. It then stages Relation rows and calls the existing exact Evidence binder.
3. After eligible Units are available, M4 locks Candidates in `candidate_key` order and recomputes aggregates from all
   non-purged Occurrences. Stable sort rules, not arrival order, choose display values and conflict inputs.
4. M4 converts the frozen ontology snapshot to shared Rule DTOs, validates Entity Candidates, performs exact formal
   Entity matching, then validates Relation Candidates against endpoint Entity Types and Constraints.
5. M4 creates/reuses Merge and Conflict rows, derives Evidence/schema/normalization components, computes confidence
   and applies hard routes.
6. M4 returns counts/IDs to M5 without changing Unit/Job state. Only `validated` Candidates are eligible for M5's live
   safety recheck and Materializer.

Failure boundaries:

- malformed parsed payload, unknown context ref, cross-scope data, mismatched/purged replay, malformed frozen policy
  or ontology snapshot, and database errors abort the caller transaction;
- Evidence/schema invalidity, ambiguity, conflict and low confidence update only affected Candidates;
- no M4 outcome changes an otherwise valid parsed Unit from succeeded to failed.

## Normalization And Stable Keys

### Public Name Rule

`app/services/graph_normalization.py` owns:

```python
def normalize_graph_name_v1(value: str) -> str:
    return " ".join(value.strip().casefold().split())
```

The existing `graph_schema_validator.normalize_graph_name` remains import-compatible and delegates directly to
`normalize_graph_name_v1`. Candidate keys, Candidate alias aggregation, formal Entity matching and v0.3 formal Entity
writes all call this function.

The function accepts only `str`. Empty normalized values are invalid names. It does not mutate the original display
name used as the representative `canonical_name`.

### Canonical JSON

All M4 keys and value hashes use one private canonical JSON contract:

```python
json.dumps(
    value,
    ensure_ascii=False,
    sort_keys=True,
    separators=(",", ":"),
    allow_nan=False,
)
```

The UTF-8 bytes of that string are SHA-256 hashed and encoded as lowercase hexadecimal. UUIDs are converted to their
lowercase hyphenated string form before serialization. Lists preserve semantic order unless a formula explicitly
requires sorting. Sets, tuples, dates, ORM objects and non-finite numbers are rejected rather than stringified.

Stable key helpers live in `graph_candidate_aggregation.py`:

```python
entity_candidate_key_v1(*, ontology_version_id, entity_type_key, normalized_name) -> str
relation_candidate_key_v1(*, ontology_version_id, source_candidate_key,
                          relation_type_key, target_candidate_key, properties) -> str
merge_candidate_key_v1(*, job_id, entity_candidate_id,
                       suggested_target_entity_id, reason) -> str
conflict_key_v1(*, job_id, conflict_type, entity_candidate_ids,
                relation_candidate_ids, conflicting_fields) -> str
```

The hash payloads are canonical JSON objects with exactly the named inputs. Candidate key inputs follow Master
Sections 11.2 and 11.3. Conflict Candidate IDs and each field's `value_hashes` are deduplicated and sorted before
hashing. Known-answer tests freeze every key and prove JSON object key order and Unit processing order do not alter it.

Raw Context, quotes, Provider response text, API secrets, model request IDs, Unit-local IDs and random Candidate UUIDs
must not enter Entity or Relation Candidate keys. Relation keys use Job-level endpoint Candidate keys, not endpoint
Candidate UUIDs.

## Shared Pure Validator

### Immutable Rule DTOs

`graph_schema_validator.py` adds frozen dataclasses. Attribute rules are explicit DTOs so the pure core never depends
on an ORM row:

```text
AttributeDefinitionRule:
  key, value_type, required, enum_values, validation_schema

EntityTypeRule:
  id, ontology_version_id, key, properties_schema,
  active_attribute_definitions: tuple[AttributeDefinitionRule, ...]

RelationTypeRule:
  id, ontology_version_id, key, direction, requires_evidence,
  default_review_policy, properties_schema,
  active_attribute_definitions: tuple[AttributeDefinitionRule, ...]

RelationConstraintRule:
  source_entity_type_id, target_entity_type_id, cardinality, requires_review

EntityShapeValidation:
  normalized_name, validated_properties, reasons

RelationShapeValidation:
  valid, schema_boundary_clear, requires_review, validated_properties, reasons
```

Mutable JSON payloads are defensively copied when DTOs/results are constructed. Rule collections are sorted by stable
keys before conversion to tuples.

### Pure Interfaces

```python
validate_entity_shape(
    *,
    entity_type: EntityTypeRule,
    canonical_name: str,
    properties: dict[str, Any],
) -> EntityShapeValidation

validate_relation_shape(
    *,
    relation_type: RelationTypeRule,
    constraint: RelationConstraintRule | None,
    source_entity_type_id: uuid.UUID,
    target_entity_type_id: uuid.UUID,
    properties: dict[str, Any],
) -> RelationShapeValidation
```

These functions perform no SQL and require no formal Entity rows. They own all current properties-schema and active
Attribute Definition checks. Entity validation rejects an empty normalized name. Relation validation checks endpoint
types against the supplied Constraint and returns `valid=False` when a non-`related_to` Relation has no matching
Constraint. A constraint-free `related_to` result is valid but has `schema_boundary_clear=False` and requires review.

Malformed properties and attributes continue to raise `ValueError` with the existing v0.3 messages. Candidate
validation catches those exceptions and records a structured Candidate error; v0.3 wrappers continue to expose the
same exception behavior.

### v0.3 Compatibility Wrappers

`validate_entity_write` and `validate_relation_write` retain their current parameters and return DTOs. Their database
loading, active-schema checks, duplicate active Entity check, Evidence count and formal status decision remain in the
wrappers. The wrappers convert active ORM rows to Rule DTOs, call the pure shape functions, and then apply the existing
v0.3-only write/status rules.

The following behavior must remain byte-for-byte compatible where asserted by existing tests:

- normalized names and trimmed canonical names;
- required/type/enum properties and Attribute Definition errors;
- duplicate active Entity rejection;
- missing non-`related_to` Constraint rejection;
- evidence and Relation review-policy status decisions;
- existing public imports and async signatures.

No second copy of `_validate_properties_schema`, Attribute Definition value checks or Constraint matching may be added
to a Candidate module.

## Frozen Ontology Rules

M4 Candidate validation consumes a normalized `OntologyRuleSet` built from `job.ontology_snapshot`.

The following minimal validation projection is the confirmed M4 consumption contract. It is derived from the existing
ORM fields and the Master Rule DTOs; production generation remains M5 scope:

```json
{
  "ontology_version_id": "uuid",
  "entity_types": [
    {
      "id": "uuid",
      "key": "department",
      "properties_schema": {},
      "active_attribute_definitions": [
        {
          "key": "owner",
          "value_type": "string",
          "required": false,
          "enum_values": null,
          "validation_schema": null
        }
      ]
    }
  ],
  "relation_types": [
    {
      "id": "uuid",
      "key": "responsible_for",
      "direction": "directed",
      "requires_evidence": true,
      "default_review_policy": "auto_active",
      "properties_schema": {},
      "active_attribute_definitions": [
        {
          "key": "effective_date",
          "value_type": "date",
          "required": false,
          "enum_values": null,
          "validation_schema": null
        }
      ]
    }
  ],
  "relation_constraints": [
    {
      "relation_type_id": "uuid",
      "source_entity_type_id": "uuid",
      "target_entity_type_id": "uuid",
      "cardinality": "many_to_many",
      "requires_review": false
    }
  ]
}
```

Field mapping is fixed:

| Snapshot field | ORM source/filter |
|---|---|
| `ontology_version_id` | `OntologyVersion.id`; must equal `job.ontology_version_id` |
| Entity `id/key/properties_schema` | same-named `EntityType` fields where ontology/library match and `status='active'` |
| Relation `id/key/direction/requires_evidence/default_review_policy/properties_schema` | same-named `RelationType` fields where ontology/library match and `status='active'` |
| Constraint fields | same-named active `RelationTypeConstraint` fields; `relation_type_id` identifies the owner |
| Attribute fields | same-named active `AttributeDefinition` fields nested under the matching `owner_kind/owner_type_id` |

`properties_schema`, `enum_values` and `validation_schema` preserve JSON `null` when the ORM field is null. Snapshot
arrays are canonicalized before hashing: Entity/Relation Types by `(key, id)`, nested Attributes by `key`, and
Constraints by `(relation_type_id, source_entity_type_id, target_entity_type_id)`. Duplicate sort identities are
invalid. The builder does not include draft/disabled/deleted rows.

M4 provides a strict snapshot-to-Rule parser, not a second ontology model. It rejects duplicate keys/IDs, unknown
Constraint references, wrong UUIDs, invalid enum fields, cross-version IDs, malformed schemas and a snapshot version
different from `job.ontology_version_id`. `job.normalization_rule_version` must be `normalization_v1` and
`job.confidence_policy_version` must be `v1`.

The parser verifies `ontology_snapshot_hash` against the canonical JSON contract before constructing Rules. The
minimal dictionaries in existing M2 Prompt/Context tests are not valid M4 Rule snapshots and are not passed to this
parser; their existing tests remain unchanged.

A malformed or mismatched frozen snapshot is a Job infrastructure/protocol failure, not a reason to bulk-reject valid
Candidates. M5 will own production snapshot construction and Job failure handling.

## Deterministic Candidate Staging

### Interfaces

`graph_candidate_aggregation.py` exposes caller-transaction functions:

```python
stage_unit_candidate_occurrences(
    db,
    *,
    job,
    unit,
    snapshot,
    payload: GraphExtractionPayload,
) -> UnitCandidateStageResult

recompute_job_candidate_aggregates(
    db,
    *,
    job,
) -> JobCandidateAggregateResult
```

The Unit function checks Job/Unit/Snapshot/library/revision/ontology scope, stages all Entity endpoints before
Relations, inserts typed Candidate Evidence through the M3 resolver, and flushes without committing. It does not
change Unit or Job status. The Job function recomputes aggregate fields and conflicts but does not orchestrate
`current_stage`.

### PostgreSQL Concurrency Strategy

For every sorted Candidate key:

1. Insert a minimal non-purged Candidate with `INSERT ... ON CONFLICT (job_id, candidate_key) DO NOTHING`.
2. Re-read it by `(job_id, candidate_key)` and lock it `FOR UPDATE`.
3. Verify immutable scope/key/type/endpoint fields. A mismatch is never overwritten.
4. Insert the Occurrence using its M3 Unit-local unique identity.
5. On replay, return the existing non-purged Occurrence only when its Candidate link, confidence and canonical raw
   payload are identical. A purged or differing replay is rejected/recorded according to the conflict contract.
6. Recompute the locked Candidate from all non-purged Occurrences ordered by Unit and local identity.

The Candidate unique index serializes same-key creation. Row locking plus full recomputation ensures the final value is
identical whether Unit A or Unit B commits first. Candidate IDs may be random; semantic keys and aggregates may not.

The service does not catch and hide `IntegrityError`. Unexpected database failures roll back the caller transaction.

### Entity Aggregate

Entity Occurrences are ordered by `GraphExtractionUnit.ordinal ASC`, `local_ref ASC`, then Occurrence UUID only as a
corruption-resistant final tie-break. The first row is representative.

- `canonical_name`: representative `name.strip()`.
- `normalized_name`: `normalize_graph_name_v1(representative.name)`; it must equal the Candidate key input.
- `proposed_aliases`: discard empty normalized aliases; group by normalized value; keep the lexicographically smallest
  original stripped spelling per normalized value; sort by `(normalized_value, original_value)`.
- `model_confidence`: maximum non-null Occurrence confidence.
- `proposed_properties`: process keys lexicographically. Equal canonical JSON values are stored once. Different values
  retain the representative Occurrence's value and create a Property Conflict; later values never overwrite it.
- `external_mapping_hints`: deduplicate by canonical JSON and sort by canonical JSON. Hints never create mappings.
- all Entity Evidence claims remain in the typed M3 table; no quote is copied into aggregate fields.
- status advances from `extracted` to `aggregated` unless a hard conflict already requires `pending_review`.

### Relation Aggregate

Each Relation endpoint first resolves through its Unit's Entity Occurrence to a Job-level Entity Candidate. Relation
Occurrences are ordered by Unit ordinal and relation `ordinal`.

- key inputs are source Candidate key, Relation Type key, target Candidate key and canonical properties;
- identical key inputs produce one Job-level Relation Candidate;
- different canonical properties intentionally produce different Relation Candidates;
- `model_confidence` is the maximum non-null Occurrence confidence;
- original per-Occurrence confidence and raw payload remain in the M3 Occurrence table;
- duplicate Evidence claims are idempotent by the M3 Claim key and do not duplicate a Relation Candidate;
- valid claims from one distinct `resolved_evidence_id` produce `single_evidence`; valid claims from two or more
  distinct Evidence IDs produce `evidence_group`;
- valid Evidence quality is the minimum valid Claim score; an invalid/ambiguous/no-claim state receives `0.0` and is
  subsequently hard-routed;
- if either endpoint is rejected, the Relation is rejected; if an unmatched endpoint is pending review, the Relation
  cannot be eligible for M5 materialization.

## Candidate Validation And Exact Entity Matching

`graph_candidate_validation.py` exposes:

```python
validate_job_candidates(db, *, job) -> JobCandidateValidationResult
```

It locks Entity Candidates by `candidate_key`, validates them, performs formal Entity matching, then locks and
validates Relation Candidates. The caller owns the transaction. Repeated calls over unchanged inputs are idempotent.

### Schema Classification

- unknown Entity Type, unknown Relation Type, wrong ontology, missing required non-`related_to` Constraint,
  endpoint type mismatch, invalid properties or invalid Attribute Definition: `invalid`, score `0.0`;
- valid shape without review signals: `valid`, score `1.0`;
- valid Relation with `requires_review` or a review-only Relation Type policy: `warning`, score `0.6`;
- valid `related_to` without an exact Constraint or another explicitly unclear boundary: `boundary_unclear`, score
  `0.4` and hard pending review.

Relation classifications are written to `ontology_validation_status`. Entity Candidates store the score and stable
structured errors because their M3 table intentionally has no ontology-status column.

Validation errors are stable objects ordered by `(code, field, value_hash)` and contain no raw Evidence quote or
Context text. `review_reason` is a single dominant machine code, not concatenated free-form model content.

### Exact Entity Matching

Automatic reuse permits only:

```text
same library + same ontology + same Entity Type
+ exact entities.normalized_name == normalization_v1(Candidate name)
```

or:

```text
same library + active exact entity_aliases.normalized_alias
+ same Entity Type on the alias owner
```

Eligible formal Entity statuses are exactly `draft`, `pending_review` and `active`.

- one eligible exact normalized-name result: set `matched_entity_id`, method `exact_normalized_match`, score `1.0`;
- otherwise one eligible exact active-alias result: set `matched_entity_id`, method `exact_alias_match`, score `0.95`;
- no result: clear `matched_entity_id`, method `new_entity`, score `0.9`;
- multiple results, name/alias disagreement, type disagreement or ineligible-status hit: clear `matched_entity_id`,
  method `ambiguous`, score `0.0`, create review records and hard-route pending.

Exact normalized-name match has priority only when every eligible name/alias lookup points to the same Entity. An
active alias that points to a different Entity is ambiguity, not a lower-priority result. Similar names, inactive
aliases, external mapping hints and vectors never cause automatic reuse.

An exact hit on `rejected`, `stale`, `disabled` or `deleted` creates an Entity status Conflict and remains pending;
M4 must not attempt a duplicate formal Entity insert. M4 does not write `entity_aliases` or formal mappings.

For each ambiguous suggested target, upsert a `GraphEntityMergeCandidate` using the stable Merge key. The Candidate is
never automatically merged.

## Conflict Contract

M4 creates these `GraphExtractionConflict.conflict_type` values:

```text
property_conflict
entity_merge_ambiguity
entity_status_conflict
endpoint_mismatch
```

`conflicting_fields` contains only field identifiers and sorted SHA-256 hashes:

```json
[
  {
    "field": "properties.owner",
    "value_hashes": ["sha256-a", "sha256-b"]
  }
]
```

Raw conflicting values are allowed only in purgeable `details`, grouped by value hash and ordered deterministically.
Descriptions/evidence must not duplicate raw Context or quote text. Candidate ID lists are lowercase UUID strings,
deduplicated and sorted.

`entity_merge_ambiguity` creates one Conflict for the complete stable target set and one Merge Candidate per target.
`entity_status_conflict` identifies exact formal hits whose status is not reusable.

`endpoint_mismatch` is deliberately narrow. It is created only when an existing same-identity Relation Occurrence
`(extraction_unit_id, ordinal)` is replayed with different endpoint Candidate keys, or a row found by an identical
Relation Candidate key has endpoint IDs inconsistent with the key inputs. Ordinary distinct Relation Occurrences with
the same Relation Type/properties and different endpoints are not conflicts. M4 never overwrites the original link;
the affected Relation Candidate is pending review and the mismatch is returned to M5 as a replay-integrity result.

Conflict upsert is idempotent by `(job_id, conflict_key)`. An existing non-purged row must exactly match the recomputed
non-sensitive identity. Purged rows are not rehydrated. Open review rows that are explicitly recomputed as no longer
applicable are marked `superseded`, never deleted.

## Confidence And Hard Routing

`graph_candidate_routing.py` owns pure score/routing functions and policy DTOs:

```python
compute_final_confidence_v1(*, model, evidence, schema, normalization) -> float
route_entity_candidate_v1(...) -> CandidateRoute
route_relation_candidate_v1(...) -> CandidateRoute
apply_job_candidate_routes(db, *, job) -> JobCandidateRouteResult
```

The exact v1 formula is:

```text
final_confidence =
    model_confidence        * 0.25
  + evidence_quality_score  * 0.35
  + schema_validation_score * 0.25
  + normalization_score     * 0.15
```

Every component must be finite and in `[0, 1]`. Missing model confidence is invalid Candidate input, not `0`. Entity
normalization score is derived from `normalization_method`; Relation normalization score is the lower endpoint score
and is persisted. The result is not rounded before storage.

The v1 policy snapshot must contain the exact weights, score maps and `0.85` thresholds frozen by Master Section 9.
A missing/malformed/different snapshot under version `v1` fails closed as a Job policy error. A future formula requires
a new policy version and separate compatibility work.

### Routing Precedence

Rules are evaluated in this order, before confidence thresholds:

1. Schema invalid, any Evidence Claim invalid, no Evidence Claim, or a rejected endpoint: `rejected`.
2. Any ambiguous Evidence Claim, schema boundary unclear, Entity match ambiguity, open Conflict, ineligible exact
   formal match, or unmatched pending endpoint: `pending_review`.
3. Relation `evidence_support_mode=evidence_group`: `pending_review`, even when every Claim is valid.
4. A uniquely matched reusable Entity: `validated`, regardless of the new-Entity threshold.
5. A new valid Entity with `final_confidence >= 0.85`: `validated`; below `0.85`: `pending_review`.
6. A valid single-Evidence Relation with usable endpoints and no conflict: `validated` at any score. M5 later creates
   a draft formal Relation at `>= 0.85` or a pending-review formal Relation below `0.85`.

`validated` means eligible for M5 checks, not guaranteed materialization. M5 must still recheck live Library/revision
safety and use v0.3 formal write services against the current active ontology.

Dominant `review_reason` codes are stable:

```text
schema_invalid
evidence_invalid
endpoint_rejected
evidence_ambiguous
schema_boundary_unclear
entity_match_ambiguous
conflict_open
endpoint_pending_review
evidence_group
low_confidence
```

Rejection reasons precede review reasons. Within each class the order above decides the dominant reason, while all
applicable structured errors remain in `validation_errors`.

## Risks And Rollback

| Risk | Required control | Rollback/recovery |
|---|---|---|
| Shared Validator changes v0.3 behavior | Refactor behind existing wrappers; run v0.3 tests in Task 2 and final gate | Revert the Task 2 commit; no data migration is involved |
| Key serialization bug creates duplicate semantic Candidates | One canonical JSON helper, typed payloads and known-answer vectors before persistence | Stop M5 consumption; fix forward and create a new full-rerun Job. Do not rewrite keys inside an existing Job |
| Same-key concurrent Units lose data or deadlock | Sort keys before locking, use unique upsert/reload, lock one Candidate at a time, recompute from Occurrences | Roll back the short transaction and retry; PostgreSQL Task 6 must reproduce reverse commit order |
| Future M5 Job builder emits a different ontology snapshot shape | Frozen M4 field mapping and strict hash/parser tests; M5 integration must use the same contract | Fix the unimplemented M5 builder; do not add a permissive second M4 shape |
| Formal Entity/Alias changes after Candidate matching | Restrict M4 to exact matches and retain review data; M5 rechecks live formal rows before materialization | Clear/supersede stale match in a recomputation or full rerun; never force materialization from an old match |
| Conflict details retain sensitive source values | Hash-only non-purgeable identity, minimal purgeable `details`, no quote/Context copies | Disable M5, purge through the M5 retention path when available; row keys/status remain for audit |
| Hard-route precedence is implemented after threshold routing | Pure route table tests cover every pairwise precedence case | Revert/fix Task 5 and rerun affected Job Candidates before enabling M5 |
| Partial M4 deployment leaves staging rows | No formal writes and caller-owned atomic transactions | Roll back application commits in reverse order. Existing non-active staging rows may remain for audit and be safely recomputed after redeploy |

M4 has no database downgrade because it has no migration. Rollback must not delete user data or M3 audit rows. If any
M4 commit is reverted after Candidate data exists, M5 remains disabled until those Candidates are recomputed by the
corrected code or replaced by a full rerun Job.
