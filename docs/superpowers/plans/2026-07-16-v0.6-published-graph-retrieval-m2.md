## 1. Goal

M2 turns the v0.5 current publication boundary into a read-only internal retrieval snapshot and resolves explicit seeds
against that snapshot. It does not traverse Relations yet.

The M2 result must answer, without exposing formal properties or source text:

1. Which healthy active publication is the query fenced to?
2. Does that publication still have complete active Entity/Relation membership?
3. Do all published Relations have published endpoints and active schema types?
4. Which published Entity does each exact ID/name seed identify?
5. Which requested Relation Type filters are active in the same scope?
6. Is the same publication still current and healthy at the end of the operation?

## 2. Non-Goals

M2 does not implement:

- `/libraries/{slug}/v06/graph/query` or any FastAPI route;
- BFS, Relation traversal, direction filtering or truncation;
- Evidence locator hydration or current-revision Evidence revalidation;
- response DTO assembly;
- query logging, metrics, timeout mapping or API permission dependencies;
- natural-language parsing, aliases, fuzzy matching or LLM entity linking;
- properties read/return/filter/sort;
- temporal filtering;
- review mutation or governance UI;
- changes to v0.5 planner, activation, reconciliation or healthy read helpers;
- a new table, column, index or Migration `0024`.

M3 owns traversal. M4 owns Evidence hydration and the REST API.

## 3. Current Facts And Gap

v0.5 activation already switches a publication atomically:

- the previous current publication becomes `superseded`;
- previous items become `superseded`;
- new items become `active`;
- the new publication becomes `active`;
- the current-scope partial unique index allows only one `active`/`degraded` row per Library/Ontology.

The existing `graph_publication_read.list_healthy_published_*` helpers are correct for v0.5's operational contract, but
M2 must not use them as its primary loader because they:

- select full Entity/Relation ORM rows, including formal `properties`;
- load every published row into Python before comparing counts;
- validate Entity and Relation sets independently but do not prove Relation endpoint membership in one snapshot;
- do not expose item hashes and type projections needed by v0.6;
- do not provide start/end publication fences.

M2 adds a separate v0.6 read service and leaves v0.5 helpers unchanged for compatibility.

## 4. Required M1 Forward-Fix

M1 allows operators to lower `GRAPH_RETRIEVAL_MAX_*` below the v1 absolute DTO caps. A request can therefore pass
Pydantic validation but exceed the configured runtime cap.

Before M2 service implementation, amend `GraphRetrievalErrorCode` with:

```text
graph_retrieval_limit_exceeded
```

Contract:

- HTTP mapping in future M4: `422`;
- internal M2 validation happens before any database query;
- the error contains only the stable code, never configured values or request payload;
- absolute caps remain enforced by the M1 DTO;
- configured lower caps are enforced by `validate_graph_retrieval_request_limits(request, config)`;
- `max_nodes` must also be at least the number of seeds.

This is a forward-compatible completion of the accepted M1 configurable-downward contract. No other M1 DTO field or
default changes in M2.

## 6. Internal Types

Use frozen, slotted dataclasses. Do not return ORM instances from the M2 service.

### 6.1 `HealthyGraphSnapshot`

```text
publication_id: UUID
library_id: UUID
ontology_version_id: UUID
manifest_version: Literal['v1']
manifest_hash: str
activated_at: datetime
entity_count: int
relation_count: int
```

It contains only query identity and counts. It excludes policy snapshots, blocked diagnostics, fact snapshots and user
IDs.

### 6.2 `ResolvedPublishedEntity`

```text
input_index: int
entity_id: UUID
item_hash: str
entity_type_id: UUID
entity_type_key: str
entity_type_label: str
canonical_name: str
normalized_name: str
source_type: str
confidence: float | None
```

It intentionally excludes Entity properties, authority, status timestamps, aliases and source text.

### 6.3 `ResolvedRelationType`

```text
relation_type_id: UUID
key: str
label: str
direction: Literal['directed', 'undirected']
```

It excludes descriptions, properties schema and review policy because M3 only needs identity and direction.

### 6.4 `GraphRetrievalResolution`

```text
snapshot: HealthyGraphSnapshot
seeds: tuple[ResolvedPublishedEntity, ...]
relation_types: tuple[ResolvedRelationType, ...]
```

`seeds` preserves request input order. Duplicate selectors may resolve to the same Entity and remain separate entries so
`seed_matches.input_index` can be reproduced later.

### 6.5 `GraphRetrievalServiceError`

```text
code: GraphRetrievalErrorCode
candidates: tuple[GraphRetrievalAmbiguousCandidate, ...] = ()
```

`str(error)` is the stable code only. It must never include a seed name, UUID supplied by the caller, SQL, count delta or
internal exception text.

## 8. Start Snapshot Selection

Use a dedicated explicit-column query scoped by:

```text
GraphPublication.library_id == library.id
GraphPublication.ontology_version_id == request.ontology_version_id
GraphPublication.status IN ('active', 'degraded')
```

Do not load the full `GraphPublication` ORM row. Select only the fields required by `HealthyGraphSnapshot` plus status.

Selection rules, in order:

1. No current row: `graph_publication_unavailable` (`503` in M4).
2. Current row is `degraded`: `graph_publication_unavailable`.
3. Status is not exactly `active`: `graph_publication_invariant_failed`.
4. `manifest_version != 'v1'`: `graph_publication_invariant_failed`.
5. Bound Ontology is missing, inactive or not in the same Library: `graph_publication_invariant_failed`.
6. Missing/invalid manifest hash or `activated_at`: `graph_publication_invariant_failed`.
7. `expected_publication_id` is present and differs from current ID: `publication_changed` (`409`).
8. Otherwise construct the snapshot and run all membership aggregates.

Do not query an untrusted `expected_publication_id` directly. A cross-Library, cross-Ontology, superseded or otherwise
non-current expected ID is handled only by comparison with the scoped current ID and returns the same
`publication_changed` result.

The database unique index is the primary one-current invariant. The service query must still use a shape that raises
`graph_publication_invariant_failed` if corruption exposes more than one current row; it must not silently `LIMIT 1`.

## 9. Aggregate Membership Invariants

M2 must prove publication completeness with aggregate SQL. It must not load all publication members into Python.

### 9.1 Item aggregate

One aggregate over all items for `publication_id` must report:

- total item count;
- Entity item count;
- Relation item count;
- active item count;
- wrong Library/Ontology count;
- invalid kind/target-shape count;
- invalid SHA-256 item-hash count.

Required equality:

```text
total == entity_count + relation_count
entity_items == entity_count
relation_items == relation_count
active_items == total
wrong_scope == 0
invalid_shape == 0
invalid_hash == 0
```

Any mismatch raises `graph_publication_invariant_failed` without returning actual/expected counts in the error.

### 9.2 Entity aggregate

One aggregate join from active Entity publication items to `entities` and `entity_types` must require:

- exact publication/Library/Ontology scope;
- `item_kind='entity'` and item status active;
- formal Entity exists and is active;
- Entity scope matches the snapshot;
- Entity Type exists, is active and matches the same scope;
- joined distinct item count equals `snapshot.entity_count`.

This query selects counts only. It does not select Entity properties or full ORM rows.

### 9.3 Relation aggregate

One aggregate join from active Relation publication items to `knowledge_relations`, `relation_types`, and two aliased
Entity publication items must require:

- exact publication/Library/Ontology scope;
- `item_kind='relation'` and item status active;
- formal Relation exists and is active;
- `review_status IN ('not_required', 'approved')`;
- Relation scope matches the snapshot;
- Relation Type exists, is active and matches the same scope;
- source and target each have an active Entity item in the same publication;
- joined distinct Relation item count equals `snapshot.relation_count`.

This proves there are no dangling published Relations. The separate Entity aggregate proves the endpoint formal rows and
Entity Types are healthy.

### 9.4 Ownership boundary with v0.5 reconciliation

M2 does not recompute v0.5 canonical item/manifest hashes on every query because doing so would load formal properties
and duplicate the publication planner. M2 verifies stored hash shape, current active status and structural membership.

v0.5 planner/reconciliation remains the owner of:

- canonical live-fact hash comparison;
- schema constraint revalidation;
- Evidence/current-revision eligibility;
- one-way publication degradation.

M4 will additionally validate each selected Evidence locator before returning it. M2 must not claim Evidence hydration
completeness.

## 10. Exact Seed Resolution

### 10.1 Normalization

Name seeds use only `normalize_graph_name_v1`. No NFKC, alias, substring, trigram, pinyin, embedding or LLM matching is
allowed.

### 10.2 Batch query shape

Partition request seeds into ID selectors and name selectors. Execute at most two resolution statements regardless of
seed count:

- one `VALUES(input_index, entity_id)` table joined to published Entity membership;
- one `VALUES(input_index, normalized_name, entity_type_key)` table joined to published Entity membership.

Each query must join:

```text
GraphPublicationItem(publication_id, active, entity)
-> Entity(active, same Library/Ontology)
-> EntityType(active, same Library/Ontology)
```

Project only the fields listed in `ResolvedPublishedEntity`. Never use `select(Entity)`, `select(EntityType)` or load
aliases.

Stable SQL ordering:

```text
input_index
entity_type.key
entity.id
```

### 10.3 Per-input result rules

- zero matches: `seed_not_found` (`404`);
- exactly one match: accept;
- more than one match: `seed_ambiguous` (`409`);
- ambiguity candidates: first 10 sorted `{entity_type_key, entity_id}` values;
- an ID outside the current publication, Library or Ontology is indistinguishable from missing;
- a name with an unknown/cross-scope Entity Type key is indistinguishable from missing;
- duplicate inputs remain separate `input_index` results;
- result tuple order is request input order.

The exception never carries canonical/normalized names.

## 11. Relation Type Filter Resolution

When `relation_type_keys` is empty, return an empty tuple meaning "no allowlist restriction". Do not load every type.

For a non-empty filter:

1. deduplicate keys without changing their contract meaning;
2. use one batch statement scoped to Library/Ontology and `status='active'`;
3. project only ID, key, label and direction;
4. sort by key then ID;
5. if any requested key is absent, inactive or cross-scope, raise `relation_type_not_found` (`409`);
6. do not report which key was missing.

M2 resolves type identity only. M3 applies direction and adjacency semantics.

## 12. End Publication Fence

`assert_graph_snapshot_still_current` performs a new read under the session's normal PostgreSQL `READ COMMITTED`
behavior. It does not lock publication rows and does not start a repeatable-read transaction.

End rules:

| Observed state | Result |
|---|---|
| same ID, same hash, status active | pass |
| different current ID | `publication_changed` |
| old snapshot is now superseded and no current row is visible | `publication_changed` |
| no current row after one existed | `publication_changed` |
| same ID is now degraded | `graph_publication_unavailable` |
| same scoped ID but hash/manifest differs | `graph_publication_invariant_failed` |
| snapshot ID is no longer visible in the scoped current query | `publication_changed` |
| more than one current row | `graph_publication_invariant_failed` |

This final read is the M2 linearization check. The service discards all resolved data on failure. It never silently
re-resolves against the replacement publication in the same request.

## 13. Cross-Scope Error Matrix

| Input or state | Public code | Future HTTP | Non-disclosure rule |
|---|---|---:|---|
| Library slug not authorized/found | existing `library_not_found` | 404 | handled by M4 dependency |
| Entity ID from other Library/Ontology | `seed_not_found` | 404 | no unscoped ID lookup |
| Entity ID active but not in publication | `seed_not_found` | 404 | lifecycle state not disclosed |
| Name/type selector absent in scope | `seed_not_found` | 404 | type existence not disclosed |
| Name selector matches multiple published types | `seed_ambiguous` | 409 | candidates bounded to same scope |
| Expected publication from another scope | `publication_changed` | 409 | compare only to scoped current ID |
| Expected superseded publication | `publication_changed` | 409 | old snapshot contents not read |
| Relation Type key absent/inactive/cross-scope | `relation_type_not_found` | 409 | missing key not named in error |
| No current publication for scoped Ontology | `graph_publication_unavailable` | 503 | no ontology existence disclosure |
| Current publication degraded | `graph_publication_unavailable` | 503 | use v0.5 admin API for diagnosis |
| Partial/corrupt membership | `graph_publication_invariant_failed` | 503 | no count delta or row ID in error |

## 14. Query Count And Resource Contract

A mixed request with ID seeds, name seeds and Relation Type filters uses at most eight statements:

| Statement | Count |
|---|---:|
| start current publication | 1 |
| item aggregate | 1 |
| Entity aggregate | 1 |
| Relation/endpoint aggregate | 1 |
| ID seed batch | at most 1 |
| name seed batch | at most 1 |
| Relation Type filter batch | at most 1 |
| end fence | 1 |

The count is independent of the number of seeds and type keys. Empty selector groups skip their statement.

No M2 statement may:

- select `Entity.properties` or `KnowledgeRelation.properties`;
- select `EntityAlias`;
- select Evidence/source/context/raw Provider/Candidate text;
- use per-seed loops that execute SQL;
- load all Entity/Relation members into Python;
- issue writes, `flush`, `commit`, `rollback` or `FOR UPDATE`.

## 15. Failure And Transaction Semantics

- M2 functions are read-only and never own the caller's transaction lifecycle.
- They do not catch arbitrary database errors and relabel them as scope errors.
- Known contract failures use only `GraphRetrievalServiceError` stable codes.
- Unknown database/programming errors propagate to M4's sanitized 500 boundary later.
- A service error does not commit or roll back the session.
- No audit row is written for a read query.
- Start/end queries intentionally use separate `READ COMMITTED` snapshots so a concurrent v0.5 activation is detected.
- M2 never uses `include_degraded=true` or diagnostic publication reads.
