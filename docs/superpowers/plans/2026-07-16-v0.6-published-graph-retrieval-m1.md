# v0.6 Published Graph Retrieval M1 Implementation Plan

> **Status:** completed and accepted on 2026-07-16
>
> **Depends on:** approved v0.6 Published Graph Retrieval Master Design
>
> **Baseline:** commit `b1863f1`; Alembic head `0023`
>
> **Scope:** M1 contract, fail-closed configuration, startup validation and boundary tests only

## 1. Goal

Freeze the v0.6 request/response/error DTOs and fail-closed runtime limits without mounting a v0.6 route, querying graph
data, changing v0.5 publication behavior, or creating Migration `0024`.

M1 is complete only when later milestones can import one strict contract and one validated settings surface without
having to reinterpret privacy, limits or response ordering fields.

## 2. Binding Decisions

- `GRAPH_RETRIEVAL_ENABLED=false` by default.
- The only accepted contract version is `v1`.
- Master Design defaults are also absolute v1 caps. Operators may lower them but may not raise them:

| Limit | v1 cap |
|---|---:|
| seeds | 10 |
| hops | 2 |
| nodes | 100 |
| relations | 200 |
| Evidence locators per fact | 20 |

- Request `max_hops=0` remains valid even though the configured server maximum must be in `1..2`.
- `GRAPH_RETRIEVAL_TIMEOUT_SECONDS` must be finite and positive.
- `GRAPH_RETRIEVAL_MAX_NODES >= GRAPH_RETRIEVAL_MAX_SEEDS`.
- All v0.6 Pydantic models use `extra='forbid'`.
- `properties` is absent from every v0.6 response DTO.
- `include_properties` is absent from the request and is rejected as an extra field.
- M1 defines DTOs but does not add `/libraries/{slug}/v06/graph/query` to OpenAPI.
- M1 does not add a graph retrieval service module or database query.
- Alembic must continue to report exactly `0023 (head)`.

The absolute caps refine the Master Design's "server hard limit" requirement. Any future increase is a contract-version
change, not an environment-only operation.

## 3. DTO Contract

Add `app/schemas/v06_graph_retrieval.py` with:

- `GraphRetrievalSeed`;
- `GraphRetrievalQueryRequest`;
- publication, Entity Type and Relation Type references;
- Evidence locator, node, relation, seed-match, count and truncation DTOs;
- `GraphRetrievalQueryResponse`;
- bounded ambiguity candidate and sanitized error DTOs;
- Literal aliases for direction, source type, relation direction and error code.

Validation rules:

- a seed provides exactly one of `entity_id` and `canonical_name`;
- `entity_type_key` is legal only for a name seed;
- blank names/type keys are rejected;
- request seeds are bounded to 10;
- relation type filters are bounded to 64 entries and each key is at most 128 characters;
- request traversal limits cannot exceed the v1 absolute caps;
- hashes use lowercase 64-character SHA-256 syntax;
- confidence is in `[0, 1]` and depth is in `[0, 2]`;
- response models contain no formal `properties`, raw text or Provider/Candidate payload field.

## 4. Configuration And Startup

Add to `Settings`:

```text
graph_retrieval_enabled = false
graph_retrieval_contract_version = v1
graph_retrieval_max_seeds = 10
graph_retrieval_max_hops = 2
graph_retrieval_max_nodes = 100
graph_retrieval_max_relations = 200
graph_retrieval_max_evidence_per_fact = 20
graph_retrieval_timeout_seconds = 3.0
```

Add `validate_graph_retrieval_startup(config)` and call it from a dedicated
`assert_graph_retrieval_startup_security()` wrapper in the API lifespan. Validation runs even when the feature is
disabled so an invalid dormant configuration cannot be promoted later without a restart failure.

No route is mounted in M1.
