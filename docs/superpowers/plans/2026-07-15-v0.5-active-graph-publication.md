# v0.5 Active Graph Publication Implementation Plan

> **For agentic workers:** implement this plan milestone-by-milestone. Do not start a later milestone until the previous
> milestone has passing targeted tests, a scope scan, and a committed completion note in this document.

**Goal:** turn v0.4 draft graph facts into an auditable active graph publication with deterministic version snapshots,
atomic activation, safe version switching, rollback/re-activation, sanitized operational APIs, and lifecycle
reconciliation when source Evidence becomes stale.

**Architecture:** keep the current PostgreSQL, SQLAlchemy, FastAPI and Evidence-first graph architecture. v0.5 adds an
active-publication layer over the existing v0.3 formal graph rows and v0.4 materialized draft rows. It does not introduce
an external graph database, GraphRAG, graph QA, graph retrieval ranking, review UI, broad governance workflows, or
Provider/extraction changes.

**Tech Stack:** Python 3, pytest, FastAPI, Pydantic v2, SQLAlchemy async ORM, Alembic, existing Library permissions,
existing v0.2 Evidence lifecycle, existing v0.3 graph schema validation, existing v0.4 materialization output.

## Current State

v0.2 provides immutable document revisions and active Evidence rows.

v0.3 provides ontology versions, Entity Types, Relation Types, formal Entities, Entity Mentions, Knowledge Relations and
Relation Evidence. Entities and Relations have formal lifecycle states including `draft`, `pending_review`, `active`,
`stale`, `disabled` and `deleted`. `RelationEvidence` and `EntityMention` are Evidence-rooted support rows.

v0.4 provides fail-closed extraction and materializes eligible production Candidates as:

- draft Entities;
- active Entity Mentions as support rows;
- draft Knowledge Relations;
- active Relation Evidence as support rows.

v0.4 intentionally does not create active Relations, active graph versions, `graph_publications`, graph retrieval,
GraphRAG, review mutation/API or governance UI. v0.5 starts exactly at that boundary.

## Resolved Decisions For M1

These decisions replace open design questions and are binding for M1 schema/tests:

- Publication provenance lives in `graph_publications` and `graph_publication_items`. M1 does not add
  `published_by_publication_id` or similar direct publication columns to `entities` or `knowledge_relations`.
- `graph_publication_items` is the canonical membership source. Formal row `status='active'` is only a lifecycle marker,
  not a complete active-graph definition.
- Manual and imported Entities may be published without active mentions. Extracted Entities require at least one active
  Entity Mention unless `GRAPH_PUBLICATION_REQUIRE_ENTITY_EVIDENCE=false`.
- Every published Relation, regardless of source, requires at least one active `supports` Relation Evidence row. This is
  stricter than legacy v0.3 writes and is intentional for the first active graph publication release.
- Published Relations must have `review_status IN ('not_required','approved')`. `NULL`, `pending_review` and `rejected`
  are not publishable. The planner may derive `not_required` only for a legacy/manual Relation when the active Relation
  Type policy explicitly allows automatic activation.
- Degraded publications use `status='degraded'`. There must be at most one current publication per
  `(library_id, ontology_version_id)` where `status IN ('active','degraded')`.
- `pending_review` is a blocking state for both Entities and Relations in v0.5, not a dead-end lifecycle. M2 records
  blocked counts and reasons; a later v0.6/v0.8 review workflow may approve or reject those facts. v0.5 may also publish
  a later clean snapshot after manually curated facts are moved to `status='draft'` or `status='active'` with
  `review_status='approved'` where applicable by existing trusted data paths.

## Global Constraints

- Base branch is the accepted v0.4 boundary after `33c0bd8`.
- Migration head before v0.5 is exactly `0022`.
- v0.5 may create Migration `0023`; no other Alembic head is allowed.
- All v0.5 features are fail-closed by default.
- No publication path may expose Context text, raw Provider output, raw Candidate payloads, quotes, API keys or secrets.
- Active publication uses existing PostgreSQL formal graph rows; do not add Neo4j, OpenSPG, KAG or another graph store.
- Do not modify Qdrant payload construction, old retrieval behavior, Chat behavior, Dify response shape or embedding
  worker publication semantics.
- Do not call an LLM or extraction Provider from v0.5 publication code.
- Do not add review mutation UI/API. v0.5 may read existing `status` and `review_status`, but reviewer workflows remain
  later scope.
- Do not implement GraphRAG, graph QA, path search, vector+graph fusion, or answer generation.
- Do not auto-publish facts from Eval Jobs.
- Do not publish a Relation unless every required Evidence support row is active, in-library, current-revision-safe and
  bound to the same active ontology scope.
- Publication activation must be one database transaction. It must not perform external HTTP, Qdrant, filesystem, LLM or
  long-running operations inside that transaction.
- Every command must be idempotent by a server-owned idempotency key or deterministic manifest hash.
- Every scope-changing command must hold a Library/ontology publication lock and prove at most one active publication per
  `(library_id, ontology_version_id)`.

## Primary Design Decisions

### Publication Model

`graph_publications` is the version row. It records the publication lifecycle, source scope, activation metadata,
previous current publication, manifest hash, counts and sanitized error fields.

`graph_publication_items` is the immutable snapshot membership table. It records the exact Entity and Relation IDs in a
publication and their item hashes. The healthy active graph read contract is:

```text
healthy active graph = graph_publications.status == 'active'
                    + graph_publication_items for that publication
                    + formal rows whose status is still active
                    + active supports Evidence rows for published Relations
```

Raw `Entity.status == 'active'` or `KnowledgeRelation.status == 'active'` is not enough to define the active graph after
v0.5. Read helpers must join the active publication snapshot when they need publication-accurate results.

## Read Contract

Read helpers must separate lifecycle-active rows from publication-accurate active graph rows:

- Existing `graph_evidence.list_active_knowledge_relations` remains a legacy lifecycle helper and must not be used for
  publication-accurate graph reads.
- Add `list_current_graph_publication(db, library, ontology_version_id=None)` returning the current `active` or
  `degraded` publication summary for operator APIs.
- Add `list_healthy_published_entities(...)` and `list_healthy_published_relations(...)` that return rows only when the
  current publication status is `active`.
- Add `list_published_entities(..., include_degraded=False)` and `list_published_relations(..., include_degraded=False)`.
  With the default `False`, a degraded current publication returns an empty result plus health metadata or raises a
  typed `PublicationDegradedError` depending on service context. With `True`, it returns snapshot rows marked with
  degraded health metadata for diagnostics only.
- `GET /active` returns the current publication summary for both `active` and `degraded`. It returns `404` only when no
  current publication exists. The response must include `status` and `healthy: false` for degraded.
- Future graph retrieval must use only the healthy helpers. It must not silently read a degraded publication.

### Publication Lifecycle

Publication states:

```text
planned -> activating -> active
planned -> cancelled
planned/activating -> failed
active -> superseded
active -> degraded
degraded -> superseded
```

`degraded` means at least one published fact lost required active Evidence after source lifecycle changes. Degraded
publications remain the current pointer for audit and operator visibility, but must not be used by future graph retrieval.
A follow-up publication or rollback must be created to restore a healthy active snapshot.

### Snapshot Type

v0.5 uses full snapshots per `(library_id, ontology_version_id)`, not append-only publish batches. The planner must decide
the complete set of facts that should remain published. Activation supersedes the previous current snapshot and marks
facts not retained by the new snapshot stale only when they are no longer included by any current publication.

### Eligibility

An Entity can be included when:

- it belongs to the Library and active ontology;
- status is `draft` or `active`;
- source is `manual`, `imported` or `extracted`;
- it is not `pending_review`, `stale`, `disabled`, `deleted` or `rejected`;
- the Entity Type still exists, belongs to the same active ontology, and has `status='active'`;
- properties still pass the active Entity Type schema;
- it has at least one active mention when the publication policy requires Evidence support for extracted Entities.

A Relation can be included when:

- it belongs to the Library and active ontology;
- status is `draft` or `active`;
- `review_status` is non-null and is `not_required` or `approved`;
- it is not `pending_review`, `rejected`, `stale`, `disabled` or `deleted`;
- source is `manual`, `imported` or `extracted`;
- both endpoints are included in the same snapshot or already active in the same active publication;
- the Relation Type still exists, belongs to the same active ontology, and has `status='active'`;
- required properties still pass v0.3 schema validation;
- at least one `support_type='supports'` Relation Evidence row is active, in scope, and current-revision-safe;
- no active `support_type='contradicts'` Relation Evidence row exists for the same Relation;
- extracted facts meet the configured publication confidence floor.

`pending_review` Entities and Relations are intentionally not auto-published in v0.5 because review mutation is not in
scope.

Current-revision-safe means:

- the Evidence row has `status='active'`;
- the Document exists, belongs to the same Library and is not deleted;
- the Document has `status='ready'`;
- `Document.current_revision_id == support_row.document_revision_id`;
- the Document Revision exists, belongs to the same Library and Document, and has `status='ready'`;
- the support row's `library_id`, `document_id` and `document_revision_id` match the Evidence row.

### Eligibility Matrix

| Row kind | Publishable states | Blocking states | Support requirement |
|---|---|---|---|
| Entity | `draft`, `active` | `pending_review`, `rejected`, `stale`, `disabled`, `deleted` | Extracted Entities require active mentions when configured. |
| KnowledgeRelation | `draft`, `active` with `review_status IN ('not_required','approved')` | `pending_review`, `rejected`, `stale`, `disabled`, `deleted`, `review_status IS NULL` | At least one active `supports` Relation Evidence and zero active `contradicts`. |
| EntityMention | `active` | `stale`, `deleted` | Used only as Entity support; never published as a top-level item. |
| RelationEvidence | `active` | `stale`, `deleted` | Only `supports` IDs enter item hashes; `contradicts` blocks Relation publication. |
| EntityType | `active` | `draft`, `disabled`, `deleted` | Required for every Entity item. |
| RelationType | `active` | `draft`, `disabled`, `deleted` | Required for every Relation item. |
| OntologyVersion | `active` | `draft`, `disabled`, `deleted` | Required for the whole publication. |

### Rollback

Rollback is implemented as a new publication command that re-activates a previous snapshot if all of its items still pass
the same eligibility checks. Rollback never blindly flips `status` values from history. If old Evidence has gone stale,
rollback fails closed with a sanitized reason and leaves the current active publication unchanged.

### Initial Seed Strategy

The first v0.5 deployment must not silently hide existing active graph data. M2 owns `plan_initial_publication`, a normal
planner entry point that creates the first `planned` publication from the existing formal graph state:

- include existing eligible `active` Entities and Relations;
- include eligible v0.4 `draft` materialized facts when the operator asks for `include_drafts=true`;
- exclude and count blocked `pending_review`, stale, disabled, deleted, rejected or evidence-incomplete facts;
- store a `source_mode='initial_seed'` publication field;
- require explicit activation through the same M3 activation path.

There is no automatic activation during migration. Migration `0023` only creates schema. Operators must run the seed plan
and inspect sanitized counts before activating it.

### Hash Contracts

All hashes use canonical JSON with sorted keys, UTF-8, no insignificant whitespace, lowercase UUID strings, and no source
text. `None` is encoded as JSON `null`. Floats, including confidence values, are encoded as decimal strings rounded to six
places after validation; missing confidence is `null`. Lists, including `support_evidence_ids`, are sorted
lexicographically. `properties_hash` is the SHA-256 hex of the canonical JSON object after v0.3 schema validation and
normalization; an absent properties object hashes as canonical `{}`.

Entity item hash fields:

```text
manifest_version
item_kind
library_id
ontology_version_id
entity_id
entity_type_id
canonical_name
normalized_name
properties_hash
source_type
confidence
support_evidence_ids
```

Relation item hash fields:

```text
manifest_version
item_kind
library_id
ontology_version_id
relation_id
relation_type_id
source_entity_id
target_entity_id
properties_hash
source_type
confidence
support_evidence_ids
```

Publication manifest hash fields:

```text
manifest_version
policy_version
policy_snapshot_hash
library_id
ontology_version_id
source_mode
parent_publication_id
include_drafts
sorted_entity_item_hashes
sorted_relation_item_hashes
blocked_count_by_reason
```

`policy_snapshot_hash` covers all configured publication policy inputs, including entity Evidence requirement,
confidence floors, max item limit, allowed support types, manifest version and policy version.

## Milestones

### M1: Schema, Flags And Invariants

**Stage goal:** add the durable publication schema and fail-closed settings without changing any active graph behavior.

**Major tasks:**

- Add Migration `0023` after `0022`.
- Add `GraphPublication` and `GraphPublicationItem` ORM models.
- Add publication status CHECK constraints and item-kind CHECK constraints.
- Add a partial unique index that allows at most one current publication per `(library_id, ontology_version_id)` where
  `status IN ('active','degraded')`.
- Add a partial unique index or exclusion-equivalent guard that prevents duplicate non-terminal planning rows for the same
  `(library_id, ontology_version_id, manifest_hash, idempotency_key)` under concurrent planners.
- Add deterministic indexes for Library, ontology, status, previous publication and item lookup.
- Add fail-closed publication configuration.
- Export models for Alembic discovery.
- Add schema tests that forbid Context, raw output, prompt, quote, Candidate payload, API key or secret columns in the
  publication tables.

**Acceptance:**

- Alembic reports exactly `0023 (head)`.
- `0023 -> 0022 -> 0023` migration round-trip works on a disposable PostgreSQL database.
- With publication disabled, all v0.2, v0.3 and v0.4 behavior remains unchanged.
- Schema tests prove there is no active publication row before a publication command runs.

**Not in this stage:** no planner, activation, API, reconciliation, graph retrieval, GraphRAG or review workflow.

Commit point: `feat: add v0.5 graph publication schema`.

### M2: Planner, Eligibility And Manifest

**Stage goal:** produce deterministic planned publication snapshots without mutating formal graph status.

**Major tasks:**

- Implement a planner that loads Library, active ontology, formal Entities, formal Relations, Entity Mentions and
  Relation Evidence under Library/ontology scope.
- Implement `plan_initial_publication` for first deployment seed snapshots.
- Enforce all eligibility rules in this document.
- Build a full snapshot for `(library_id, ontology_version_id)`.
- Produce stable item hashes and a publication manifest hash using canonical JSON.
- Store a `planned` publication and immutable planned items.
- Make planning idempotent by `idempotency_key` for command replay and by `(library_id, ontology_version_id,
  manifest_hash)` for manifest reuse. A second plan request with the same manifest returns the existing reusable
  `planned`, `activating`, `active` or `degraded` publication even if it uses a different idempotency key.
- Serialize concurrent planners with a Library/ontology advisory lock or an equivalent row lock, then rely on the M1
  uniqueness guard as the final race-condition protection.
- Reject stale, disabled, deleted, rejected and pending-review Relations.
- Reject Relations whose endpoints are outside the planned snapshot.
- Reject extracted facts below the configured publication confidence floor.
- Reject any Evidence row that is inactive, stale, deleted, cross-library, cross-ontology, or not current-revision-safe.
- Record only sanitized counts and error codes.

**Acceptance:**

- Replanning the same formal graph produces the same manifest hash and no duplicate reusable publication.
- Permuting fact insertion order produces the same manifest and item order.
- Changing publication policy inputs changes `policy_snapshot_hash` and therefore the manifest hash.
- Planner writes no active facts and does not supersede any previous publication.
- Eval-created draft facts are ignored or rejected according to their Job scope.
- Initial seed planning preserves eligible existing active graph facts and reports blocked facts by reason.
- Planner tests cover every eligibility rejection branch.

**Not in this stage:** no active status change, no version switch, no rollback, no public API.

Commit point: `feat: plan deterministic graph publication manifests`.

### M3: Atomic Activation And Version Switch

**Stage goal:** activate one planned publication atomically and safely supersede the previous current snapshot.

**Execution tasks:**

#### Task 0: Stage Gate And Transaction Contract

- Preserve the M1 and M2 focused test baseline.
- Produce the missing disposable PostgreSQL `0022 -> 0023 -> 0022 -> 0023` migration evidence before M3 is accepted.
- Define activation as a service-owned transaction: callers pass an idle `AsyncSession`; the service commits the atomic
  version switch or rolls it back before returning.

#### Task 1: Scope Lock And Publication State Machine

- Lock Library first, then the target publication and current publication in deterministic order.
- Handle `planned`, interrupted `activating`, already `active` and terminal states explicitly.
- Guarantee that two activation commands for the same Library/ontology cannot both install a current publication.

#### Task 2: Locked Activation Recheck

- Recheck `GRAPH_PUBLICATION_ENABLED`, active ontology, immutable item counts/hashes and the stored manifest.
- Recheck every stored Entity and Relation against the M2 eligibility contract while the scope lock is held.
- Reject missing, cross-scope, schema-invalid, review-blocked, low-confidence or current-revision-unsafe facts.

#### Task 3: Atomic Formal Graph And Version Switch

- Move `planned -> activating -> active` in one transaction.
- Promote included Entities and Relations to `active`.
- Supersede the previous `active` or `degraded` publication and its items in the same transaction.
- Mark previously active Relations omitted by the new snapshot `stale`; keep support rows active only when their parent
  Relation remains active.
- Preserve provenance only through `graph_publication_items`; do not add direct publication fields to formal rows.

#### Task 4: Rollback Snapshot Planning

- Copy a previous `active`, `degraded` or `superseded` snapshot into a new `planned` rollback publication.
- Give the rollback command its own idempotency contract and retain `rollback_target_publication_id`.
- Send rollback through the same locked eligibility recheck and activation path; stale historical Evidence fails closed.

#### Task 5: Failure Persistence, Recovery And Audit

- Roll back the version-switch transaction completely on failure, then persist sanitized `failed` state in an independent
  short transaction when the session remains usable.
- Fence interrupted `activating` recovery and make already-active retry idempotent.
- Emit a structured audit record or operational log for `active`, `superseded` and `failed` transitions without graph
  payloads, quotes or Evidence text.

### Failure Semantics

Activation has two persistence phases:

1. The activation/version-switch phase is one short transaction. It locks scope, rechecks eligibility, promotes included
   formal rows, activates items, activates the publication and supersedes the previous current publication. If this
   transaction fails, it rolls back completely.
2. The failure-record phase is an independent short transaction. It may mark the planned publication `failed` with a
   sanitized `error_code`/`error_message`, but it must not modify the previous `active` or `degraded` publication, formal
   fact status, support rows or item membership.

Retry rules:

- Retrying a successfully active publication returns the active publication unchanged.
- Retrying a failed publication is not allowed; callers must create a new planned publication with a new idempotency key
  or reuse the same manifest through the planner.
- Retrying after an ambiguous client timeout must read by idempotency key before creating a new plan.
- A planned publication whose activation is interrupted while `status='activating'` is recovered by M3 with a fenced
  recheck. If no active switch happened, it can be failed or retried; if the switch happened, it is completed as active.
