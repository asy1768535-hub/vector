## Frozen Contracts

### 1. Phase Order And Human Gate

The release order is immutable:

```text
dataset freeze
-> tooling and Mock/PostgreSQL acceptance
-> real Development Smoke
-> selected calibration run
-> human review and eval_policy_v1 freeze commit
-> post-freeze run 1
-> post-freeze run 2
-> post-freeze run 3

```

The calibration run does not count as one of the three post-freeze runs. The implementation agent must stop after the
selected calibration artifact is committed and request explicit human approval of the four precision/recall
thresholds, approver identity and UTC freeze time. It must not invent approval metadata or auto-freeze policy.

Any model, base URL, Prompt content, Parser, extraction policy, Context policy, ontology, normalization or dataset
change after calibration requires a new calibration. Any such change after `eval_policy_v1` is frozen requires a new
Eval Policy version and three new post-freeze runs. Existing artifacts remain immutable and are not rewritten.

### 2. Dataset Record Contract

All committed source text is synthetic and repository-safe. `release_v1.jsonl` contains one canonical JSON object per
document in ascending `document_key` order:

```json
{
  "schema_version": "graph-extraction-eval-document-v1",
  "document_key": "release-001",
  "title": "Synthetic title",
  "security_level": "internal",
  "units": [
    {
      "unit_key": "u001",
      "text": "One complete synthetic Evidence statement."
    }
  ],
  "gold_entities": [
    {
      "gold_id": "e001",
      "canonical_name": "Canonical name",
      "entity_type_key": "department",
      "evidence_unit_keys": ["u001"],
      "aliases": []
    }
  ],
  "gold_relations": [
    {
      "gold_id": "r001",
      "source_gold_id": "e001",
      "relation_type_key": "responsible_for",
      "target_gold_id": "e002",
      "evidence_unit_keys": ["u001"]
    }
  ]
}
```

Dataset validation is strict:

- unknown or missing fields fail;
- document keys are globally unique and sorted;
- Unit keys and gold IDs are unique inside a document;
- every document has at least one Unit and every Unit text is non-empty;
- every gold Evidence reference resolves to a Unit in the same document;
- every Relation endpoint resolves to an Entity gold ID in the same document;
- every type/relation/constraint is valid under the frozen enterprise ontology;
- every gold quote is exactly the referenced Unit text; no paraphrased quote or cross-Unit synthetic Evidence exists;
- aliases are labels on one gold Entity and never standalone Entity gold facts;
- source records contain no UUID, database ID, API key, real person/project/customer identifier or external URL.

The Release manifest selects at least 30 documents and must total at least 100 Units, 100 Entity gold facts and 100
Relation gold facts. The Development Smoke manifest selects exactly 10 fixed documents from the same frozen source
file. It does not mutate or sample randomly at runtime.

`gold_v1.json` encodes exactly the six Chinese Units, six Entity facts, eleven Entity Evidence bindings, five Relation
facts and five Relation Evidence bindings frozen in Master Plan section 20.1.

### 3. Canonical Hashes And Deterministic Seeding

Use the existing M4 canonical JSON/hash helper. Do not hash checkout bytes or newline style.

```text
dataset_content_sha256 = SHA-256(canonical JSON of selected parsed records in manifest order)
dataset_manifest_sha256 = SHA-256(canonical JSON of the complete parsed manifest)
```

Every Eval database is seeded with deterministic UUIDv5 identifiers derived from a fixed M6 namespace plus
`dataset_id/document_key/unit_key/schema-key`. Library, ontology, schema, Document, Revision, Chunk and Evidence IDs
therefore remain identical across independent databases. This is required so each Job freezes the same ontology
snapshot hash.

For a run, every Job must have identical model, policy, ontology and Prompt hashes. The report-level hash is:

```text
evaluation_config_hash = SHA-256(canonical JSON of:
  model_config_hash
  policy_config_hash
  ontology_snapshot_hash
  prompt_content_hash
  prompt_version
  extractor_version
  output_parser_version
  context_policy_version
  extraction_policy_version
  normalization_rule_version
  confidence_policy_version
  document_parser_version
  chunking_strategy_version)
```

Document identity, run ID, Job ID, Attempt ID, timestamps and Provider request IDs are not config inputs. The runner
fails if Jobs inside one run disagree on any frozen config input.

### 4. Prediction Keys And Precision/Recall

Metrics use exact deterministic keys, never fuzzy, embedding, LLM-as-judge or manual after-the-fact matching.

Entity key:

```text
(document_key, entity_type_key, normalize_graph_name_v1(canonical_name))
```

Relation key:

```text
(document_key, normalized source Entity key, relation_type_key, normalized target Entity key)
```

Directed Relation endpoints preserve order. Undirected endpoint keys are sorted. Proposed aliases do not create
predictions. Every unpurged persisted Candidate is included in the prediction population regardless of
`validated`, `pending_review` or `rejected` status; status breakdowns are supplementary. A rejected bad extraction
therefore cannot disappear from precision.

Multiple Candidates with the same evaluation key count once in the set intersection and contribute their extra rows
to the duplicate count. Matching is one-to-one set equality. Report micro totals and rates:

```text
precision = TP / (TP + FP)
recall = TP / (TP + FN)
```

The release dataset guarantees non-zero gold and prediction denominators. A zero or missing denominator produces
`null`, not `1.0`, and fails the release gate. Per-type and per-document metrics may be reported but never replace the
global micro gate.

### 5. Operational Metric Denominators

The metric engine records numerator, denominator and decimal value for every rate. Rounded display values are not
used for gates.

- `real_model_call_count`: all pre-created Attempts for the selected run, including timeout/network/HTTP failures and
  abandoned pending Attempts. Retry Attempts remain separate and count.
- `json_parse_rate`: Attempts with `request_status=succeeded` and `parse_status=valid` divided by all Attempts.
- `schema_valid_rate`: Relation Candidates with `ontology_validation_status=valid` divided by all persisted Relation
  Candidates produced by successfully parsed Attempts.
- `entity_precision/recall`: exact Entity set totals above.
- `relation_precision/recall`: exact Relation set totals above.
- `invalid_evidence_rate`: atomic Candidate Evidence rows with `validation_status=invalid` divided by all atomic
  Candidate Evidence rows. Ambiguous rows are reported separately.
- `candidate_duplicate_rate`: extra rows after grouping by evaluation key divided by all persisted Candidates.
- `cross_revision_evidence_count`: Candidate Evidence whose resolved revision differs from its Job revision.
- `eval_formal_write_count`: Entity, Mention, Relation or Relation Evidence rows with `created_by_job_id` from an Eval
  Job. It must be zero.

Eval Jobs never call the Materializer. The Master Plan's formal `materialized relation evidence coverage`, illegal
active relation, duplicate formal Relation, expired-token write and failed-Job active-graph gates are verified by the
deterministic production-mode PostgreSQL acceptance, not by pretending Eval Candidates were materialized. The final
release verdict requires both the real-provider quality artifacts and those operational PostgreSQL gates.

### 6. Isolated PostgreSQL Runner

`scripts/graph_extraction_eval.py` is an internal operator CLI, not an API. It reads the admin connection only from
`VECTOR_KB_M6_EVAL_ADMIN_DSN` and the Provider credential only through `GRAPH_EXTRACTION_API_KEY` in the current
process `os.environ`. An old value loaded only from `.env` is not explicit authorization for a real run. The runner
requires the process value to be non-empty and identical to the Secret seen by the accepted Provider path. Neither
credential may appear in argv, stdout, result JSON, logs or exceptions. After the pivot, this variable contains only an
official DeepSeek API key; a DashScope or `CHAT_*` key is not an accepted substitute.

Real runs require all of:

```text
GRAPH_EXTRACTION_ENABLED=true
GRAPH_EXTRACTION_AUTO_TRIGGER_ENABLED=false
non-empty GRAPH_EXTRACTION_API_KEY
--real-provider
--confirm-external-send <exact synthetic dataset_id>
an explicit database name matching ^vkt_m6_eval_[a-z0-9_]+$
```

The runner refuses an existing non-empty database, a non-synthetic manifest, a security level other than `internal`,
any base URL/model snapshot other than `https://api.deepseek.com/v1` plus `deepseek-chat`, a dirty dataset hash or an
API key from any `CHAT_*` fallback. It
creates/upgrades only the named Eval database, verifies `0022 (head)`, seeds one opt-in Eval Library with deterministic
IDs, creates current ready revisions and `trigger_type=eval/execution_mode=eval` Jobs, then invokes the accepted M5
claim/process/retry services.

Workers may run concurrently with a bounded `--workers 1..8`; they still use normal PostgreSQL leasing and fencing.
Provider HTTP remains outside transactions. Retry waves use the original Job and preserve all Attempts. Every selected
Release run uses a distinct clean database and distinct run ID. The runner never uses the same-fingerprint full-rerun
exception and never weakens production duplicate blocking.

Release databases are retained through acceptance so Attempt audit rows remain inspectable. After sign-off, the
operator may run the accepted purge and dispose of the database. The runner never deletes failed Attempts to make a
rate look better.

### 7. Result Artifact And Privacy Contract

Every invocation requires a unique `--run-id` and writes one new JSON file; existing files are never overwritten.
Interrupted or failed runs write a sanitized failed artifact when possible and are not silently reused.

Each artifact contains only:

```text
schema_version, run_id, phase, status
started_at, finished_at, code_commit, alembic_head
database_name, dataset_id, dataset counts and hashes
model provider/name (no key), frozen component versions and evaluation_config_hash
Job IDs, Job/Unit/Attempt status counts
real_provider boolean and SHA-256 of sorted non-empty Provider request IDs
all metric numerators/denominators/values
safety counts and sanitized stable error-code counts
policy version/hash for post-freeze runs
```

Artifacts must not contain dataset source text, title, canonical Entity names, aliases, quotes, Context, Prompt,
messages, request/response bodies, parse errors, free-form Provider errors, API keys, headers, raw Provider request IDs
or complete Settings dumps. The Provider request-ID digest is evidence without disclosing IDs.

The CLI writes artifacts atomically through a temporary file and rename. Artifact validation rejects NaN/Infinity,
unknown fields, rounded-only rates, timestamps outside the run interval, a dirty Git tree for selected release runs,
or a code commit that is not the checked-out commit.

### 8. Eval Policy Freeze

`eval_policy_v1.json` is created only after a selected successful calibration artifact exists and a human explicitly
approves it. It contains:

```json
{
  "schema_version": "graph-extraction-eval-policy-v1",
  "policy_id": "eval_policy_v1",
  "dataset_manifest_sha256": "64 lowercase hex",
  "evaluation_config_hash": "64 lowercase hex",
  "calibration_result_path": "eval/graph_extraction/results/<run-id>.json",
  "calibration_result_sha256": "64 lowercase hex",
  "thresholds": {
    "entity_precision": 0.85,
    "entity_recall": 0.75,
    "relation_precision": 0.85,
    "relation_recall": 0.70
  },
  "approved_by": "human identity",
  "approved_at": "RFC3339 UTC",
  "approval_reference": "review reference"
}
```

The shown numbers are Master Plan protection floors, not automatically approved final thresholds. Human-approved
values may be higher but never lower. The policy validator requires the exact selected calibration hash, Release
manifest hash and evaluation config hash. The freeze commit is recorded in the final acceptance report.

Once committed, `eval_policy_v1.json` is immutable. Lowering a threshold, changing config/dataset, or selecting a new
calibration requires a new policy version and a fresh three-run sequence; do not amend or rewrite v1.

### 9. Post-Freeze Release Verdict

`release_evidence_v1.json` references by relative path and SHA-256 exactly one calibration artifact, one immutable
policy and three distinct post-freeze artifacts. The verifier fails unless:

- all four selected real runs used the same Release manifest and evaluation config hash;
- every selected Release run has `real_provider=true` and at least 100 real model-call Attempts;
- post-freeze run IDs and database names are pairwise distinct;
- every post-freeze Job and Unit finishes `succeeded`; failed Provider Attempts may remain only when a later original-
  Job retry succeeds;
- every post-freeze run has JSON parse rate at least `0.99` and Schema valid rate at least `0.95`;
- every post-freeze run independently meets all four frozen precision/recall thresholds;
- every selected run has zero cross-revision Evidence and zero Eval formal writes;
- the deterministic PostgreSQL artifact proves 100% formal Relation Evidence coverage, zero illegal active Relation,
  zero duplicate materialized Relation, zero expired-token writes and zero failed-Job modifications to existing active
  graph facts;
- M1-M5, v0.2/v0.3, Dify, Qdrant payload, Chat and old retrieval compatibility gates pass on the selected code commit.

Calibration metrics are reported but never substitute for a post-freeze run. A mean across runs cannot hide one failed
run. Any failure leaves v0.4 incomplete.

| Risk | Required control | Recovery |
|---|---|---|
| Real source data is sent externally | Only committed synthetic manifests; exact dataset confirmation; Library opt-in and `internal` allowlist | Cancel run, revoke key if needed, purge retained Eval DB and record incident; do not accept artifact |
| API key or raw response enters Git/logs | Environment-only secrets, allowlisted artifact schema, privacy scanner, no free-form errors | Revoke credential, remove artifact before commit, create a new run after remediation |

| Thresholds are chosen to fit results | Human freeze after calibration, hard protection floors, immutable policy commit | Reject policy; obtain reviewed thresholds and rerun post-freeze sequence |
| Dataset changes after calibration | Canonical manifest/content hashes in policy and every artifact | New calibration and policy version; retain old artifacts |

| Fresh databases produce different ontology hashes | Deterministic UUIDv5 seeding and same-config assertion | Fix seeder before real calibration; all earlier results become non-selectable |
| Failed Attempts disappear | Original-Job Retry and retained databases; no delete/overwrite in runner | Reject artifact and rerun in a new database after audit fix |
| Provider rate limit makes run partial | Bounded workers, normal retry Attempts, complete Job requirement | Preserve failed result; rerun with a new ID, never edit counts |
| Provider billing/account state rejects every call | Minimal preflight after explicit approval; stable sanitized HTTP category; immutable failed artifact | Restore the official DeepSeek account, obtain new approval and rerun with a new ID/database |
| M6 drifts into v0.5 | Scope scans and zero active Relation/publication/retrieval files | Revert out-of-scope commit; M6 remains incomplete |
