## 1. Goal

M5 proves that the completed M1-M4 endpoint is correct, deterministic, private and operationally bounded before M6 final
release acceptance.

The required sequence is:

```text
strict synthetic dataset and metric engine
-> isolated PostgreSQL correctness runner
-> 10,000-item performance and EXPLAIN runner
-> sanitized production observation events
-> one calibration artifact
-> STOP for explicit human threshold approval
-> immutable release_policy_v1
-> three independent post-freeze database runs
-> release_evidence_v1 offline verification
-> M5 completion record and M6 planning handoff
```

M5 evaluates structured graph retrieval only. It does not compare generated answers, call a model, rank natural-language
questions or implement GraphRAG.

## 2. Non-Goals

M5 does not implement:

- natural-language query parsing, entity linking, GraphRAG, answer generation or LLM-as-judge;
- dense/vector/keyword versus graph ranking or fusion;
- Qdrant, Dify, Chat, reranking, Provider or extraction behavior changes;
- alias, fuzzy, temporal, shortest-path or traversal-contract changes;
- response properties, properties filters, source text or an `include_properties` escape hatch;
- publication, formal graph, review or Evidence mutation in production;
- a new public/admin/metrics endpoint or a Prometheus/OpenTelemetry dependency;
- a metrics label containing Library, Publication, Entity, Relation, type key or slug;
- automatic server retry, timeout increase or query-limit increase;
- new tables, columns, indexes, models or Migration `0024`;
- performance fixes hidden inside the evaluation milestone;
- final v0.6 release acceptance, which remains M6.

If the frozen M4 query cannot meet the default three-second timeout with adequate margin, implementation stops and this
design returns to review. M5 must not raise the timeout, add an index or alter query semantics to manufacture a pass.

## 3. Repository Facts And Reuse Decisions

The repository already provides:

- `canonical_graph_json_v1` and `canonical_graph_value_hash_v1` for semantic canonical JSON;
- strict Pydantic artifact, policy and release-evidence precedent in `graph_extraction_eval.py`;
- disposable PostgreSQL database create/upgrade/drop precedent with non-skipped acceptance;
- v0.5 planner/activation and v0.6 M2-M4 correctness helpers;
- a single v0.6 route with fixed privacy and timeout behavior.

The repository does not provide a metrics backend, request-ID middleware or `/metrics` endpoint. M5 therefore uses a
small standard-library observation module and emits allowlisted structured log events from the existing v0.6 route. It
does not introduce an in-memory counter that would look durable, nor a new monitoring dependency or endpoint. The
operator runbook defines how a deployment converts the stable metric events into backend-specific counters/histograms.

The v0.4 graph-extraction release verifier is precedent, not a schema to import or extend. Graph retrieval gets separate
v1 types and paths because its dataset, metrics, privacy rules, performance fields and response hashes are different.

All JSON models are `extra='forbid'`, frozen and finite-number-only. JSON files are written as

non-canonical file bytes, duplicate keys/records, CRLF differences, trailing blank lines and invalid UTF-8.

Each artifact reference records both:



## 7. Synthetic Gold Graph Contract

`gold_v1.json` defines a repository-safe synthetic graph using symbolic keys, never database-generated IDs:

```json
{
  "schema_version": "graph-retrieval-gold-v1",
  "dataset_id": "release-v1",
  "ontology": {
    "ontology_key": "release-ontology-v1",
    "entity_types": [],
    "relation_types": []
  },
  "evidence": [],
  "entities": [],
  "relations": [],
  "privacy_canaries": [],
  "scenario_publications": []
}
```

Exact implementation schemas must include:

- Entity: `entity_key`, type key, canonical/normalized name, source type, confidence, support Evidence keys and synthetic
  properties used only as privacy canaries;
- Relation: `relation_key`, type key, source/target Entity keys, source type, confidence, support Evidence keys and
  synthetic private properties;
- Evidence: `evidence_key`, Document/Revision/optional Block keys and only locator coordinates needed for gold matching;
- schema direction for every Relation Type;
- scenario publication key and desired state (`active`, `degraded`, `superseded` or partial/corrupt negative fixture);
- privacy canary IDs plus synthetic key/value strings; no credential-looking value, real identifier or external URL.

Privacy properties must include nested synthetic markers representing `secret`, `token` and `source_text` key/value
shapes. The marker values are repository-safe canaries, not credential-looking strings. Each canary is assigned to one or
more success, fixed error and invalid-request cases so response, log and error surfaces are all evaluated.

The release dataset must contain at least:

```text
40 Entities
40 Relations
20 Evidence locators
2 Libraries
2 Ontologies in the primary Library
1 directed and 1 undirected Relation Type
1 high-degree subgraph with more than 200 eligible Relations
1 cycle and 1 duplicate-path diamond
2 same-normalized-name Entities with different Entity Types
12 nested property privacy canaries across Entity and Relation rows
```

All symbolic keys are unique, lowercase and sorted. Every endpoint/support reference resolves locally. Evidence points to
the current ready revision unless the row belongs to an explicit negative scenario.

## 9. Deterministic Database Seeding

The runtime creates a fresh database named only with the prefix `vkt_v06_m5_eval_`. It refuses:

- the configured application database name;
- an existing target database;
- a database outside the exact prefix;
- a missing admin DSN;
- a database whose Alembic head is not upgraded to `0023`;
- cleanup of any name other than the exact database it created.

Every Library, Ontology, Type, Document, Revision, Block, Evidence, Entity and Relation ID uses UUIDv5 from one fixed M5
namespace and a symbolic dataset path. Publication runtime IDs/timestamps produced by v0.5 are mapped to logical
publication keys by canonical response projection. The runner uses accepted v0.5 plan/activation behavior for healthy
scenarios and explicit isolated-database mutations only for degraded/superseded/corrupt negative fixtures.

The runner validates after seed:

- publication counts and active item membership exactly match gold;
- every gold Relation endpoint is an active item in the same publication;
- frozen support IDs match the intended Evidence logical keys;
- all success Evidence is same-scope and current-ready;
- properties canaries exist in formal rows but not fact snapshots or response DTOs;
- no application/audit row is created by query execution;
- no test ever points the API dependency at the configured non-eval database.

The database is dropped in `finally`. A failed drop is reported as a gate failure, not hidden by the query result.

## 10. Canonical Response Projection V1

Raw response JSON is never committed. Each response is validated against the public DTO and converted in memory to a
complete logical projection:

- every runtime UUID must map to a known Library/Ontology/Publication/Entity/Relation/Evidence/Document/Revision/Block
  symbolic key; an unknown ID fails the run;
- `publication.activated_at` must be valid UTC but is represented by the fixed token `dataset-activation-v1`;
- publication/item/manifest hashes remain in the projection and must be identical across databases;
- every public contract field is represented; no semantic field is silently dropped;
- error status/detail/candidates are represented with candidates mapped to logical keys;
- response list order is preserved exactly;
- the projection contains no properties, source text, SQL, log text or raw runtime UUID.

Each case executes three times per database after fixture setup. Define:

```text
canonical_case_response_sha256 = SHA-256(canonical logical projection)
canonical_response_set_sha256 = SHA-256(canonical ordered list of:
  {case_id, status_code, canonical_case_response_sha256})
```

All three repeats for a case must match. The three post-freeze runs must have identical
`canonical_response_set_sha256`. Latency, database ID, timestamps and observation events are not response-hash inputs.

## 11. Metric Contract

All metrics are exact micro-aggregates over explicitly defined populations. Rates store `numerator`, `denominator` and
`value`; denominator zero produces `value=null` and can never pass a required threshold.

| Metric | Numerator | Denominator |
|---|---|---|
| Seed exact accuracy | selectors with exact expected match/rejection | all evaluated seed selectors |
| Node Recall | expected bounded node keys returned | expected bounded node keys |
| Relation Recall | expected bounded relation keys returned | expected bounded relation keys |
| Relation Precision | expected returned relation keys | all returned relation keys |
| Evidence Coverage | expected Relation/Evidence pairs returned | expected Relation/Evidence pairs |
| Determinism | repeat comparisons equal to first response hash | all required repeat comparisons |
| Scope Safety | safety-negative cases returning exact rejection with no candidates/leak | all safety-negative cases |
| Property Privacy | canary/surface checks with no match | canaries x response/log/error surfaces checked |

Additional exact diagnostics include:

- case pass/fail counts and stable error-code counts;
- unexpected/missing node, relation and Evidence-pair counts;
- publication-membership check count and failure count;
- node/relation/Evidence truncation case counts;
- maximum SQL statements after authorized Library resolution;
- timeout cancellation and post-rollback connection-reuse success;
- disabled-feature old-path compatibility result.

Correctness is deterministic, not statistical. Calibration may not lower these hard gates:

```text
Seed exact accuracy = 1.0
Node Recall = 1.0
Relation Recall = 1.0
Relation Precision = 1.0
Evidence Coverage = 1.0
Determinism = 1.0
Scope Safety = 1.0
Property leak count = 0
Property Privacy = 1.0
gold publication membership failures = 0
```

Calibration selects performance ceilings only; the policy still records every quality threshold explicitly.

## 12. 10,000-Item PostgreSQL Performance Fixture

The manifest freezes a generated performance graph rather than committing 10,000 JSON records:

```text
6,000 active Entity publication items
4,000 active Relation publication items
10,000 total publication items
at least 250 Relations on one high-degree seed
at least one two-hop branch with more than 100 nodes
same-scope ready Evidence on all facts selected by measured Evidence-on cases
deterministic UUIDv5 IDs, names, types, item hashes and topology
```

The generator version, namespace, counts, topology parameters, Evidence distribution and expected manifest hash are part
of the dataset manifest and evaluation config hash. Generation is followed by the same M2 publication invariant checks.

Measured scenarios are:

```text
1-hop, Evidence off
1-hop, Evidence on
2-hop, Evidence off
2-hop, Evidence on
high-degree relation truncation
high-degree node truncation
```

For each scenario:

1. resolve the authorized Library before measurement;
2. run five unrecorded warm-ups;
3. run at least thirty serial measured samples with `perf_counter_ns`;
4. verify the response hash and SQL statement budget on every sample;
5. convert each sample to integer microseconds with `ceil(duration_ns / 1000)` and compute nearest-rank p50/p95 as
   `sorted_samples[ceil(percentile * sample_count) - 1]`, without interpolation;
6. run one separate `EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON, TIMING OFF)` per distinct SQL shape;
7. discard the raw SQL, bound parameters and raw plan after extracting normalized fields.

Latency samples do not include database creation, migration, seed, Library authorization, JSON artifact writes or
EXPLAIN. They do include the complete M4 graph service through final publication fence. A mounted ASGI endpoint smoke
separately proves the three-second timeout and rollback contract.

## 13. EXPLAIN And Scanned-Row Contract

Raw SQL, parameters and full plan JSON never enter an artifact or log. For every plan node, extract only:

```text
node_type
relation_role (allowlisted logical role, never physical table/alias text)
actual_rows
actual_loops
rows_removed_by_filter
shared_hit_blocks
shared_read_blocks
temp_read_blocks
temp_written_blocks
```

Normalized values are non-negative integers. Define:

```text
node_rows_observed = (actual_rows + rows_removed_by_filter) * actual_loops
scan_rows_observed = sum(node_rows_observed for node types containing "Scan")
plan_rows_observed = sum(node_rows_observed for all nodes)
plan_shape_sha256 = SHA-256(canonical tree of allowlisted logical role + node_type only)
```

The artifact records maxima by stable SQL shape name, never raw SQL. Calibration proposes scanned-row ceilings as
`ceil(observed_max * 1.10)`. Human approval must select a ceiling between the observed maximum and that candidate,
inclusive. A higher value requires a new calibration.

## 14. Performance Threshold Freeze

Calibration records p50/p95 and proposes a ceiling for every measured scenario:

```text
candidate_max_p95_us = min(
  2_400_000,
  max(
    ceil(calibration_p95_us * 1.25),
    calibration_p95_us + 5_000))
```

Every candidate must be at most `2_400_000 us`, leaving 20% headroom under the fixed three-second API timeout. If any
calibration p95 exceeds that hard ceiling, M5 stops. The threshold is not raised and the timeout is not changed.

The calibration and all post-freeze runs must share a sanitized environment fingerprint over:

- PostgreSQL `server_version_num`;
- Python major/minor version;
- PostgreSQL `shared_buffers`, `work_mem`, `effective_cache_size`, `random_page_cost` and `jit` settings;
- runner sample/warm-up counts and timing protocol version.

No hostname, IP, username, password, filesystem path or database DSN enters the fingerprint input or artifact. A changed
fingerprint requires a new calibration rather than comparing incomparable p95 values.

## 18. Post-Freeze And Release Evidence Contract

Each post-freeze run must:

- use phase `post-freeze` and a unique run ID/database ID;
- create a new database rather than reuse calibration or another run database;
- bind the exact policy canonical/file SHA;
- match dataset/config/tree/environment hashes;
- independently pass every frozen threshold;
- have the same ordered case IDs and identical `canonical_response_set_sha256`;
- cleanly drop its database after artifact material is held in memory;
- atomically write a previously nonexistent result file only after cleanup succeeds.

`release_evidence_v1.json` uses `graph-retrieval-release-evidence-v1` and references exactly one calibration, one policy
and three post-freeze artifacts by relative scoped path plus canonical/file SHA. The loader rejects:

- absolute paths, `..`, symlinks or paths outside `eval/graph_retrieval`;
- missing, duplicate or extra references;
- duplicate run IDs or database IDs;
- noncanonical bytes or hash mismatch;
- calibration counted as post-freeze;
- policy approval before calibration;
- dataset/config/tree/environment mismatch;
- policy threshold weakening or properties exposure;
- non-UTC timestamps;
- failed/missing/null required gates;
- fewer or more than three post-freeze runs;
- differing canonical response-set hashes;
- any artifact privacy scanner failure.

The verifier never accepts a mean across runs, a skipped PostgreSQL gate, a handwritten report or a mock artifact.
