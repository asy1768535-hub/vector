## 1. Goal

M3 turns the M2 healthy snapshot and exact seed resolution into a deterministic, bounded internal graph traversal.
Given one `HealthyGraphSnapshot`, resolved seeds and optional resolved Relation Type filters, it must return:

1. unique published nodes with minimal BFS depth;
2. unique published relations with deterministic discovery depth and order;
3. independent node/relation truncation flags;
4. no dangling relation and no row outside the fenced publication;
5. the same ordered result for the same request and healthy publication.

M3 remains an internal read service. M4 will hydrate Evidence, build response DTOs, enforce HTTP permission/feature/timeout
semantics and mount the route.

## 2. Non-Goals

M3 does not implement:

- `POST /libraries/{slug}/v06/graph/query` or any FastAPI route;
- Evidence ID selection, Evidence locator hydration or current-revision validation;
- Pydantic response assembly, HTTP status mapping, permission dependencies, timeout handling, logging or metrics;
- natural-language query parsing, GraphRAG, LLM calls, vector search, Qdrant, Dify or Chat integration;
- aliases, fuzzy resolution, temporal filtering, shortest path, all paths, ranking or scoring;
- formal `properties` reads, filters, sorting, output or logging;
- review mutation, publication mutation, audit writes or governance UI;
- changes to M2 snapshot, seed or Relation Type error semantics;
- changes to v0.5 planning, activation, reconciliation or healthy-read helpers;
- a table, column, index, model change or Migration `0024`;
- M5 performance thresholds or release artifacts.

## 5. Internal Types

Use frozen, slotted dataclasses and tuples. No M3 result may contain an ORM instance.

### 5.1 `TraversedPublishedEntity`

```text
entity_id: UUID
item_hash: str
entity_type_id: UUID
entity_type_key: str
entity_type_label: str
canonical_name: str
normalized_name: str
source_type: str
confidence: float | None
depth: int
```

Seed nodes are converted from `ResolvedPublishedEntity` at depth 0. Non-seed nodes are projected by the hop query. The
type excludes `input_index`, properties, authority, status timestamps, Evidence IDs and source text.

### 5.2 `TraversedPublishedRelation`

```text
relation_id: UUID
item_hash: str
relation_type_id: UUID
relation_type_key: str
relation_type_label: str
relation_type_direction: Literal['directed', 'undirected']
source_entity_id: UUID
target_entity_id: UUID
source_type: str
confidence: float | None
depth: int
```

The source and target always preserve the formal Relation orientation. Inbound and undirected traversal never swap them.
The type excludes properties, authority, temporal fields, review state, Evidence IDs and source text.

### 5.3 `GraphTraversalTruncation`

```text
nodes: bool
relations: bool
```

Evidence truncation remains M4-owned and is not represented by M3.

### 5.4 `PublishedGraphTraversal`

```text
nodes: tuple[TraversedPublishedEntity, ...]
relations: tuple[TraversedPublishedRelation, ...]
truncated: GraphTraversalTruncation
```

Nodes are ordered by `(depth, discovery_order)`, with depth-0 nodes ordered by Entity UUID. Relations are ordered by the
Master Design key `(depth, relation_type_key, source_entity_id, target_entity_id, relation_id)`.

### 5.5 `GraphRetrievalTraversalResolution`

```text
resolution: GraphRetrievalResolution
traversal: PublishedGraphTraversal
```

This wrapper preserves the accepted M2 result as-is while adding the M3 result. It avoids changing the fields or return
type of the accepted M2 `resolve_graph_retrieval_query` convenience function.

The full M3 orchestrator order is fixed:

```text
runtime configured-limit validation
-> M2 start snapshot and membership invariants
-> M2 exact seed resolution
-> M2 Relation Type filter resolution
-> M3 deterministic traversal
-> M2 end publication fence

```

If the end fence fails, all traversal data is discarded. The service never retries against a replacement publication.
The existing M2 orchestrator remains unchanged for its accepted tests and internal compatibility. M4 must use the new M3
orchestrator rather than call the M2 convenience orchestrator and traverse after its end fence.

## 7. Seed Initialization And Zero-Hop Contract

Initialization is pure Python and executes no SQL:

1. Build the input-to-Entity mapping from the original M2 seed tuple without modification.
2. Deduplicate traversal seeds by `entity_id`.
3. Sort unique seed Entity IDs by UUID ascending.
4. Convert each unique seed to a traversal node at depth 0.
5. Set the depth-0 frontier to those sorted IDs.

The M1/M2 validation `max_nodes >= len(request.seeds)` guarantees enough capacity for all unique seed nodes.

For `max_hops=0`:

- return only the unique depth-0 seed nodes;
- return no relations;
- set both M3 truncation flags false;
- execute no traversal statement;
- still execute the M2 start checks, resolution and end fence in the full orchestrator.

Duplicate seed selectors may produce duplicate M4 `seed_matches`, but never duplicate traversal nodes or frontier work.

## 8. Per-Hop Batch SQL

M3 executes at most one traversal statement for each requested hop. It never executes SQL inside a per-node loop.

### 8.1 Fixed scope and membership predicates

Every hop statement starts from active Relation publication items and joins explicit columns from:

```text
GraphPublicationItem relation item
KnowledgeRelation
RelationType
GraphPublicationItem source Entity item
Entity source endpoint
EntityType source type
GraphPublicationItem target Entity item
Entity target endpoint
EntityType target type
```

Every item, formal row and type join must require:

- the exact `snapshot.publication_id`, `snapshot.library_id` and `snapshot.ontology_version_id` where applicable;
- publication item `status='active'` and the correct `item_kind`;
- formal Entity/Relation `status='active'`;
- Relation `review_status IN ('not_required', 'approved')` as a predicate only;
- active Entity Type and Relation Type rows in the same Library/Ontology;
- source and target Entity items in the same publication.

This repeats the eligibility predicates at each layer so no returned edge is dangling or assembled from a stale row.
The accepted M2 aggregate validation remains the global fail-closed check before traversal.

### 8.2 Direction predicate

The request and Relation Type direction matrix is exact:

| Request | Directed Relation | Undirected Relation |
|---|---|---|
| `outbound` | source endpoint is in frontier | either endpoint is in frontier |
| `inbound` | target endpoint is in frontier | either endpoint is in frontier |
| `both` | either endpoint is in frontier | either endpoint is in frontier |

The SQL predicate must implement this matrix directly. Direction filtering may not be deferred to a Python full-graph
scan. A self-loop is eligible once when its single endpoint satisfies the predicate.

### 8.3 Relation Type allowlist

When resolved filters are non-empty, the query filters by the resolved same-scope `relation_type_id` values. It does not
re-resolve untrusted keys and does not use labels.

When filters are empty, omit the allowlist predicate and keep the active same-scope Relation Type join.

### 8.4 Seen Relation exclusion

Relations already emitted at a lower depth are excluded in SQL by their bounded ID set. The set is at most
`max_relations` and is passed as a bound collection, not interpolated SQL.

This ensures that an edge incident to multiple frontier nodes, a cycle edge, a self-loop or a duplicate path is returned
at most once and that over-fetch capacity is spent only on unseen relations.

### 8.5 Projection and ordering

The query uses explicit column projection for the relation, Relation Type, both endpoint items, both Entities and both
Entity Types. It must not select a full ORM row.

SQL ordering is exactly:

```text
RelationType.key ASC
KnowledgeRelation.source_entity_id ASC
KnowledgeRelation.target_entity_id ASC
KnowledgeRelation.id ASC
```

Depth is constant within one hop and is added by the service. Python applies the same key defensively before folding the
bounded rows.

The projection must not include:

```text
properties
authority_level
review_status
valid_from / valid_to
support_evidence_ids
description / properties_schema / review policy
Evidence, Document, block, quote, context, prompt or raw Provider text
```

`KnowledgeRelation.review_status` is allowed only inside the eligibility predicate.

### 8.6 Bounded over-fetch

Let `relation_slots = max_relations - emitted_relation_count`.

Each hop query uses:

```text
LIMIT max(1, relation_slots + 1)
```

The extra row proves relation truncation without loading the full adjacency. When no relation slots remain but another hop
is reachable, a one-row probe is allowed to determine whether an unseen eligible relation exists. The probe counts as
that hop's single statement and never adds a node or relation.

At v1 absolute limits, each hop materializes at most 201 SQL rows in Python.

## 9. Deterministic BFS Fold

Traversal is level-order and uses these state collections:

```text
nodes_by_id
node_discovery_order
seen_relation_ids
ordered_relations
frontier_ids
```

Rules:

1. Expand only nodes first discovered in the immediately preceding depth.
2. Sort each frontier by Entity UUID before building the SQL predicate.
3. Fold bounded query rows in the canonical relation order.
4. Emit each Relation at most once, at the first depth where it is eligible.
5. For each emitted Relation, identify its undiscovered opposite endpoint. Because every candidate is adjacent to the
   current frontier, at least one endpoint is already known and one Relation can introduce at most one new Entity.
6. An Entity is added at its first discovery only and retains that minimal depth.
7. The next frontier contains only newly discovered Entities, deduplicated and sorted by Entity UUID before the next SQL
   statement.
8. Stop when `max_hops` is reached, the frontier is empty, or a deterministic truncation condition stops traversal.

Cycles, diamonds, reciprocal directed edges and parallel Relations of different IDs are valid. Cycles do not rediscover
nodes; parallel Relations remain distinct and retain canonical ordering.

## 10. Truncation Contract

Truncation is determined against the next candidate in the canonical stream, not merely by `count == limit`.

For every unseen candidate Relation:

1. Determine whether emitting it would exceed `max_relations`.
2. Determine the set of undiscovered endpoints required to emit it without a dangling edge.
3. Determine whether adding all required endpoints would exceed `max_nodes`.
4. If neither cap would be exceeded, atomically add the complete Relation and all required nodes.
5. If either cap would be exceeded, add none of that Relation or its new endpoints, set each corresponding flag and stop
   the traversal at that deterministic prefix.

The flags mean:

- `nodes=true` only when an otherwise eligible candidate needs one or more new endpoints that do not fit;
- `relations=true` only when an otherwise eligible unseen candidate does not fit the Relation cap;
- both may be true for the same next candidate;
- reaching an exact numeric limit with no additional eligible candidate leaves the corresponding flag false;
- a Relation connecting only already-returned nodes may still be emitted when the node count equals `max_nodes`;
- no Relation is ever emitted without both endpoint nodes.

Stopping at the first non-fitting canonical candidate makes every truncated result a stable prefix. M3 does not skip a
non-fitting Relation and return later Relations.

M4 will add Evidence truncation independently without changing these node/relation flags.

## 11. Result Ordering And Canonicalization

M3 output order is part of the v1 contract:

- depth-0 nodes: Entity UUID ascending;
- depth greater than 0 nodes: first discovery order from the canonical Relation stream at that depth;
- relations: `(depth, relation_type_key, source_entity_id, target_entity_id, relation_id)`;
- identical input selectors and publication state produce byte-identical canonical test serialization.

No output ordering may depend on PostgreSQL natural order, insertion time, Python set/dict construction order or request
concurrency. Confidence and source type are metadata and never participate in ordering.

## 12. Query Count And Resource Contract

A worst-case mixed two-hop M3 orchestrator uses at most ten SQL statements:

| Statement | Maximum count |
|---|---:|
| M2 current publication start | 1 |
| M2 item/entity/relation aggregates | 3 |
| M2 ID seed batch | 1 |
| M2 name seed batch | 1 |
| M2 Relation Type filter batch | 1 |
| M3 traversal batch | `max_hops`, at most 2 |
| M2 end publication fence | 1 |

General formula:

```text
8 + max_hops for a mixed request
```

Empty seed selector groups and an empty type allowlist skip their corresponding M2 statements. `max_hops=0` executes no
M3 traversal statement.

Resource limits:

- frontier IDs are bounded by `max_nodes <= 100`;
- seen Relation IDs are bounded by `max_relations <= 200`;
- each hop returns at most `max_relations + 1 <= 201` rows;
- Python retains at most 100 nodes and 200 Relations plus bounded working sets;
- no full publication or full formal graph is loaded into Python;
- no recursive SQL, per-node query, write, lock, flush, commit or rollback is issued.

M5, not M3, owns the 10,000-item `EXPLAIN (ANALYZE, BUFFERS)` and p50/p95 release benchmark. M3 must nevertheless
freeze a query shape that can be measured there.

## 13. Failure, Consistency And Transaction Semantics

- M3 uses the existing `GraphRetrievalServiceError` codes and adds no error code.
- Invalid request/configured limits fail before database access through the M2 validator.
- Pre-existing partial membership fails in the M2 start aggregates before traversal.
- Every returned hop row rechecks active item/formal/type state and both endpoint memberships.
- Missing or invalid rows are never converted into dangling output.
- Publication switch, disappearance, degradation or identity drift at the final fence discards the entire result using
  the accepted M2 error ordering.
- M3 does not lock, auto-retry, commit, roll back or own the caller's transaction lifecycle.
- Unknown database/programming errors propagate for M4's future sanitized 500 boundary.
- M3 writes no audit or business row and emits no request data to logs.

The normal PostgreSQL isolation remains `READ COMMITTED`. M3 does not introduce repeatable-read or `FOR UPDATE`.
