## Goal

Turn the M1-M4 contracts into an operational, fail-closed graph extraction pipeline:

```text
current ready Document Revision
-> production Job and frozen Ontology Snapshot
-> queued Units
-> leased Unit Worker
-> M2 Context / Attempt / Provider / Parser
-> M3 Candidate Evidence
-> M4 aggregation / validation / routing
-> production-only non-active Materializer
-> API, retry/rerun/cancel, auto trigger, compensation scan and purge
```

M5 is the first milestone that consumes Units and may call the configured external Provider. It still does not run the
real DashScope release Eval, freeze precision/recall thresholds, publish active graph versions, expose graph retrieval,
build a governance UI, or create Migration `0023`. Those remain M6, v0.5 or later.

## Frozen Contracts

### Job Creation

`graph_extraction_jobs.py` owns production Job creation:

```python
create_graph_extraction_job(db, *, library, document, revision, trigger_type,
                            execution_mode, requested_by, idempotency_key,
                            rerun_of_job_id=None) -> GraphExtractionJob
```

Rules:

- Ordinary API and auto trigger accept only the document's current ready revision.
- Global graph extraction, Library graph extraction, external LLM opt-in, non-empty security allowlist, revision security
  level, document not-deleted and current-ready status are checked before creating a Job.
- Historical revisions are rejected for ordinary production API paths.
- `trigger_type='eval'` remains internal and cannot materialize.
- The input fingerprint includes document revision identity, Unit fingerprints, model/prompt/parser/context/policy
  versions, model and policy config hashes, ontology snapshot hash, prompt content hash, normalization version,
  confidence policy version and materialization thresholds.
- For `manual`, `revision_published`, `repair` and `eval` creation paths, any existing Job with the same semantic
  `input_fingerprint` blocks duplicate creation, including cancelled Jobs.
- Admin `full_rerun` is the only explicit exception to same-`input_fingerprint` blocking. It stores the same semantic
  fingerprint when the source revision/config is unchanged, but it must provide a new globally unique
  `idempotency_key` and `rerun_of_job_id` so the rerun is intentional and auditable. Repeating the same full-rerun
  idempotency key must not create another Job.
- Job creation inserts all queued Units in deterministic Chunk order. A Unit is planned only when it has an active
  same-scope center Evidence.

### Ontology Snapshot Builder

The production builder must read active v0.3 ontology rows and emit exactly the strict M4 snapshot contract:

```python
build_ontology_rule_snapshot(db, *, library, ontology_version_id) -> tuple[dict, str]
```

The snapshot includes active Entity Types, Relation Types, Relation Constraints and Attribute Definitions only. Arrays
are canonicalized exactly as M4 expects; the hash uses the same canonical JSON contract. Duplicate keys, malformed JSON
schemas or missing active ontology rows fail Job creation before any Unit is queued.

### Worker And Lease

`graph_extraction_worker.py` owns Unit processing. The Worker loop:

1. emits heartbeat metadata with `mode='active_worker'`;
2. runs a bounded compensation scan;
3. claims one queued Unit using `FOR UPDATE SKIP LOCKED`;
4. writes `processing`, `worker_id`, random `claim_token`, `claimed_at` and `lease_expires_at` in a short transaction;
5. builds/reuses Context;
6. pre-creates a pending Attempt with M2 fencing;
7. calls Provider outside any database transaction or row lock;
8. finalizes the Attempt with the claim token;
9. parses, stages, aggregates, validates and routes through M2-M4;
10. marks the Unit terminal and updates Job counts/stage.

Every result write is fenced by the live claim token. If lease renewal or finalization affects zero rows, the Worker
discards in-memory Provider output and performs no Candidate or formal write.

Stale recovery follows the M1 contract: pending Attempts for lost processing Units are marked `abandoned`, retryable
Units return to `queued` while budget remains, exhausted Units become `failed/retryable=false`, and claim fields are
cleared before another Worker may create a new Attempt.

Candidate invalidity, ambiguity, low confidence or conflict is a successful Unit outcome. Infrastructure errors,
scope violations, malformed frozen snapshots, Provider failures after retry budget and parser/protocol failures may
fail the Unit.

### Retry And Rerun

Ordinary Retry:

- `POST /libraries/{slug}/v04/graph-extractions/{job_id}/retry`;
- runs inside the original Job;
- only failed retryable Units with remaining model attempt budget return to queued;
- increments `retry_generation`;
- returns `409 no_retryable_units` when nothing can be retried;
- never creates a retry Job.

Full Rerun:

- `POST /libraries/{slug}/v04/graph-extractions/{job_id}/rerun`;
- requires admin identity and Library scope;
- creates a new Job with `trigger_type='full_rerun'` and `rerun_of_job_id`;
- requires a new idempotency key;
- does not revive cancelled or purged rows from the old Job.

Cancel:

- cancels queued/processing Jobs in the same Attempt -> Unit -> Job order used by Library safety cancellation;
- pending Attempts become `abandoned/unit_cancelled`;
- queued/processing Units become `cancelled/unit_cancelled` and clear claim fields;
- already terminal Units remain terminal.

### Materializer

`graph_extraction_materializer.py` may run only when:

- Job `execution_mode='production'`;
- all Units are terminal and none failed;
- Job still points to the current ready revision;
- document is not deleted;
- global and Library safety gates still pass;
- Job ontology snapshot still corresponds to an active ontology version;
- Candidate routing has completed.

Materializer writes only non-active formal graph facts:

- Entity Candidate: only `status='validated'`, final confidence above entity threshold and non-purged Evidence.
- If `matched_entity_id` is an eligible exact active/draft formal Entity, reuse it; otherwise create a draft Entity
  through the v0.3 service path.
- Create active Entity Mentions for each valid Entity Candidate Evidence row using deterministic extraction keys.
- Relation Candidate: only `status='validated'`, `evidence_support_mode='single_evidence'`, `ontology_validation_status='valid'`,
  no conflict, final confidence above relation threshold and endpoints with materialized or matched Entities.
- Create draft Knowledge Relations through the v0.3 relation service path.
- Create active Relation Evidence only from valid Candidate Evidence. Deduplicate by formal `relation_id` plus
  `resolved_evidence_id`; do not flatten Evidence Groups.
- Populate `created_by_job_id`, `extraction_key`, `materialized_entity_id` and `materialized_relation_id`.
- Mark Candidates `materialized` only after formal writes succeed.

In this plan, "non-active formal graph facts" means no active Entity, no active Knowledge Relation, no active graph
publication and no active graph-version switch. Active Entity Mentions and active Relation Evidence are support rows
attached to draft formal facts; they are not themselves an active graph publication or an active Relation fact.

Materializer does not create active Relations, active graph versions, aliases, external mappings, merge records or
review decisions. Materialization is a single Job-level database transaction over all eligible Candidates. Any
Candidate materialization failure rolls back every formal row written for that Job attempt, leaves Candidates
non-materialized, and marks the Job failed with a sanitized error. M5 does not allow partially materialized Jobs.

### API

Add router prefix:

```text
/libraries/{slug}/v04/graph-extractions
```

Endpoints:

```text
POST   /                         create manual production Job for current ready revision
GET    /                         list Jobs with filters and pagination
GET    /{job_id}                 read Job summary, counts and stage
GET    /{job_id}/units           list Units and attempts summary
GET    /{job_id}/candidates      list Candidate summaries
POST   /{job_id}/retry           ordinary Retry
POST   /{job_id}/rerun           admin full Rerun
POST   /{job_id}/cancel          cancel queued/processing Job
```

Permissions:

- read endpoints require `require_lib("read")`;
- create, retry and cancel require `require_lib("insert")`;
- rerun also requires admin identity;
- no endpoint returns Context text, raw Provider output, raw Candidate payloads, quotes, API keys or secrets.

### Auto Trigger And Compensation

When a revision becomes current ready, the existing publication path tries to enqueue a graph extraction Job in a new
transaction. Failure to enqueue must not roll back document publication.

Auto trigger requires both global `GRAPH_EXTRACTION_ENABLED` and `GRAPH_EXTRACTION_AUTO_TRIGGER_ENABLED`, all Library
safety gates, current ready revision, non-empty security level and active ontology. It must not enqueue historical
revisions.

Each Worker poll runs a compensation scan with `LIMIT 100` over current ready revisions satisfying the same safety
gates. Any existing same-`input_fingerprint` Job blocks automatic enqueue, including cancelled Jobs created before an
opt-out. Only an admin `full_rerun` with a new idempotency key can create a replacement after security authorization
changed.

### Sensitive Purge

`graph_extraction_purge.py` owns immediate and scheduled purge:

- document deletion and revision cleanup call it through existing cleanup paths;
- queued/processing work is cancelled before payload purge;
- Context `context_json`, `context_text`, document metadata and title-path payloads are nulled;
- Attempt `raw_response`, `parsed_response` and `parse_error` are nulled;
- Occurrence raw payloads are nulled;
- Candidate names, aliases, properties, external hints, review reasons and validation errors are nulled;
- Candidate Evidence quote text, source span and validation error are nulled;
- Merge/Conflict `details`, `description` and `evidence` are nulled;
- every affected row gets `purged_at`;
- Job gets `sensitive_payload_purged_at`;
- IDs, hashes, statuses, timestamps, counts, non-sensitive resolved scope IDs and sanitized error codes remain.

The scheduled Cleanup Worker calls the same service in batches. Purge is idempotent and must satisfy the existing
database purge CHECK constraints, not merely write timestamps.

## Risks And Controls

| Risk | Required control | Recovery |
|---|---|---|
| Worker writes after losing lease | Every write carries claim token; zero-row updates discard in-memory output | Requeue or fail through stale recovery, never force-write |
| Job duplicates send the same source text twice | Fingerprint and idempotency checks include frozen config and revision identity | Admin full Rerun only with new idempotency key |
| Materializer creates active graph facts | Use v0.3 services with draft formal facts and active support rows only; scope scan formal writes | Revert Materializer commit; staging rows are non-active audit data |
| Security opt-out races with Worker or Materializer | Recheck gates before claim, Provider call and Materializer; cancellation clears in-flight claims | Cancel Job permanently and require admin full Rerun after reauthorization |
| Purge marks timestamps but leaves payload | Database CHECK constraints and tests inspect every sensitive column | Disable Worker, rerun purge service, then resume |
| Auto trigger rolls back document publication | Enqueue in a separate transaction and catch/report failure | Compensation scan can enqueue later if still safe |

## Definition Of Done

- Job creation freezes the same ontology snapshot contract M4 consumes.
- Units are claimed, renewed, retried and recovered with short transactions and fencing tokens.
- Provider calls never run inside database transactions or row locks.
- M2-M4 services are reused rather than duplicated.
- Materializer writes only production, validated, single-evidence, non-active formal facts.
- Retry stays inside the original Job; full Rerun creates a new Job.
- API responses are permission-checked and sanitized.
- Auto trigger and compensation are fail-closed and idempotent.
- Immediate and retention purge remove sensitive payloads, not just mark rows.
- Real PostgreSQL Mock end-to-end acceptance, inherited regressions, full suite, Ruff and `0022 (head)` pass.
- M5 completion is recorded before M6 planning begins.
