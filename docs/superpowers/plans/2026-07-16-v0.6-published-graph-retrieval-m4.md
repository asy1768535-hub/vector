## 1. Goal

M4 exposes the accepted M1-M3 internal retrieval pipeline as one authorized read-only API and adds bounded Evidence
locators from the frozen publication manifest.

For a successful request M4 must:

1. authorize `read` access to exactly one active Library;
2. enforce the independent graph retrieval feature gate and timeout budget;
3. run the accepted snapshot, exact resolution and deterministic traversal pipeline;
4. read Evidence IDs only from each selected publication item's frozen `support_evidence_ids`;
5. validate selected Evidence against the current ready Document revision;
6. assemble the strict M1 response DTO without properties or source text;
7. run one final publication fence after Evidence hydration;
8. return deterministic node, Relation and locator ordering with exact counts/truncation flags.

M4 is the first milestone that mounts `/libraries/{slug}/v06/graph/query`. It remains a structured graph read endpoint,
not GraphRAG or answer generation.

## 2. Non-Goals

M4 does not implement:

- evaluation datasets, quality metrics, `EXPLAIN`, p50/p95 or 10,000-item performance acceptance;
- M5 release policy, calibration or three post-freeze artifacts;
- operational metrics, high-cardinality labels or expanded structured request logging;
- source text, file bytes, quote text, Evidence snapshots, block text or Document normalized text responses;
- formal Entity/Relation properties, properties filters or `include_properties`;
- Chat, Dify, Qdrant, LLM, GraphRAG, reranking or answer generation;
- aliases, fuzzy matching, temporal filtering, shortest path or traversal changes;
- review/publication/formal graph mutation, audit business rows or idempotency records;
- a new permission action, shared `require_lib` behavior change or per-Document ACL system;
- admin UI or graph visualization UI;
- a table, column, index, model or Migration `0024`;
- changes to old retrieval/Chat/Dify/Qdrant/extraction/publication behavior.

M5 owns evaluation, performance and observability. M6 owns final release acceptance and operator documentation.

## 3. Required M1 Error Forward-Fixes

FastAPI's default request validation response includes rejected input values. A malicious or accidental request containing
a seed name, `properties` object or secret-like extra field could therefore be echoed in the 422 body even though the
strict DTO correctly rejects it. Unknown exceptions can likewise expose unsafe text if mapped with `str(exc)`.

Before mounting the route, extend `GraphRetrievalErrorCode` with exactly:

```text
graph_retrieval_invalid_request
graph_retrieval_internal_error
```

Contracts:

| HTTP | Code | Condition |
|---:|---|---|
| 422 | `graph_retrieval_invalid_request` | Pydantic/body/path validation before service execution |
| 500 | `graph_retrieval_internal_error` | unknown non-contract exception at the API boundary |

Both use `GraphRetrievalErrorResponse` with `candidates=[]`. Their body and logs must not include the validation error
list, rejected body, exception class/message, SQL, stack trace or bound parameters.

`graph_retrieval_limit_exceeded` remains the 422 code for a structurally valid request that exceeds a configured runtime
cap. No other M1 DTO field or limit changes in M4.

## 4. Permission Clarification

The Master Design says to reuse `require_lib('read')`. The current repository's accepted shared dependency deliberately
returns the same `403 {"detail":"forbidden"}` for a missing, deleted or unreadable Library to prevent existence
disclosure. It does not return `404 library_not_found`.

M4 must preserve that existing behavior:

- unauthenticated requests retain the existing authentication response;
- missing/deleted/unreadable Library requests return the existing 403 before graph service execution;
- an authorized superuser or principal with Library `read` may query;
- `insert`, `delete` or unrelated permissions alone do not grant the endpoint;
- M4 does not modify `app/deps.py`, Casbin actions or shared API behavior.

The existing `library_not_found` graph error Literal remains reserved but is not emitted by this route's dependency path.
This explicit clarification must be approved before implementation.

## 6. Shared M3 Core And Final Fence

The accepted public M3 orchestrator currently performs its end publication fence immediately after traversal. M4 must
not hydrate Evidence after that fence and return without a later linearization check.

Refactor inside `app/services/graph_retrieval.py` only:

```text
_resolve_and_traverse_graph_retrieval_query_unfenced(...)
    -> GraphRetrievalTraversalResolution
```

The private core performs the accepted M3 order through traversal but does not run the end fence.

The accepted public M3 function keeps the same signature, return type, statement count and behavior:

```text
resolve_and_traverse_graph_retrieval_query(...)
    -> private unfenced core
    -> assert_graph_snapshot_still_current
    -> return
```

M4 adds a higher-level service function that uses the same private core:

```text
execute_graph_retrieval_query(...)
    -> private unfenced M3 core
    -> optional bounded Evidence hydration
    -> response DTO assembly
    -> assert_graph_snapshot_still_current
    -> return response
```

This is one query path, not a duplicate loader/resolver/traversal implementation. Existing M2/M3 public functions and
tests remain backward-compatible.

If Evidence hydration detects a known invariant failure, M4 first runs the final publication fence once to distinguish a
concurrent publication switch/degradation from stable-publication Evidence corruption. A failing fence takes precedence;
if the fence passes, return `graph_publication_invariant_failed`. Unknown SQL/programming errors remain unknown and go to
the sanitized 500 API boundary.

## 7. Internal Evidence Types

Use frozen, slotted dataclasses and tuples. Never return publication item, Evidence, Document, Revision or Block ORM rows.

### 7.1 `HydratedFactEvidence`

```text
item_kind: Literal['entity', 'relation']
fact_id: UUID
locators: tuple[GraphRetrievalEvidenceLocator, ...]
```

### 7.2 `GraphEvidenceHydration`

```text
facts: tuple[HydratedFactEvidence, ...]
truncated: bool
```

`facts` follows selected traversal order: all nodes in response order, then all Relations in response order. A response
assembler may build a temporary `(item_kind, fact_id)` lookup but must not expose it.

The only Evidence payload retained is the strict M1 locator DTO. No internal type contains quote, text, metadata,
visibility/security policy, full support arrays or ORM objects.

## 8. Selected Fact Input

Build a bounded input tuple from the accepted M3 traversal:

```text
output_index
item_kind
fact_id
expected_item_hash
```

Rules:

- one row per returned node and Relation, at most 300 rows;
- nodes precede Relations and preserve their accepted M3 order;
- `fact_id` is Entity ID for `entity` and Relation ID for `relation`;
- `expected_item_hash` is the M2/M3 publication item hash already carried by the result;
- duplicate `(item_kind, fact_id)` is an invariant failure, not silently collapsed.

No request-supplied ID is added here unless it already resolved into the selected published traversal.

## 9. Bounded Frozen Support Selection

M4 must not project each item's complete `support_evidence_ids` JSONB array into Python. v0.5 does not impose a per-item
support count, so doing that would make a request's Python memory depend on an unbounded array.

Use one PostgreSQL statement with a `VALUES` input for the selected facts and safe bounded lateral JSONB indexing.

### 9.1 Publication item join

Join each selected fact to exactly one `GraphPublicationItem` using:

- exact snapshot publication, Library and Ontology IDs;
- `status='active'`;
- matching item kind and corresponding Entity/Relation target column;
- stored `item_hash == expected_item_hash`;
- exact target shape.

The statement may reference `support_evidence_ids` only for bounded SQL-side extraction. It must not select
`fact_snapshot`, `support_counts`, properties or a full item ORM row.

### 9.2 Safe JSONB extraction

For each matched item the statement returns:

```text
output_index
item_kind
fact_id
support_shape_valid
support_count
support_position
selected_evidence_id_text
```

Requirements:

- guard JSONB functions with `CASE` so a non-array value becomes a reported invalid shape, not an unknown database error;
- use `jsonb_array_length` for total count;
- use a lateral `generate_series(0, least(safe_array_length, configured_cap) - 1)`;
- read each selected value by JSONB array index and expose `index + 1` as the support position;
- preserve one fact row even when its support list is empty;
- never materialize more than `max_evidence_per_fact` support strings per fact in Python.

Do not use `jsonb_array_elements*` followed by a filter/limit: PostgreSQL may enumerate the complete array before applying
that bound. The generated index range must itself be capped before JSONB values are read.

At absolute v1 limits, the support selection returns at most 6,000 rows total. An empty-support fact consumes one row;
a non-empty fact consumes at most the configured cap.

### 9.3 Shape and order validation

For each fact:

- item cardinality must be exactly one;
- support JSON must be an array;
- selected positions must be contiguous from 1;
- each selected value must be a lowercase canonical UUID string;
- selected UUIDs must be non-decreasing, matching the v0.5 frozen sorted-list contract;
- selected row count must equal `min(support_count, configured_cap)`;
- negative or inconsistent counts fail closed.

v0.5 does not enforce uniqueness for every EntityMention binding, so duplicate Evidence UUIDs are not publication
corruption. Preserve the bounded raw prefix for validation/truncation, then stable-deduplicate UUIDs per fact before
locator attachment. A duplicate locator is not repeated in one fact's response and is hydrated from PostgreSQL only once.

Any failure raises only `graph_publication_invariant_failed` without values/count deltas in the error.

### 9.4 Evidence truncation

Global `truncated.evidence=true` if at least one selected fact has `support_count > configured_cap`.

Reaching the cap with exactly that many supports is not truncation. Empty support lists are valid and produce empty
locator tuples. M4 does not claim every manual Entity has Evidence.

Only the first configured-cap IDs from the already sorted frozen list are selected and safety-validated. Unselected IDs
are not hydrated or returned.

## 10. Evidence Locator Hydration

Deduplicate all selected Evidence UUIDs across facts and issue at most one explicit-column query.

### 10.1 Required joins and predicates

The query joins:

```text
EvidenceUnit
Document
DocumentRevision
optional DocumentBlock
```

For every selected Evidence ID require:

- `EvidenceUnit.id` in the bounded selected set;
- Evidence same Library and `status='active'`;
- Document ID and Revision ID exactly match the Evidence row;
- Document same Library, not deleted, `status='ready'`;
- `Document.current_revision_id == EvidenceUnit.document_revision_id`;
- Revision same Library and Document, `status='ready'`;
- when `document_block_id` is non-null, Block exists and has the same Library, Document and Revision.

The query selects only:

```text
evidence_id
document_id
document_revision_id
document_block_id
joined_document_block_id
evidence_kind
page_start / page_end
source_start / source_end
```

It must not select title paths, positions, text quote/hash, Evidence metadata, visibility/security values, Document title or
metadata, Revision normalized text/config, Block text/content/position or source file data.

### 10.2 Exact hydration

Hydrated row IDs must equal the selected unique ID set exactly. Missing, duplicate, cross-scope, inactive,
historical-revision or invalid-Block rows fail closed as `graph_publication_invariant_failed`.

Validate the strict locator shape before returning:

- non-blank Evidence kind within the DTO bound;
- page positions are positive and ordered when present;
- source offsets are non-negative and ordered when present;
- joined Block identity matches the locator's non-null Block ID.

Attach locators to each fact in frozen support UUID order after stable per-fact deduplication. The same Evidence may appear
under multiple facts but is read from PostgreSQL only once. Response counts include each cross-fact attachment.

## 11. `include_evidence_locators=false`

When the request flag is false:

- skip both the publication-item support query and Evidence query;
- attach an empty Evidence list to every node and Relation;
- set `truncated.evidence=false`;
- do not fail because an unrequested Evidence row drifted after publication activation;
- still execute the final publication fence and all M2/M3 graph invariants.

This flag controls locator work only. It does not relax publication membership, traversal, privacy or final-fence rules.

## 12. Response Assembly

Add a pure assembler:

```text
build_graph_retrieval_response(
    result: GraphRetrievalTraversalResolution,
    hydration: GraphEvidenceHydration,
    *,
    contract_version: str,
) -> GraphRetrievalQueryResponse
```

Mapping is exact:

- publication identity from `HealthyGraphSnapshot`;
- `seed_matches` from M2 seeds in input order, including duplicate selectors;
- nodes and Relations from M3 in accepted order;
- Entity/Relation Type identity, key, label and direction from accepted projections;
- item hashes from M2/M3;
- locator tuples from M4 hydration;
- node/relation truncation from M3 and Evidence truncation from M4;
- counts equal actual serialized collection sizes and attached locator occurrences;
- contract version equals validated `v1` configuration.

Construct and return the strict M1 Pydantic DTO before the API boundary. Any unexpected DTO validation failure is converted
to sanitized `graph_publication_invariant_failed`, not returned as a raw Pydantic error.

No assembly path accepts or inspects formal properties.

## 13. Service Statement And Resource Budget

A worst-case mixed two-hop graph service request with locators uses at most twelve SQL statements:

| Statement | Maximum count |
|---|---:|
| M2 current publication start | 1 |
| M2 item/entity/relation aggregates | 3 |
| M2 ID and name seed batches | 2 |
| M2 Relation Type filter | 1 |
| M3 traversal | 2 |
| M4 selected fact support extraction | 1 |
| M4 selected Evidence hydration | 1 |
| final publication fence | 1 |

Formula for a worst-case mixed request:

```text
10 + locator support query + locator hydration query = at most 12
```

When locators are disabled the accepted M3 ten-statement maximum remains. If every selected support list is empty, the
support query runs but the Evidence query is skipped, so the maximum is eleven.

Resource limits:

- selected facts: at most 300;
- support strings materialized in Python: at most 6,000;
- unique Evidence hydration IDs: at most 6,000;
- locator occurrences in the response: at most 6,000;
- support and locator queries are batch queries, never per-fact/per-Evidence N+1;
- no full support JSON array, source text or Document/Block content is loaded into Python;
- no writes, locks, flushes, commits or audit rows.

M5 will measure query plans and p50/p95. M4 must freeze this bounded shape first.

This budget begins after the existing authentication/`require_lib('read')` dependency has supplied the authorized
Library. Existing auth/permission dependency statements are not graph service statements and are measured separately at
the HTTP layer.

## 14. REST API Contract

Add one router:

```text
POST /libraries/{slug}/v06/graph/query
```

Router prefix and tag:

```text
/libraries/{slug}/v06/graph
v0.6-graph-retrieval
```

Endpoint dependencies:

```text
library: Library = Depends(require_lib('read'))
db: AsyncSession = Depends(get_db)
```

The route is always mounted and appears in OpenAPI even when disabled. After successful authentication/authorization and
request validation, `GRAPH_RETRIEVAL_ENABLED=false` returns `503 graph_retrieval_disabled` before any graph service SQL.

Success uses `GraphRetrievalQueryResponse`. OpenAPI explicitly documents the strict graph error model for 404, 409, 422,
500, 503 and 504. Existing authentication/permission 401/403 responses retain shared application schemas/semantics.

No other `/v06` endpoint is added.

## 15. Route-Local Sanitized Request Validation

Define a v0.6-only `APIRoute` subclass in `app/api/v06_graph_retrieval.py`.

Its route handler wrapper catches `RequestValidationError` raised while resolving this route and returns exactly:

```json
{
  "detail": "graph_retrieval_invalid_request",
  "candidates": []
}
```

with HTTP 422.

Requirements:

- keep `GraphRetrievalQueryRequest` as the actual body model so OpenAPI remains accurate;
- do not install a global validation exception handler;
- do not serialize `exc.errors()`, `exc.body`, rejected field names/values or raw JSON;
- invalid JSON, unknown fields, `include_properties`, nested properties and oversized inputs use the same fixed body;
- do not log the exception or request body.

Authentication/permission `HTTPException` behavior is not caught or rewritten by this route class.

## 16. API Error Mapping

Known service errors map exactly:

| HTTP | Code |
|---:|---|
| 404 | `seed_not_found` |
| 409 | `seed_ambiguous` |
| 409 | `publication_changed` |
| 409 | `relation_type_not_found` |
| 422 | `graph_retrieval_limit_exceeded` |
| 503 | `graph_retrieval_disabled` |
| 503 | `graph_publication_unavailable` |
| 503 | `graph_publication_invariant_failed` |
| 504 | `graph_retrieval_timeout` |
| 500 | `graph_retrieval_internal_error` |

Return `GraphRetrievalErrorResponse.model_dump(mode='json')` through `JSONResponse`, so the runtime body and documented
schema are identical. Only `seed_ambiguous` includes its bounded same-scope candidates.

For every error after a database session may have been used, the API owns transaction cleanup and calls `await
db.rollback()` before returning. It never commits.

Unknown exceptions map to fixed 500 without `str(exc)`, class name, traceback, SQL or parameters in body or logs. M4 does
not add request success logs or metrics; M5 owns sanitized observability.

## 17. Timeout Contract

Wrap the complete M4 service operation, including Evidence hydration, response assembly and final fence, in:

```text
asyncio.timeout(settings.graph_retrieval_timeout_seconds)
```

On timeout:

1. cancellation propagates into the active async SQL/service call;
2. the API catches the resulting `TimeoutError` outside the context;
3. the API rolls back the read-only session to clear any failed/cancelled transaction;
4. it returns HTTP 504 with `graph_retrieval_timeout`;
5. no partial traversal/locator response is returned;
6. the pooled connection/session can execute a later query safely.

Do not use `asyncio.shield` around graph/Evidence SQL and do not auto-retry. A rollback failure must not replace the fixed
sanitized public error with raw database text.
