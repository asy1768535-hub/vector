# v0.2 Evidence Foundation Design

> Project: `vectorDatabase`
>
> Status: design approved
>
> Date: 2026-07-08
>
> Scope: v0.2 only. This phase builds the evidence foundation for a future evidence-trustworthy enterprise knowledge graph platform. It does not implement ontology, entities, relations, graph extraction, graph retrieval, graph QA, or graph governance UI.

## 1. Project Positioning

The long-term product direction is an evidence-trustworthy enterprise knowledge graph platform.

It is not a generic RAG knowledge base, and it is not initially a full graph database platform. Its core is: document evidence and structured business facts as roots; entities, relations, domain schema, version consistency, permission control, and graph QA as the main line.

The long-term pipeline is:

```text
documents / business data
-> document_blocks structured parsing
-> evidence chunks
-> ontology / schema
-> entities / relations
-> evidence binding
-> graph lifecycle
-> graph retrieval / graph QA / graph API
-> governance UI / external system integration
```

The current product principle is:

```text
evidence as root, schema as constraint, graph as expression, vector retrieval as recall support
证据为根，Schema 为约束，图谱为表达，向量检索为召回支撑。
```

For v0.2 engineering execution, the practical ordering is:

```text
evidence first, schema second, extraction third, lifecycle fourth, retrieval fifth, QA sixth,
governance seventh, external integration eighth, advanced graph database evaluation last.
```

## 2. v0.2 Goal And Boundaries

v0.2 is named:

```text
v0.2 Evidence Foundation: document structure, versions, evidence anchors, and sync identity
```

v0.2 upgrades the current system from:

```text
documents + chunks + embedding_jobs + Qdrant
```

to:

```text
documents
-> document_revisions
-> document_blocks
-> evidence_units
-> chunks
-> Qdrant retrieval
```

The main goal is that every retrieval hit, future entity mention, future relation evidence, and future answer source can be traced to:

```text
library
folder / sync_source
document
document_revision
document_block
evidence_unit
chunk
page / title path / paragraph / table / OCR / sheet row/column location
```

### 2.1 Core Objects

`documents` are stable document identities. They store library, folder, sync source, external ID, current revision pointer, latest revision pointer, and soft-deletion state.

`document_revisions` are immutable version snapshots. They store the content, file reference, metadata snapshot, parser/chunking strategy, processing status, and publication metadata for one document version. A failed latest revision must not affect the old current revision.

`document_blocks` are document structure units. They store `heading`, `paragraph`, `table`, `image_ocr`, `sheet_row`, `page_text`, `record`, and related structure. Blocks serve extraction context, evidence location, and human review; they are not retrieval units.

`evidence_units` are first-class evidence anchors. Future `entity_mentions`, `relation_evidence`, and `answer.sources` must reference `evidence_id`, not `chunk_id` directly.

`chunks` are retrieval and embedding units. They are derived from blocks/evidence and may cover one or more blocks and one or more evidence units.

`folders` provide lightweight document asset organization inside a library. Folder movement does not create a new revision and v0.2 does not implement folder ACL.

`sync_sources` provide external source-system namespaces. `source_key` is a stable technical identifier. External identity is `(library_id, sync_source_id, external_id)`.

### 2.1.1 Evidence Ref Contract

v0.2 uses `evidence_units.id` as the internal standard evidence reference.

APIs may expand that ID into an `evidence_ref` object:

```text
evidence_ref =
  evidence_units.id
  + evidence_units source fields
  + optional chunk/block/source metadata
```

Future `entity_mentions`, `relation_evidence`, and `answer.sources` bind to `evidence_id`. They do not bind directly to `chunk_id`.

## 4. Write, Update, Publish, Delete Flows

### 4.1 Transaction Boundary Rule

Do not execute OCR, file parsing, embedding, or Qdrant upsert while holding a document row lock or inside a long-running document write transaction.

Large-file workflows should split boundaries:

```text
1. Create minimal pending revision + file record.
2. Perform parsing/OCR outside long row-lock transactions.
3. On success, write blocks/evidence/chunks/job in a short transaction.
4. On failure, mark revision failed.
```

### 4.2 New Document

Flow:

```text
resolve identity
create document
create minimal document_revision(status=pending)
store revision file record if any
parse outside long lock
write document_blocks
write evidence_units
write chunks + chunk_blocks + chunk_evidence
create embedding_job(document_revision_id)
commit
return 202 Accepted
```

For a new document, `current_revision_id` is null until the first revision is published.

### 4.3 Existing Document Upsert / Replace

No-op means:

```text
content/file hash unchanged
title unchanged
payload/filter/provenance metadata unchanged
parser/chunking strategy unchanged
force=false
```

No-op returns `200 OK` and does not create a revision or job.

Changed update flow:

```text
create new pending revision
update documents.latest_revision_id
keep documents.current_revision_id unchanged
parse and generate blocks/evidence/chunks
create embedding_job
return 202 Accepted
```

The old current revision stays retrievable until the new revision publishes.

### 4.4 Worker Processing

Worker claim uses revision-level eligibility:

```text
job.status = pending
document_revision_id is present
document is not deleted
revision is pending/processing
revision.id == documents.latest_revision_id
library index_state allows work
```

Worker success flow:

```text
claim job
mark job/revision processing
read chunks for document_revision_id
embed chunks
upsert Qdrant points using stable deterministic point IDs
enter short publish transaction
CAS publish:
  documents.latest_revision_id == job.document_revision_id
  documents.deleted_at IS NULL
set document_revisions.status = ready
set embedding_jobs.status = done
set documents.current_revision_id = job.document_revision_id
record old_current_revision_id
enqueue cleanup for old_current_revision_id
commit
```

`current_revision_id` is published only after database blocks/evidence/chunks exist and Qdrant points were upserted and the CAS condition succeeds.

Qdrant point IDs must be idempotent and revision-scoped. The recommended rule is a stable deterministic ID derived from:

```text
document_revision_id + chunk_id
```

This avoids duplicate points during worker retry and avoids reusing point IDs across different document revisions.

### 4.5 Worker Failure

If embedding or Qdrant fails:

```text
retry/backoff using existing job semantics
on max attempts:
  job.status = failed
  revision.status = failed
  documents.current_revision_id unchanged
```

For a new document with no current revision:

```text
documents.status = failed
current_revision_id remains null
```

For an existing document:

```text
old current revision remains retrievable
```

### 4.6 Qdrant Success But DB Publish Failure

If Qdrant upsert succeeds but DB publish fails:

```text
revision is not published
current_revision_id remains unchanged
cleanup outbox or reconciler must clean unpublished points
```

### 4.7 Concurrent Updates

If worker processes revision A while API creates revision B:

```text
documents.latest_revision_id becomes B
A publish CAS fails
A/job marked superseded
A Qdrant points cleaned by outbox/reconciler
current_revision_id never points to A
```

### 4.8 Delete Document

Delete semantics remain:

```text
set documents.deleted_at
set documents.status = deleted
supersede active jobs
enqueue delete_document_all
commit
```

After commit:

```text
ordinary retrieval immediately hides the document by document tombstone
Qdrant physical cleanup is asynchronous
evidence_units may be asynchronously marked deleted
```

### 4.9 Cleanup Outbox

Existing cleanup outbox remains and gains revision-specific events:

```text
delete_document_all
delete_document_revision
delete_unpublished_revision_points
delete_collection
```

After publishing a new current revision, cleanup should delete only the recorded `old_current_revision_id`, not all old-looking points.

## 6. Parser, Block, Evidence, Chunk Generation

### 6.1 Parser Adapter

v0.2 introduces parser adapters that standardize existing parser outputs into:

```text
ParsedDocument
- normalized_text
- blocks[]
- parser_name
- parser_version
- parser_config
- diagnostics[]

ParsedBlock
- block_kind
- seq
- parent_ref
- title_path
- page_start/page_end
- source_start/source_end
- text
- content
- position
```

Adapters:

```text
text / markdown -> heading, paragraph, list_item, code
pdf -> page_text, image_ocr
docx -> heading, paragraph, table, image_ocr
xlsx -> sheet, sheet_row or table
csv/json -> record
```

No new parser engine is introduced in v0.2.

### 6.2 Evidence Generation

Rules:

```text
pure structure blocks do not require evidence units
all referable/retrievable/extractable content must generate evidence units
evidence can be block-level, span-level, row-level, sheet-row-level, or OCR-region-level
evidence source_start/source_end points to normalized_text where possible
position stores structural location such as table row range or OCR box
```

### 6.3 Chunk Generation

Rules:

```text
chunk belongs to one document_revision
chunk can cover multiple blocks
chunk can cover multiple evidence units
chunk.text can include retrieval-optimized context such as repeated table header
evidence source spans must remain faithful to original normalized_text or structure
```

If a chunk covers multiple evidence units, `visibility_scope` and `security_level` use the strictest value among covered evidence units.

### 6.4 Source Span Stability

`source_start/source_end` must have stable semantics over `document_revisions.normalized_text`.

For table/OCR cases where `chunk.text` differs from source text:

```text
chunk.text is retrieval text
evidence text/source span is authoritative evidence
position explains the original structure
```

### 6.5 Parser Failure

Default behavior:

```text
partial block parse failure makes the entire revision failed
```

Only parser adapters that explicitly mark a diagnostic as `non_fatal` may allow a revision to continue.

## 7. Metadata And Permission Field Governance

v0.2 uses:

```text
weak schema + reserved system field protection + size/depth limits + permission fields pre-positioned
```

### 7.1 Metadata Layers

```text
document_metadata
chunk_metadata
evidence_metadata
asset_management_fields
```

`document_metadata` enters the revision snapshot and can be used for payload/filter/provenance and future extraction context.

`asset_management_fields` do not enter evidence provenance, do not enter Qdrant payload, and do not create a revision.

### 7.2 Reserved Fields

External metadata must not include:

```text

document_revision_id
document_revision_no
document_revision
document_block_id
block_id
evidence_id
chunk_id
seq
text

page_start
page_end
title_path

```

Reserved namespaces:

```text

```

If external metadata hits a reserved field or namespace, return `422`. System-field overwrite during payload building is only a defensive measure.

`title`, `external_id`, `visibility_scope`, and `security_level` may be top-level API fields, but metadata must not override them.

### 7.3 Qdrant Metadata Projection

Rules:

```text
PostgreSQL keeps complete metadata
Qdrant payload only projects safe shallow fields by default
system provenance and permission fields are written last
```

### 7.4 Revision Trigger

Generate a new revision when changes affect:

```text
content
file hash
title
payload/filter/provenance metadata
visibility_scope
security_level
parser config/version
chunking config/version
```

Do not generate a revision for:

```text
folder_id
display_name
remark
sync_status
last_seen_at
last_sync_at
UI-only notes
```

### 7.5 Audit

Audit high-risk changes:

```text
metadata changed
visibility_scope changed
security_level changed
folder moved
sync_source changed
revision created
revision failed
revision published
document deleted
```

Audit records include:

```text
actor_user_id
action
library_id
document_id
document_revision_id
changed_keys
before_hash
after_hash
request_id
at
```

Do not record large text or complete large metadata in audit log.

## 8. Migration, Compatibility, And Implementation Batches

v0.2 uses a complete target model with phased release.

### 8.1 Batch 1: Schema And Backfill

Create new tables and nullable columns, then backfill legacy data.

Initial migrations should prefer nullable columns and non-validating or deferred constraints where practical. After backfill and validation pass, follow-up migrations may add:

```text
NOT NULL constraints
foreign keys
unique constraints
stricter CHECK constraints
```

This reduces migration lock risk and keeps rollback practical during the first deployment window.

Deleted documents:

```text
default: do not participate in retrieval and may be skipped
if backfilled for audit: revision.status must be deleted
```

Backfill uses `migration_backfill_state` for resumable, idempotent processing.

Legacy active chunks are backfilled with:

```text
default document_revision
legacy paragraph/page_text block
evidence_unit
chunk_evidence
```

### 8.2 Batch 2: Write Path

Switch new writes to revision/block/evidence/chunk generation behind a feature flag.

Use minimal pending revision + file record before parsing, then parse outside long row-lock transactions.

### 8.3 Batch 3: Worker / Qdrant / Retrieval

Switch worker and visibility to `document_revision_id` behind feature flags.

Use CAS publication:

```text
documents.latest_revision_id == job.document_revision_id
```

Qdrant point IDs use a stable idempotent rule, recommended as a deterministic ID from:

```text
document_revision_id + chunk_id
```

Worker retries must upsert the same point IDs for the same revision/chunk pair. Cleanup must target document revision IDs and must not delete current revision points.

### 8.4 Batch 4: New APIs

Add folders, sync sources, sync upsert/delete/sync, evidence read APIs, and source APIs.

Evidence and chunk source APIs default to current ready revision evidence. Historical evidence can be read only through explicit revision-scoped parameters and must pass the same library permission and visibility checks.

### 8.5 Batch 5: Cleanup, Docs, Acceptance

Keep compatibility fields in v0.2:

```text
documents.current_revision
embedding_jobs.document_revision
Qdrant payload.document_revision
```

Update docs, tests, release notes, and runbooks.

Before release, Batch 5 must include:

```text
migration dry-run
rollback dry-run
real PostgreSQL/Qdrant integration acceptance
old /retrieval compatibility acceptance
```

### 8.6 Feature Flags

Recommended flags:

```text
ENABLE_EVIDENCE_SCHEMA_READ
ENABLE_EVIDENCE_WRITE_PATH
ENABLE_REVISION_ID_WORKER
ENABLE_REVISION_ID_VISIBILITY
ENABLE_SYNC_SOURCE_API
```
