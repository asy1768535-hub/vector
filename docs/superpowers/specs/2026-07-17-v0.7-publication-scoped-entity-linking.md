## 0. 结论

v0.7 定义为 **Publication-Scoped Entity Linking**：调用方显式提供一个或多个 mention string，服务只在一个
健康 v0.5 active publication 的 Entity 成员内做确定性候选排序、高精度自动链接或显式 abstain。链接结果可由
调用方作为 Entity ID seed 继续调用 accepted v0.6 graph query；v0.7 本身不解析自然语言问题、不遍历图、不生成
答案，也不修改旧 `/retrieval`。

本阶段只批准设计和 feasibility gate。产品实施必须满足以下顺序：

```text
freeze v0.6 accepted baseline
-> approve v0.7 Master Design and project gates
-> approve fixed feasibility dataset/evaluator plan
-> run exact-only and old-retrieval controls
-> run entity-linking feasibility candidate
-> calibration selects candidate thresholds
-> human freezes one policy from that calibration
-> run exactly three independent post-freeze release runs
-> human GO / NO-GO decision
-> only after GO, split M1-Mn implementation plans
```

如果最小 lexical linker 不能在零错误自动链接、确定 abstention、Evidence utility 和 latency 门禁下证明增益，
结论必须是 **NO-GO**。不得在同一 v0.7 立项中临时加入 alias、Embedding、LLM、vector+graph fusion、path
retrieval 或 manifest v2 来制造通过。

## 3. 为什么选择 Entity Linking

v0.6 已证明 publication-scoped exact seed 和 bounded graph retrieval 可以正确、确定、可追溯地工作，但入口仍要求
调用方知道 Entity ID 或 exact normalized canonical name。现实调用经常只掌握简称、省略后缀、轻微词序差异或其他
非精确 mention。直接进入 vector+graph fusion 会同时引入 query parsing、两路召回、融合权重和答案评测，无法判断
增益来自链接还是融合；path retrieval 和 manifest v2 也不解决当前入口摩擦。

Entity Linking 是最小可独立证伪的下一步：

- 输入/输出边界可与 graph traversal 解耦；
- 可直接对照 v0.6 exact-only 的 link recall；
- 可用 link 后的 v0.6 graph Evidence 对照旧 `/retrieval` 的 Evidence utility；
- 不需要改 manifest v1、publication 数据或旧 endpoint；
- 失败时可以完整保留 v0.6，不产生 schema/data rollback。

## 4. 目标与非目标

### 4.1 目标

- 只在指定 Library、Ontology 和 healthy active publication 内解析显式 mentions。
- exact canonical match 优先；非 exact 使用确定性 lexical scoring v1。
- 高精度自动链接；不满足阈值或 margin 时明确 `ambiguous`/`not_found`。
- 每个候选都必须是同一 publication 的 active Entity item。
- 返回 publication/item provenance、Entity Type、canonical name 和整数分数，不返回 properties/Evidence 文本。
- 一次请求批量处理 1 到 10 个 mentions，无 N+1、无数据库写入。
- start/end publication fence，degraded/partial/superseded fail closed。
- 复用 `read` permission、Library isolation、route-local sanitized validation。
- 用固定评测证明相对 exact-only 和旧 retrieval 的增益。

### 4.2 非目标

v0.7 不实现：

- 修改 `/retrieval`、Dify、Chat 或 v0.6 request/response；
- 从完整自然语言问题自动抽取 mention；
- LLM entity linking、LLM-as-judge、query rewrite、Prompt 或答案生成；
- Entity/alias embedding、Qdrant entity collection 或 semantic rerank；
- dense/keyword/vector 与 graph 的 fusion、RRF 或 score blending；
- active/live `entity_aliases` lookup；
- `entity_mentions.mention_text`、quote、snapshot 或 source span lookup；
- pinyin、transliteration、NFKC、synonym dictionary 或 external mapping；
- automatic merge/split、alias write、Entity mutation 或 review workflow；
- path retrieval、shortest/all paths、GraphRAG 或 graph QA；
- manifest v2、temporal fields 或 properties exposure；
- UI、agent/tool orchestration、external graph database；
- Migration `0024`、新表/列/index 或 cache；
- production rollout 或 feature enablement。

如果 feasibility 显示必须依赖以上任一项才能过门禁，G3 结论是 NO-GO，并为该新 scope 单独立项。

## 5. 核心原则

### 5.1 Publication Scoped

Candidate universe 只能来自一个 healthy active publication 的 Entity items。`entities.status='active'`、active
alias 或全库 Entity 不是候选全集。Relation 不参与链接候选。

### 5.2 Exact Before Lexical

先复用 `normalize_graph_name_v1` 做 exact canonical match。unique exact 直接链接；exact 多匹配直接 ambiguous，
lexical score 不得覆盖 exact ambiguity。只有 exact 零匹配才进入 lexical v1。

### 5.3 High Precision, Explicit Abstention

错误自动链接比不链接更危险。绝对阈值和 top1/top2 margin 都满足才 auto-link；否则返回候选或 not-found。
客户端不能在请求中降低阈值。

### 5.4 Deterministic And Reproducible

相同 mention、type hint、publication、ontology schema identity、policy 和实现版本必须得到相同 status、候选、
score 和顺序。分数用整数 micros，不依赖数据库 locale、浮点序列化、模型或网络服务。

### 5.5 Link First, Retrieve Separately

v0.7 只返回 link result。调用方如需图，使用 linked Entity IDs 和相同 publication fence 调用 accepted v0.6。
这让 linking 和 traversal 的质量/延迟可分别评估，也保护 v0.6 合同。

## 6. 总体架构

以下是 G3 human GO 后、且对应 M1-Mn milestone 另行获批时才允许实施的目标 runtime 架构。G2/G3 evaluation
通过 reference entry point 调用相同的纯算法合同，不得创建 production route、OpenAPI path、runtime config 或
startup behavior。

```text
Authorized Library Reader
        |
        v
POST /libraries/{slug}/v07/entity-links/resolve
        |
        +--> feature gate + strict bounded DTO
        +--> load healthy v0.5 current publication
        +--> verify expected_publication_id
        +--> load one bounded published-Entity projection
        +--> normalize mention with normalize_graph_name_v1
        +--> exact canonical match
        +--> if no exact: deterministic lexical_score_v1
        +--> frozen policy: link or abstain
        +--> recheck same healthy/current publication
        v
PublicationScopedEntityLinkResponse

optional caller flow after a linked result:
linked Entity IDs + same publication_id
        -> POST /libraries/{slug}/v06/graph/query
```

v0.7 使用 FastAPI、Pydantic v2、SQLAlchemy async 和 PostgreSQL。没有 Qdrant、Embedding Provider、LLM、cache
或新持久化对象。

## 7. Publication 与数据合同

### 7.1 Healthy snapshot

必须复用 v0.6 `HealthyGraphSnapshot` 语义：

- Library/Ontology scope 完全匹配；
- current publication 唯一且 `status='active'`；
- `manifest_version='v1'`；
- publication Entity/Relation counts 与 active item/row/type health 完全一致；
- degraded、partial、superseded、endpoint dangling 或 item hash 异常全部 fail closed；
- optional `expected_publication_id` 不一致统一 `409 publication_changed`。

### 7.2 允许读取的 Entity projection

一条 bounded SQL projection 只允许：

```text
GraphPublicationItem.item_hash
Entity.id
Entity.entity_type_id
Entity.canonical_name
Entity.normalized_name
EntityType.id/key/label
```

固定 join 条件必须包含 publication/library/ontology/item kind/item status、Entity active 和 EntityType active。
projection row count 必须等于 snapshot `entity_count`，重复/missing row 视为 invariant failure。

`GraphPublicationItem.item_hash` 的 linker-relevant protected fields 是 `entity_type_id`、`canonical_name` 和
`normalized_name`；manifest v1 Entity item hash **不包含** `EntityType.key` 或 `EntityType.label`。因此 key/label
不是 manifest-protected projection，它们依赖现有 ontology service 所保证的 immutable active ontology。任何绕过
service 的 active ontology/schema 原地修改都属于 invariant violation。

Linker 必须另外计算 `ontology_schema_identity_v1`。其 canonical JSON 精确为：

```json
{
  "identity_version": "entity-linking-ontology-schema-v1",
  "library_id": "lowercase-uuid",
  "ontology_version_id": "lowercase-uuid",
  "version_key": "exact-db-string",
  "version_no": 1,
  "ontology_status": "active",
  "entity_types": [
    {
      "id": "lowercase-uuid",
      "key": "exact-db-string",
      "label": "exact-db-string",
      "status": "active"
    }
  ]
}
```

`entity_types` 只包含同一 Library/Ontology 的 active EntityType，按 lowercase UUID text ASC 排序。canonical bytes
使用 UTF-8、JSON object keys lexicographic sort、无 insignificant whitespace、non-ASCII 不转义、禁止 NaN；
`ontology_schema_hash = sha256(canonical_bytes)` lowercase hex。OntologyVersion scope/status、每个 published Entity
引用的 EntityType membership，以及 schema hash 都必须在 request start/end 复核；变化时丢弃整个 response。
单个 runtime response 绑定其 scope 的 `ontology_schema_hash`。评测包含多个 scope 时，dataset manifest 用 logical
scope ID 记录按 logical scope ID ASC 排序的各 scope schema hash，并对该 array 再做同一 canonicalization，得到
`ontology_schema_set_hash`；calibration、policy、三次 post-freeze run 和 release evidence 都绑定 set hash，不在
sanitized artifact 中记录原始 UUID。

OntologyVersion 与完整 active EntityType identity 可以由一个独立 bounded schema query 加载；它不是 Entity candidate
projection，也不得读取 description、properties schema、attribute/relation definitions 或其他 JSONB。Candidate Entity
projection 仍严格是一条，不能按 mention 或 type 发额外 query。

### 7.3 禁止读取的数据

Linker 不 select、不 enumerate、不 log：

```text
Entity.properties / authority_level / confidence / timestamps
EntityAlias rows or alias text
EntityMention text / normalized text / quote / evidence snapshot / source span
Relation rows and relation properties
Evidence/source/chunk text
Candidate extraction payloads
```

Alias 已存在 formal table，但不是 manifest v1 item，也没有进入 Entity item hash。读取 live alias 会让同一
publication 的链接结果随 publication 外状态变化，因此本版禁止。选择 alias linking 必须另做 manifest v2 立项。

### 7.4 Bounded load

v0.5 publication 总 item 上限为 10,000。v0.7 只加载其中 Entity projection；若 snapshot 声明或实际 projection
超过服务器 `ENTITY_LINKING_MAX_PUBLICATION_ENTITIES=10000`，返回固定 limit error，不降级到全库或分页猜测。

首版不 cache projection。若性能门禁失败，G3 NO-GO；不得在 feasibility 中临时引入跨 publication cache。

## 8. API 合同

本节是 post-GO implementation 的目标合同，不是 G2/G3 要求存在的 production API。G3 期间 OpenAPI 必须没有
`/v07/` path。

### 8.1 Route

```text
POST /libraries/{slug}/v07/entity-links/resolve
permission: read
feature flag: ENTITY_LINKING_ENABLED=false by default
```

独立版本 route 不挂载到 `/retrieval` 或 `/v06/graph/query`。v0.6 OpenAPI 和 response bytes 保持不变。

### 8.2 Request

概念 DTO：

```json
{
  "ontology_version_id": "uuid",
  "expected_publication_id": "uuid-or-null",
  "mentions": [
    {"text": "星河公司", "entity_type_key": "organization"},
    {"text": "研发中心"}
  ],
  "max_candidates_per_mention": 5
}
```

合同：

- `extra='forbid'`；
- `ontology_version_id` 必填；
- mentions 1 到 10；
- 每个 `text` trim 后 1 到 512 code points；
- optional type key 1 到 128，必须属于同一 active Ontology；
- max candidates 1 到服务器上限 10，默认 5；
- request 不允许 threshold、margin、algorithm、include_aliases、include_properties、query、Prompt、Embedding、
  Cypher、SQL、source text 或任意 filter expression；
- mention string 是调用方显式提供的 selector，不代表服务已实现 query parsing。

Candidate 只含 publication-visible identity/type/canonical name/item hash 和整数 score。禁止 properties、alias、
Evidence、source text、confidence、explanation feature vector 或 cross-scope hint。

### 8.4 Error contract

固定错误：

| HTTP | code | 语义 |
|---:|---|---|
| 404 | `library_not_found` | 复用不泄露 scope 的 Library 语义 |
| 409 | `publication_changed` | expected/start/end publication fence 失败 |
| 409 | `entity_type_not_found` | request type key 不属于 active scoped Ontology |
| 422 | `entity_linking_invalid_request` | route-local sanitized validation |
| 422 | `entity_linking_limit_exceeded` | client/server hard limit |
| 500 | `entity_linking_internal_error` | unknown failure，禁止 detail |
| 503 | `entity_linking_disabled` | feature off |
| 503 | `graph_publication_unavailable` | 无 healthy active publication |
| 503 | `graph_publication_invariant_failed` | membership/schema/item invariant 失败 |
| 504 | `entity_linking_timeout` | fixed timeout |

Batch 中的 mention ambiguity/not-found 是 200 per-result status，不用一个 mention 失败丢弃其他结果；但 publication
或 scope invariant 失败必须丢弃整个 response。这是 API batch response 合同；Section 18.4 另行冻结 evaluation
utility 的 required-mention 整题计分语义，两者不得混用。

## 9. `lexical_score_v1` 合同

### 9.1 Normalization

mention 和 candidate 都调用现有 `normalize_graph_name_v1`：trim、casefold、连续 whitespace 折叠为单空格。
不得增加 NFKC、标点删除、拼音、同义词或第二套 normalizer。

normalized mention 为空时 request validation 失败。normalized candidate 必须等于 formal `Entity.normalized_name`；
不一致是 publication invariant failure，不现场修复。

### 9.2 Exact stage

在 optional type filter 后：

- normalized canonical name unique match：`linked/exact_canonical/1000000`；
- 多 match：`ambiguous`，按固定顺序返回最多 K 个 exact candidates；
- 零 match：进入 lexical stage。

### 9.3 Lexical features

只计算三个 Unicode-code-point/token 特征：

```text
character_bigram_dice_micros
token_jaccard_micros
substring_containment_micros
```

定义：

- bigram 对长度大于 1 的 normalized string 生成相邻 code-point multiset；长度 1 使用整个 string 作为一个 gram；
- Dice = `2 * multiset_intersection / (left_gram_count + right_gram_count)`；
- token Jaccard 使用 whitespace-split 后的 token set；
- containment 仅当一个 normalized string 是另一个的连续 substring，值为 `shorter_length / longer_length`，
  否则 0；
- 每个比例必须直接从非负整数 numerator/denominator 计算，不得先构造 float 或 Decimal：
  `ratio_micros = (2 * numerator * 1000000 + denominator) // (2 * denominator)`；
- `score_micros = max(three features)`；
- candidate presentation floor 固定 `500000`，低于 floor 不返回且不能 auto-link。

三个比例的 numerator/denominator 精确定义为：

```text
bigram Dice:
  numerator   = 2 * multiset_intersection_count
  denominator = left_gram_count + right_gram_count

token Jaccard:
  numerator   = token_set_intersection_count
  denominator = token_set_union_count

substring containment when either string contains the other:
  numerator   = shorter_code_point_length
  denominator = longer_code_point_length

substring containment otherwise:
  numerator   = 0
  denominator = 1
```

Validated normalized strings are non-empty，因此上述 denominator 必须大于 0。实现必须使用不会溢出中间乘法的整数
类型；该公式等价于对精确有理数做 nonnegative round-half-up，且是 reference scorer 与未来 production scorer 的
唯一合法舍入公式。

不使用浮点作为合同输入/输出。reference tests 必须覆盖重复字符、单字符、CJK、Latin、空格、组合字符、包含、
完全不相关、同分和边界 rounding。

### 9.4 Stable candidate order

```text
score_micros DESC
entity_type_key ASC
normalized_name ASC
entity_id ASC (lowercase UUID text)
```

同分不得依赖 SQL arrival order、Python set order 或 locale collation。

## 10. Auto-Link 与 Abstention Policy

### 10.1 Frozen policy fields

```text

```

Request 和普通环境变量不能覆盖 score/margin。feature enable 前必须加载并验证 exact policy hash。

### 10.2 Selection grid

Feasibility plan 只能从预注册网格选择：

```text
min_score_micros: 850000, 880000, 900000, 920000, 950000
min_margin_micros: 80000, 100000, 120000, 150000, 200000
```

在 calibration split 上：

1. 排除任何 wrong auto-link、cross-scope failure、exact regression 或 privacy failure 的组合；
2. 排除 auto-link precision < 1.0 或 ambiguity/unlinkable false-link count > 0 的组合；
3. 对剩余组合最大化 non-exact correct auto-link coverage；
4. coverage 同分时依次选择更高 `min_score`、更高 `min_margin`；
5. 没有组合满足硬门禁则 calibration NO-GO，不得扩展网格。

### 10.3 Runtime decision

- top1 score < min score：有 presentation-floor candidates 则 ambiguous，否则 not_found；
- top1 score >= min score，但 `top1 - top2 < min margin`：ambiguous；
- top1 达到 score 和 margin：linked lexical；
- 没有 top2 时 margin 按 top1 计算；
- exact ambiguity 永远不进入 lexical auto-link；
- type hint 是 hard filter，不是加分；unknown type 是 request error。

## 11. Consistency、事务与并发

一次请求顺序固定：

1. auth/read scope；
2. validate bounds；
3. load healthy snapshot + membership aggregates；
4. resolve active requested Entity Types；
5. load one published Entity projection；
6. exact/lexical decisions in memory；
7. recheck same current publication、manifest hash、status/counts；

## 16. Evaluation 总体设计

## 18. Controls

### 18.1 Control A: v0.6 exact-only

对同一 mention/type hint 只执行 `normalize_graph_name_v1` + unique published canonical match。它提供 intrinsic

### 18.2 Control B: old retrieval dense

```text

```

### 18.3 Control C: old retrieval hybrid

同上，仅 `retrieval_mode=hybrid`，使用 accepted pg_trgm path 或其既有 ILIKE fallback。不得为 control 调参、加
synonym、改 chunking 或改 metadata filter。对每个 utility metric，`old_retrieval_best` 取 dense/hybrid 两个
aggregate control 中更好的值，candidate 必须超过更强 control。

### 18.4 Candidate

同一 question 的 dataset-frozen mention annotations 全部是 required seeds，并作为一个 batch 进入 lexical linker。
只有每个 input index 都返回 `linked` 时，才按首次 input index 顺序去重 Entity ID，并且只调用一次 accepted v0.6：

```text
expected_publication_id = linker publication_id
direction = both
relation_type_keys = []
max_hops = 2
max_nodes = 100
max_relations = 200
include_evidence_locators = true
```

Candidate 不获得 gold relation type、direction、path 或 answer。任一 required mention 返回 `ambiguous` 或
`not_found` 时，整题不调用 v0.6，candidate graph Evidence set 固定为空；该题 Evidence Recall@10、Evidence
Precision@10、complete support-set coverage、question-with-any-gold-Evidence、relation fact recall 和 node recall 均
记 0，不允许用其余 linked seeds 做部分查询，也不人工选择候选。Request-level error、scope/publication invariant 或
fence failure 是 evaluation run hard failure，不能降级成普通零分。

Intrinsic linking metrics 仍按每个 input index 独立计分并保留 dataset case/input-index 映射；一个 mention 的 utility
整题失败不得抹去同 batch 其他 mention 的 intrinsic correct/wrong/abstain 结果。旧 retrieval control 也使用相同的
empty Evidence set question-level precision=0 规则，避免空结果口径不对称。

```text
all four database IDs are absent according to a live admin existence probe
```

任一 uniqueness、time ordering、cleanup 或 live absence check 失败都使 verifier fail closed。Release evidence body
同样不得保存自身 hash；其 canonical/file SHA 只能由成功的 release verifier CLI output 和后续 completion record
外部发布，不得回写 release evidence。

禁止 artifact/log 包含 question、mention、canonical name、alias、source/chunk/Evidence text、UUID、raw response、
Embedding vector、SQL/parameters、DSN/API key 或 filesystem absolute path。

Policy freeze 后任何 scorer/dataset/ontology schema/config/control/environment identity 变化都要求新 calibration、
policy version 和三次 run；旧 artifact 不覆盖。

## 24. 被否决的替代方案

### 24.1 直接使用 active EntityAlias

否决。Alias 不在 manifest v1，同一 publication 会因 live alias mutation 得到不同结果。需要 manifest v2 单独立项。

### 24.2 复用 Qdrant 做 Entity embedding index

否决。这需要 Entity index lifecycle、publication switching、双写/清理和 embedding policy，属于 semantic linking 或
vector+graph fusion 扩展，不是最小 lexical feasibility。

### 24.3 用 LLM 从 question 抽 mention 并选择 Entity

否决。它把 mention extraction、linking、Prompt/model variance 和答案评测混在一起，无法独立归因。

### 24.4 修改 v0.6 seed resolver 为 fuzzy

否决。会破坏 accepted exact-only contract、客户端错误语义和 release hashes。v0.7 必须独立版本 endpoint。

### 24.5 自动选择 ambiguous top1

否决。高错误成本要求 absolute score + margin；不满足时显式 abstain。

### 24.6 只比较 exact-only，不比较旧 retrieval

否决。只能证明 linker intrinsic gain，不能证明关系问题 Evidence utility，无法支持继续图能力投资。

### 24.7 用 LLM answer correctness 作为 go/no-go

否决。v0.7 不生成答案；使用 LLM judge 会引入未冻结模型和主观评判。只比较 link/Evidence structured metrics。

| 风险 | 控制 |
|---|---|
| lexical overlap 错链相似实体 | zero wrong-link hard gate、margin、abstain |

| 10k Entity CPU/内存放大 | hard entity/mention limits、single projection、p95/memory gate |
