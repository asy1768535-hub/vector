# v0.3 Graph Relation Foundation Spec

> Project: `vectorDatabase`
>
> Status: design approved
>
> Date: 2026-07-09
>
> Scope: v0.3 only. This phase builds a lightweight property graph model and domain schema layer on top of v0.2 Evidence Foundation. It does not implement automatic LLM graph extraction, GraphRAG, graph QA, Neo4j/OpenSPG/KAG migration, complex entity disambiguation, automatic merge/split, or frontend graph visualization.

## 1. Principle

The v0.3 product principle is unchanged from the long-term graph direction:

```text
证据为根，Schema 为约束，图谱为表达，向量检索为召回支撑。
```

In practical engineering terms:

```text
evidence_units are the root of graph facts
ontology/schema defines what graph facts are legal
property graph rows express the business facts
vector retrieval remains recall support and is not replaced by graph retrieval in v0.3
```

v0.3 must make graph facts governable before it makes extraction intelligent. The first priority is therefore not automatic extraction. The first priority is defining legal graph structure: entity types, relation types, attribute definitions, relation connection constraints, ontology versions, fact states, evidence binding, and stale lifecycle.

## 2. Goals And Boundaries

### 2.1 Goals

v0.3 must establish:

```text
ontology_versions
entity_types
relation_types
relation_type_constraints
attribute_definitions
entities
entity_aliases
entity_mentions
knowledge_relations
relation_evidence
```

The system must support:

```text
library-scoped ontology versions
immutable active ontology semantics
default enterprise ontology seed data
schema validation for entity and relation writes
evidence-bound entity mentions
evidence-bound relation support
document/evidence revision stale lifecycle
active reads that filter stale/deleted facts by default
minimal service/API acceptance for v0.4 extraction and agent callers
```

### 2.2 Non-Goals

v0.3 must not implement:

```text
LLM automatic graph extraction as the main flow
complex multi-hop reasoning
GraphRAG answer generation
large graph visualization
Neo4j / OpenSPG / KAG migration
complex entity disambiguation
automatic entity merge/split
frontend graph UI redesign
changes to existing chat dirty files
changes to v0.2 retrieval behavior
changes to v0.2 write path behavior
changes to v0.2 deletion behavior
changes to publication worker behavior
changes to Qdrant payload shape
```

## 3. Versioning And Library Scope Rules

All ontology/schema tables must explicitly carry `library_id`.

This is required even when the row also has `ontology_version_id`. Direct `library_id` columns are required for:

```text
permission filtering
debugging
schema migration
audit trails
future library sharding
future offline exports
safer operational cleanup
```

Graph fact tables must also carry `library_id` directly. Graph reads and writes must never rely only on a multi-hop join to infer library scope.

### 3.1 Revision Field Compatibility

v0.3 must reuse the v0.2 revision field names that already exist in the codebase and database.

Current v0.2 Evidence Foundation uses `document_revision_id` as the UUID revision reference on evidence-related rows, while preserving older integer compatibility fields such as `documents.current_revision`, `embedding_jobs.document_revision`, and Qdrant payload `document_revision`.

Rules:

```text
v0.3 graph fact tables use document_revision_id when binding to v0.2 evidence_units.
v0.3 must not rename an existing v0.2 revision field for aesthetic consistency.
if an implementation finds an existing table uses document_revision instead of document_revision_id, preserve the existing name and document the mapping.
legacy integer document_revision compatibility fields must not be removed or repurposed in v0.3.
```

### 3.2 Feature Flag

v0.3 graph APIs and graph write paths must be disabled by default.

Default flag:

```text
GRAPH_V03_ENABLED=false
```

Rules:

```text
when GRAPH_V03_ENABLED=false, v0.3 API endpoints must return not found or an equivalent disabled response.
service-layer helpers may remain importable for tests and seed scripts, but production API writes must be gated.
enabling GRAPH_V03_ENABLED must not alter v0.2 retrieval, write path, publication worker, or Qdrant payload behavior.
```

## 4. Ontology And Schema Tables

### 4.1 `ontology_versions`

Fields:

```text
id UUID PK
library_id UUID NOT NULL
version_key VARCHAR(128) NOT NULL
version_no INT NOT NULL
status VARCHAR(32) NOT NULL
description TEXT NULL
parent_version_id UUID NULL
published_at TIMESTAMPTZ NULL
created_at TIMESTAMPTZ NOT NULL
updated_at TIMESTAMPTZ NOT NULL
```

Unique constraint:

```text
UNIQUE(library_id, version_key, version_no)
```

Status values:

```text
draft
active
disabled
deleted
```

Rules:

```text
draft ontology can be edited.
active ontology cannot be silently modified in place.
active ontology child schema rows cannot be silently modified in place.
schema changes to active ontology require creating a new ontology_version.
only one active ontology should be used as current per library and version_key.
disabled ontology is retained for audit/read compatibility but is not used for new writes.
deleted ontology is hidden from normal reads and cannot be used for new writes.
```

Immutability enforcement:

```text
active ontology immutability is enforced by service-layer update helpers.
database unique constraints prevent duplicates but are not sufficient to prevent post-publication mutation.
all create/update/delete paths for ontology_versions and schema child rows must call the ontology service guard.
direct update helpers must reject mutations to active ontology_versions and their active schema child rows.
tests must prove service-layer rejection; DB constraints alone do not satisfy M1.
```

## 5. Graph Fact Tables

v0.3 uses `properties JSONB` on entities and knowledge relations. It does not add `entity_attributes` or `relation_attributes` yet.

Future versions may split attributes into dedicated tables when strong indexing, aggregation, filtering, or auditing needs justify it.

## 7. Schema Validator

The critical v0.3 service is `graph_schema_validator`.

It is responsible for making the graph governable. All entity and relation writes must pass through it, regardless of whether the caller is an API, script, import job, or future extraction worker.

### 7.1 Entity Validation

Creating an entity must validate:

```text
library_id exists and matches the caller library.
ontology_version_id belongs to the same library.
entity_type_id belongs to the same ontology_version_id.
canonical_name is non-empty.
normalized_name is generated by the shared normalizer.
properties comply with entity_type.properties_schema.
properties comply with active attribute_definitions for the entity_type.
required attributes are present.
attribute value types match attribute_definitions.value_type.
enum attributes use allowed enum_values.
same library + ontology_version_id + entity_type_id + normalized_name does not duplicate an active entity.
source_type is manual, imported, or extracted.
```

Duplicate handling:

```text
exact duplicate active entity is rejected or returned idempotently only when all identity fields match.
same-name same-type ambiguity should become pending_review if the caller can preserve it safely.
automatic merge/split is out of scope.
```

### 7.2 Relation Validation

Creating a relation must validate:

```text
library_id exists and matches the caller library.
source_entity belongs to the same library.
target_entity belongs to the same library.
source_entity and target_entity belong to the same ontology_version_id.
relation_type_id belongs to the same ontology_version_id.
source_entity_type + relation_type + target_entity_type matches an active relation_type_constraint.
properties comply with relation_type.properties_schema.
properties comply with active attribute_definitions for the relation_type.
required attributes are present.
attribute value types match attribute_definitions.value_type.
enum attributes use allowed enum_values.
requires_evidence=true requires at least one active evidence before active status.
related_to cannot be auto-active.
low confidence cannot be active.
schema-boundary uncertainty cannot be active.
```

Status decision rules:

```text
valid relation + enough evidence + auto_active policy can become active.
valid relation + pending_review policy must become pending_review.
related_to must become pending_review even when schema allows it.
requires_evidence=true without active relation_evidence must be draft or pending_review, not active.
invalid source/target constraint must be rejected.
```

## 8. Evidence Binding And Snapshot Rules

All graph evidence bindings must point to v0.2 `evidence_units.id`.

`entity_mentions` and `relation_evidence` must denormalize:

```text
document_id
document_revision_id
chunk_id
quote_text
evidence_text_snapshot
source_span
```

Rules:

```text
evidence_id is the authoritative evidence reference.
chunk_id is optional denormalized context, not the authoritative graph anchor.
nonexistent evidence_id cannot be bound.
cross-library evidence_id cannot be bound.
inactive/stale/deleted evidence cannot create active mention or active relation_evidence.
document_id and document_revision_id are copied at bind time.
quote_text and evidence_text_snapshot are copied at bind time for audit and stale display.
```

Snapshot fields are required because later revision changes may remove or alter the current evidence path while historical graph audit still needs to explain how the fact was created.

## 9. Stale Lifecycle

v0.3 must implement the minimum stale lifecycle needed for document revision replacement, document deletion, and evidence invalidation.

### 9.1 Stale Triggers

When a document revision is replaced, deleted, or its evidence_units become invalid:

```text
entity_mentions tied to the old document_revision_id become stale.
relation_evidence tied to the old document_revision_id becomes stale.
knowledge_relations with no active relation_evidence become stale.
active reads stop returning stale/deleted mentions, relation_evidence, and relations by default.
```

When a document is deleted:

```text
do not directly delete entities.
mark related entity_mentions stale.
mark related relation_evidence stale.
mark affected knowledge_relations stale only if no active relation_evidence remains.
```

When an evidence_unit is marked stale/deleted:

```text
mark entity_mentions for that evidence_id stale.
mark relation_evidence for that evidence_id stale.
mark relation stale if it no longer has active relation_evidence.
```

### 9.2 Entity Retention Rule

Do not delete an entity just because a document is deleted or replaced.

Reason:

```text
an entity may be supported by multiple documents
an entity may be imported from a business system
an entity may be manually curated
an entity may remain valid after one evidence source changes
```

### 9.3 Default Read Filtering

Active graph reads must default to:

```text
entities.status IN ('active', 'pending_review') depending on endpoint intent
entity_mentions.status = 'active'
knowledge_relations.status = 'active'
relation_evidence.status = 'active'
```

Admin/review APIs may expose stale, rejected, disabled, and deleted states through explicit filters. v0.3 minimal APIs may defer broad admin filtering if tests prove active reads are safe.

## 10. Service Modules

Recommended modules:

```text
app/services/ontology.py
app/services/graph_schema_validator.py
app/services/graph_entities.py
app/services/graph_relations.py
app/services/graph_evidence.py
app/services/graph_seed.py
```

Rationale:

```text
graph_* prefixes avoid confusion with document entities or ordinary service names.
ontology.py owns versioned schema lifecycle.
graph_schema_validator.py owns legal graph validation.
graph_entities.py owns entity and alias writes/reads.
graph_relations.py owns relation writes/reads and status transitions.
graph_evidence.py owns mention/evidence binding and stale propagation.
graph_seed.py owns idempotent default ontology creation.
```

If the codebase strongly prefers `*_service.py`, equivalent names are acceptable:

```text
ontology_service.py
entity_service.py
relation_service.py
```

But the default implementation plan should use `graph_*` names for clarity.

## 11. Minimal API

v0.3 can implement only minimal APIs needed for acceptance and future v0.4 extraction callers.

Suggested endpoints:

```text
GET  /api/v03/ontology/current
GET  /api/v03/entity-types
GET  /api/v03/relation-types
GET  /api/v03/relation-constraints

POST /api/v03/entities
GET  /api/v03/entities/{entity_id}
POST /api/v03/entities/{entity_id}/aliases
POST /api/v03/entities/{entity_id}/mentions

POST /api/v03/relations
GET  /api/v03/relations/{relation_id}
POST /api/v03/relations/{relation_id}/evidence
POST /api/v03/relations/{relation_id}/status
```

API rules:

```text
minimal APIs must be gated by GRAPH_V03_ENABLED=false by default.
write APIs must enforce library permissions.
read APIs must enforce library read permission.
invalid relation writes return explicit validation errors.
requires_evidence relation activation without active evidence returns an explicit error.
related_to active request is downgraded to pending_review or rejected with explicit error.
```

If scope pressure is high, v0.3 may implement service + tests first and only a very small API slice:

```text
POST /api/v03/entities
POST /api/v03/relations
POST /api/v03/relations/{relation_id}/evidence

```

## 15. Implementation Notes

### 15.1 Naming

Use graph-specific fact names:

```text
entities
entity_aliases
entity_mentions
knowledge_relations
relation_evidence
```

Use `knowledge_relations`, not `relations`, to avoid ambiguity with generic application relations and SQLAlchemy relationship naming.

### 15.2 Status Scope

v0.3 accepted fact statuses are:

```text
draft
pending_review
active
rejected
stale
disabled
deleted
```

The following are reserved future concepts and must not be required for v0.3 acceptance:

```text
superseded
conflicted
```

### 15.3 Evidence First

The graph foundation must preserve the v0.2 handoff:

```text
future entity_mentions bind to evidence_units.id
future relation_evidence bind to evidence_units.id
chunk_id is only optional denormalized context
```

### 15.4 Future Attribute Tables

Do not implement these in v0.3:

```text
entity_attributes
relation_attributes
```

They may be introduced later when strong indexing, reporting, filtering, or attribute-level provenance justify the complexity.

### 15.5 Backward Compatibility

v0.3 graph foundation must not change:

```text
/retrieval top-level response shape
v0.2 document ingest/write path behavior
v0.2 publication worker behavior
v0.2 Qdrant payload shape
current chat dirty files
```

### 15.6 M1 Boundary

M1 is strictly an ontology/schema foundation milestone.

M1 may create:

```text
ontology_versions
entity_types
relation_types
relation_type_constraints
attribute_definitions
```

M1 must not create or modify:

```text
evidence_units
entities
entity_aliases
entity_mentions
knowledge_relations
relation_evidence
chunks
embedding_jobs
Qdrant payload builders
publication worker code
```

Evidence binding begins in M2.
