## 0. 结论

v0.6 定义为 **Published Graph Retrieval**：把 v0.5 的健康 active publication 变成一个只读、
确定、有限、Evidence-aware 的图检索接口。

首版只支持：

- 以显式 Entity ID 或精确规范化名称作为种子；
- 在一个明确的 Library、Ontology 和 active Publication 内做 1 到 2 跳邻域遍历；
- 按 Relation Type 和方向过滤；
- 返回发布快照身份、Entity、Relation、确定性深度和 Evidence locator；
- formal `properties` 只参与 manifest 一致性校验，永不进入 v0.6 response、filter、log 或 error；
- 在 Publication 降级、切换或成员不完整时 fail closed；
- 保持旧 `/retrieval`、Chat、Dify、Qdrant 和 v0.4 Provider/Worker 行为完全不变。

v0.6 不等同于 GraphRAG。它不接收自然语言问题，不调用 LLM，不做向量和图融合，不生成答案，
也不建设审核 UI。完整治理前端继续归属 v0.8。

## 2. 为什么 v0.6 先做图检索

前四个图谱阶段已经形成连续合同：

| 版本 | 已解决问题 | 对下一阶段的交付物 |
|---|---|---|
| v0.2 | 证据、修订和来源定位 | `evidence_units.id` 与 current-ready revision |
| v0.3 | Ontology、Entity、Relation、Evidence binding | 受 Schema 约束的正式图事实 |
| v0.4 | LLM 抽取、Candidate、校验和物化 | 带 Evidence 的 draft 正式事实 |
| v0.5 | Eligibility、immutable manifest、atomic activation、degradation | 健康 active publication |
| v0.6 | 已发布图的只读消费 | 可评测的结构化图检索结果 |

v0.5 已经有发布边界，但没有普通消费入口。继续先做完整审核 UI 会扩大治理面，却仍无法证明发布图对
关系型检索是否有价值。v0.6 先提供最小可评测消费面，可以回答三个更关键的问题：

1. active publication 能否在真实关系问题中稳定返回正确子图；
2. Evidence locator 能否让每条返回关系追溯到当前文档修订；
3. PostgreSQL 邻接遍历在当前 10,000-item publication 上是否足够，无需外部图数据库。

审核并没有被取消。v0.5 会继续报告 `pending_review` 等 blocked counts；候选审核、正式事实状态变更、
merge/split、冲突解决和完整治理 UI 仍保留到后续治理版本，完整前端边界保持 v0.8。

## 3. 目标与非目标

### 3.1 目标

- active publication 是唯一图检索成员来源。
- 查询只在一个 Library 和一个明确 Ontology 内执行。
- 每次响应携带 `publication_id`、`manifest_hash` 和 `ontology_version_id`。
- 同一输入、同一健康 publication、同一合同版本得到相同的节点、边和顺序。
- 名称解析复用 `normalize_graph_name_v1`，不增加第二套归一规则。
- 遍历使用确定性 breadth-first search，严格受 seeds、hops、nodes、relations 和 Evidence 上限约束。
- 每个返回事实都携带对应 publication item hash 和有界 Evidence locator。
- Publication 不健康、成员漂移或查询期间切换时不返回部分健康图。
- 所有读操作复用 `read` 权限和 Library scope 隔离。
- 用独立关系问题评测集验证结构召回、Evidence 覆盖和延迟。

### 3.2 非目标

v0.6 不实现：

- 修改旧 `/retrieval` 或 Dify response；
- Chat 接入、答案生成、引用编排或 Prompt；
- 自然语言 query parsing、LLM entity linking 或 query rewrite；
- dense/keyword/vector 与 graph 的融合、RRF 或 rerank；
- GraphRAG、graph QA、agent tool orchestration；
- shortest path、all paths、centrality、community detection 或全图导出；
- fuzzy、substring、拼音、embedding 或 alias entity resolution；
- `valid_from` / `valid_to` 的 `as_of` 过滤；
- formal Entity/Relation `properties` 的响应、过滤、排序或日志记录；
- Candidate 审核、Entity/Relation approve/reject、merge/split 或 conflict mutation；
- 治理 UI、图可视化 UI 或通用知识图谱工作台；
- Neo4j、OpenSPG、KAG、RedisGraph 或其他外部图存储；
- Qdrant payload、Embedding Worker、Graph Extraction Provider 或 Materializer 变化；
- 新数据库表、列或 Migration `0024`。

## 4. 核心原则

### 4.1 Publication First

`entities.status='active'` 或 `knowledge_relations.status='active'` 不是完整的 active graph 定义。
所有 v0.6 查询必须从一个健康 `graph_publications` 行和其 active
`graph_publication_items` 成员开始。

禁止：

- 直接调用 v0.3 lifecycle-only helper 作为 v0.6 数据源；
- 为了返回结果而设置 `include_degraded=true`；
- Publication 缺失时回退到所有 active/draft formal rows；
- Relation 命中但 endpoint 不在同一 manifest 时返回残缺边。

### 4.2 Evidence First

图事实是 Evidence 的表达，不是 Evidence 的替代。v0.6 返回的每个 Evidence 引用必须来自对应
`graph_publication_items.support_evidence_ids`，不得在查询时从所有 live mentions/evidence 重新推导一套
不同的支持集合。

### 4.3 Exact Before Smart

首版 Entity resolution 只接受显式 Entity ID 或 `normalization_v1` 后的精确 canonical name。
零匹配和多匹配都显式失败，不猜测最可能实体。

### 4.4 Bounded By Construction

任何请求都不能触发无界 recursive traversal、全库 scan 或任意数量的 Evidence hydration。客户端可以把
上限调低，不能超过服务器硬上限。

### 4.5 Retrieval And Answer Generation Stay Decoupled

v0.6 返回结构化事实和 locator。上层系统可以用它做展示、规则判断或后续上下文构建，但答案生成不进入
本服务合同。

## 5. 总体架构

```text
Authorized Library Reader
        |
        v
POST /libraries/{slug}/v06/graph/query
        |
        +--> validate feature gate + bounded request
        |
        +--> load one healthy current publication
        |      +--> optional expected_publication_id fence
        |
        +--> resolve exact published seed entities
        |
        +--> deterministic bounded BFS over published relations
        |      +--> publication item membership
        |      +--> active formal Entity/Relation rows
        |      +--> active EntityType/RelationType rows
        |
        +--> hydrate bounded Evidence locators from frozen support IDs
        |
        +--> recheck same publication is still healthy/current
        |
        v
PublishedGraphQueryResponse
```

实现继续使用 PostgreSQL、SQLAlchemy async ORM、FastAPI 和 Pydantic v2。当前 publication 上限为 10,000
items，v0.6 查询上限远小于全图规模，因此首版不复制邻接表、不建缓存、不引入外部图数据库。

## 6. Publication 读取合同

### 6.1 健康前置条件

查询开始时必须找到请求 `ontology_version_id` 对应的 current publication，并满足：

- `graph_publications.library_id == library.id`；
- `graph_publications.ontology_version_id == request.ontology_version_id`；
- `graph_publications.status == 'active'`；
- `manifest_version == 'v1'`；
- Entity 和 Relation 实际健康成员数分别等于 publication 计数；
- active Relation 的 source 和 target 都是同一 publication 的 active Entity item；
- 查询使用的 formal row 仍为 `status='active'`；
- 查询使用的 EntityType 和 RelationType 仍为 active 且同库同 Ontology。

`degraded` publication 只用于 v0.5 运维诊断，不得成为 v0.6 查询数据源。

### 6.2 Query-visible v1 字段

v0.6 只依赖 manifest v1 已冻结或已哈希保护的事实字段：

| Kind | 可用于响应或过滤的字段 |
|---|---|
| Entity | ID、Entity Type ID、canonical/normalized name、source type、confidence、support Evidence IDs |
| Relation | ID、Relation Type ID、source/target Entity ID、source type、confidence、support Evidence IDs |
| Schema | 当前 active Ontology 下不可变的 type key、label 和 direction |

`properties` 值不直接保存在 item snapshot 中，其 canonical hash 已进入 item hash。v0.6 只使用该 hash
参与 publication/item 健康不变量校验，不选择 live properties 组装响应，不提供 `include_properties`，也不
允许 properties filter、sort 或 metric。请求携带 `include_properties` 会因 `extra='forbid'` 返回 422。

这是 v0.6 的固定 privacy contract，不是前端默认值。未来若要开放 properties，必须先增加 Schema 级
public-field allowlist、嵌套值清洗规则、独立隐私 fixture 和新的 graph retrieval contract version；不能仅靠
调用方传一个布尔开关读取任意业务 JSON。

以下 formal 字段没有进入 v0.5 manifest v1，v0.6 不读取、不返回、不用于过滤：

- Entity/Relation `authority_level`；
- Relation `review_status`；
- Relation `valid_from` 和 `valid_to`；
- Entity aliases。

后续若要暴露这些字段，必须先设计 manifest v2、重新发布，并明确旧 v1 publication 的兼容策略，不能在
v0.6 中直接读取 live value 破坏 publication 可复现性。

### 6.3 Publication fence

请求可以携带 `expected_publication_id`：

- 与 current publication 相同：继续；
- 不同：返回 `409 publication_changed`；
- ID 来自其他 Library：同样返回 `409 publication_changed`，不泄露跨库存在性。

无论请求是否携带 fence，响应都必须在组装完成后重新检查：

- 同一 `publication_id` 仍是该 scope 的 current active publication；
- `manifest_hash` 未变化；
- publication 未 degraded/superseded；
- 本次读取计数和 endpoint membership 不违反健康不变量。

最终检查失败时丢弃已构造结果并返回 `409 publication_changed` 或
`503 graph_publication_unhealthy`，不得返回部分响应。

## 7. 查询合同

### 7.1 Request

概念 DTO：

```json
{
  "ontology_version_id": "uuid",
  "expected_publication_id": "uuid-or-null",
  "seeds": [
    {"entity_id": "uuid"},
    {"canonical_name": "某公司", "entity_type_key": "organization"}
  ],
  "direction": "both",
  "relation_type_keys": ["belongs_to", "depends_on"],
  "max_hops": 1,
  "max_nodes": 100,
  "max_relations": 200,
  "include_evidence_locators": true
}
```

Pydantic 使用 `extra='forbid'`。合同要求：

- `ontology_version_id` 必填，不静默选择“最近”的 Ontology；
- `seeds` 1 到 `GRAPH_RETRIEVAL_MAX_SEEDS` 个；
- 每个 seed 恰好提供 `entity_id` 或 `canonical_name` 之一；
- `entity_type_key` 只允许和 `canonical_name` 一起使用；
- `canonical_name` 去空白后长度 1 到 512；
- `direction` 只允许 `outbound`、`inbound`、`both`；
- `relation_type_keys` 去重后必须是该 Ontology 的 active Relation Type；
- `max_hops` 范围 0 到服务器上限；0 只返回已解析 seeds；
- `max_nodes` 和 `max_relations` 必须为正且不超过服务器上限；
- 请求不存在 `include_properties`；任何未知字段都因 `extra='forbid'` 被拒绝；
- 请求中不接受 source text、Embedding、Prompt、Cypher、SQL 或任意 filter expression。

### 7.2 Seed resolution

Entity ID seed：

- 必须对应同一 publication 的 active Entity item；
- 不存在、跨 Library、跨 Ontology、未发布或非 active 统一返回 `404 seed_not_found`。

名称 seed：

1. 使用 `normalize_graph_name_v1(canonical_name)`；
2. 只匹配 publication member Entity 的 `normalized_name`；
3. 提供 `entity_type_key` 时，同时按 active Entity Type 过滤；
4. 零匹配返回 `404 seed_not_found`；
5. 多匹配返回 `409 seed_ambiguous`；
6. 多个输入 seed 解析到同一 Entity 时去重，但响应保留输入到 Entity 的映射。

`seed_ambiguous` 响应只返回 reason code 和有界候选 `{entity_id, entity_type_key}`，不返回跨库数据、
properties 或 Evidence。

Entity aliases 当前不是 publication item，也没有进入 manifest v1。即使 alias row 为 active，v0.6 也不得
使用它做 seed resolution。

### 7.3 Direction

Relation Type 的 `direction` 决定遍历语义：

| Request direction | directed Relation | undirected Relation |
|---|---|---|
| `outbound` | frontier 必须是 source | frontier 可以是任一 endpoint |
| `inbound` | frontier 必须是 target | frontier 可以是任一 endpoint |
| `both` | frontier 可以是任一 endpoint | frontier 可以是任一 endpoint |

响应始终保留 formal Relation 的 `source_entity_id` 和 `target_entity_id`，不会因为 inbound 或 undirected
查询而交换 endpoint。

### 7.4 Deterministic BFS

遍历采用层序 BFS：

1. 解析并按 Entity UUID 排序 seeds，深度为 0；
2. 每一层只从上一层首次发现的 frontier 扩展；
3. 查询同一 publication 内符合方向和 Relation Type allowlist 的 active Relation items；
4. Relation 排序键固定为
   `(depth, relation_type.key, source_entity_id, target_entity_id, relation_id)`；
5. 新 Entity 的发现顺序由上述 Relation 顺序决定；
6. Entity 只记录最小 depth；Relation 只返回一次；
7. 达到 nodes 或 relations 上限后停止新增，但保留已完整组装的 node/edge；
8. 不返回 endpoint 缺失的 dangling edge；
9. 不因数据库自然顺序、Python set 顺序或并发请求改变结果顺序。

服务实现可以每 hop 发起一次有界 batch query，不允许 per-node N+1 query。

### 7.5 Truncation

达到任一上限不是服务器错误。响应必须明确：

```json
{
  "truncated": {
    "nodes": false,
    "relations": true,
    "evidence": false
  }
}
```

截断响应只声明“返回了确定性的有界子图”，不得声明完整邻域。若某一 Relation 因 node 上限无法同时
返回两个 endpoint，则该 Relation 不进入响应，并设置对应 truncation flag。

### 7.6 不做隐式 ranking

v0.6 不根据 confidence、properties、Evidence 数量或 Relation Type 做相关性排序，也不把不同尺度分数
相加。`confidence` 是发布事实元数据，不是 v0.6 rank score。

### 8.1 Evidence locator

当 `include_evidence_locators=true` 时，每个 node/relation 最多返回服务器配置上限个 locator：

```json
{
  "evidence_id": "uuid",
  "document_id": "uuid",
  "document_revision_id": "uuid",
  "document_block_id": "uuid-or-null",
  "evidence_kind": "direct_statement",
  "page_start": 3,
  "page_end": 3,
  "source_start": 120,
  "source_end": 182
}
```

locator 必须满足：

- ID 出现在对应 publication item 的 `support_evidence_ids`；
- Evidence 同库、active，且仍属于 Document current ready revision；
- 排序按 Evidence UUID；
- 不返回 `text_quote`、`evidence_text_snapshot`、Document normalized text、block text 或 source file bytes；
- 任一选中 locator 无法安全 hydration 时，整个查询 fail closed。

需要正文或文件时，授权客户端继续调用已有受控 source/file API。v0.6 不复制第二套原文读取合同。

### 8.2 Query data 与 operational data 的边界

v0.5 publication 运维 API 继续只返回 sanitized IDs、hashes、counts 和 reason codes。v0.6 是授权的
knowledge consumer API，可以返回 published canonical name、typed Relation 和 Evidence locator；formal
properties 即使属于 published fact 也不进入 v0.6 DTO。允许返回的业务字段不得进入应用日志、metrics
label、审计 target 或错误详情。

## 9. API 与权限

首版只增加一个 endpoint：

| Method | Path | Permission | Purpose |
|---|---|---|---|
| `POST` | `/libraries/{slug}/v06/graph/query` | `read` | 精确 seed resolution + 有界邻域遍历 |

使用 POST 是因为 seeds 和 filters 是结构化查询体，不代表写操作。该 endpoint 不写数据库，也不创建
审计业务行。

权限合同：

- 复用 `require_lib('read')`；
- superuser 和普通用户遵循现有 Library read 语义；
- 所有 publication、Entity、Relation、Type、Evidence 和 Document join 都显式带 `library_id` scope；
- 跨库 UUID 不返回对象存在性；
- feature disabled 时，在任何图查询前返回 `503 graph_retrieval_disabled`；
- OpenAPI 路由可以挂载，但默认开关关闭。

v0.6 不新增 `graph_read` Casbin action，避免和既有 `read` 形成两套权限含义。若未来需要把图事实和文档
正文拆权，必须单独做权限设计和迁移，不能在本版隐式实现。

## 10. 配置合同

建议配置：

| Setting | Default | Contract |
|---|---:|---|
| `GRAPH_RETRIEVAL_ENABLED` | `false` | 独立 fail-closed 读开关 |
| `GRAPH_RETRIEVAL_CONTRACT_VERSION` | `v1` | 响应与排序合同版本 |
| `GRAPH_RETRIEVAL_MAX_SEEDS` | `10` | 请求 seed 硬上限 |
| `GRAPH_RETRIEVAL_MAX_HOPS` | `2` | BFS 最大 hop |
| `GRAPH_RETRIEVAL_MAX_NODES` | `100` | 单请求最大 node |
| `GRAPH_RETRIEVAL_MAX_RELATIONS` | `200` | 单请求最大 Relation |
| `GRAPH_RETRIEVAL_MAX_EVIDENCE_PER_FACT` | `20` | 每个事实最大 locator |
| `GRAPH_RETRIEVAL_TIMEOUT_SECONDS` | `3.0` | 单请求服务预算 |

启动时拒绝：

- 空白或非 `v1` contract version；
- 非正 seeds/nodes/relations/evidence 上限；
- hops 不在 `1..2` 的服务器配置；请求仍可使用 `max_hops=0`；
- timeout 非有限数或 `<= 0`；
- `max_nodes < max_seeds`。

`GRAPH_PUBLICATION_ENABLED=false` 只禁止 publication mutation，不应自动关闭对既有健康 active publication
的 v0.6 读取。两个 feature gate 独立。

## 11. 错误合同

| HTTP | Code | Condition |
|---:|---|---|
| 404 | `library_not_found` | 既有 Library scope 行为 |
| 404 | `seed_not_found` | seed 不存在、跨 scope、未发布或非 active |
| 409 | `seed_ambiguous` | 精确名称在所选 scope 内匹配多个 Entity |
| 409 | `publication_changed` | expected fence 或查询末尾 recheck 失败 |
| 409 | `relation_type_not_found` | 请求 filter 不是 active Relation Type |
| 422 | Pydantic validation | shape、长度、枚举或 limit 非法 |
| 503 | `graph_retrieval_disabled` | v0.6 feature gate 关闭 |
| 503 | `graph_publication_unavailable` | 无 active publication 或 current publication degraded |
| 503 | `graph_publication_invariant_failed` | membership、endpoint、type 或 Evidence 不完整 |
| 504 | `graph_retrieval_timeout` | 超过 query budget |

错误响应不包含 canonical name、properties、Evidence text、跨库 ID、SQL 或内部 exception message。

## 12. 查询一致性和事务

v0.6 是只读请求，不对 publication 或 formal rows 加 `FOR UPDATE`，避免阻塞 activation/reconciliation。

一致性通过以下方式保证：

1. 查询开始固定 `publication_id` 和 `manifest_hash`；
2. 所有 member query 显式使用该 publication ID；
3. 每一层批量查询同时检查 item/formal/type active 状态和 endpoint membership；
4. 构造响应前重新读取 current publication；
5. ID、hash 或 status 变化则丢弃结果并要求客户端重试。

这为单次响应提供清晰线性化检查点，不要求长时间持有 repeatable-read snapshot，也不阻塞 v0.5 原子
activation。实现不得自动重试到新 publication 后混合两个快照；是否重试由客户端决定。

## 13. 性能和资源边界

v0.6 继续使用现有索引：

- publication current-scope partial unique index；
- publication item 的 per-publication Entity/Relation unique indexes；
- Knowledge Relation source/target adjacency indexes；
- Entity primary/unique identity indexes；
- Evidence library/status 和 revision indexes。

首版不创建 Migration `0024`。原因：

- v0.5 单 publication 已限制在 10,000 items；
- v0.6 单查询最多 100 nodes / 200 relations；
- 精确名称解析只在已发布成员内执行；
- 应先用真实 PostgreSQL `EXPLAIN (ANALYZE, BUFFERS)` 和 p95 数据证明缺口，再增加索引。

性能验收必须证明：

- 每 hop 是 batch query，不是 per-node N+1；
- 2-hop 最大默认响应不会读取整个 formal graph 到 Python 再过滤；
- timeout 会取消/回滚当前只读事务，session 可安全释放；
- 10,000-item publication 合成基准下记录 p50/p95 和 scanned rows；
- 若默认 3 秒预算无法稳定满足，M5 必须停止并修订设计，不能通过提高 timeout 掩盖。

## 14. 隐私、日志和可观测性

允许进入响应：

- published canonical name；
- Type key/label/direction；
- confidence/source type；
- publication/item hashes；
- Evidence locator 的 ID 和位置字段。

禁止进入响应：

- Context text、Prompt、raw Provider output、Candidate payload；
- quote text、Evidence text snapshot、block/document full text；
- Entity/Relation properties，包括任意嵌套 key/value；
- API key、credential、raw idempotency key；
- internal SQL、stack trace 或未经 allowlist 的 error message。

结构化日志只记录：

- request/correlation ID；
- Library ID、Ontology ID、Publication ID；
- hops、counts、truncation flags、duration、result/error code；
- 不记录 seed name、canonical name、properties、Evidence locator 或 source text。

建议 metrics：

- `graph_retrieval_requests_total{result_code}`；
- `graph_retrieval_duration_seconds`；
- `graph_retrieval_nodes_returned`；
- `graph_retrieval_relations_returned`；
- `graph_retrieval_truncated_total{dimension}`；
- `graph_retrieval_publication_recheck_failures_total`。

不得使用 Library slug、Entity ID、Relation Type key 或 Publication ID 作为 metrics label，避免高基数。

## 15. 评测合同

GraphRAG 是条件触发路线，因此 v0.6 必须先建立关系检索基线，而不是凭示例判断有效。

### 15.1 Dataset

至少包含：

- direct 1-hop：明确实体和一条关系；
- inbound/outbound 区分；
- undirected Relation；
- 2-hop chain；
- 同名不同 Entity Type 的歧义；
- Relation Type allowlist；
- cycle 和重复路径；
- Evidence locator；
- degraded/superseded publication；
- 跨 Library 和跨 Ontology negative cases；
- high-degree node truncation。
- Entity/Relation properties 中嵌套 secret/token/source text 的 privacy negative fixture。

Release dataset 必须固定 Entity/Relation/Evidence IDs 或 canonical hashes，不能依赖数据库自然顺序。

### 15.2 Metrics

| Metric | Meaning |
|---|---|
| Seed exact accuracy | 唯一 seed 正确解析率；歧义必须正确拒绝 |
| Node Recall | 期望子图 Entity 的召回率 |
| Relation Recall | 期望子图 Relation 的召回率 |
| Relation Precision | 返回 Relation 中 gold Relation 比例 |
| Evidence Coverage | gold Relation 是否带期望 Evidence locator |
| Determinism | 相同 publication/input 重复运行的 canonical response hash 一致率 |
| Scope Safety | 跨库、跨 Ontology、degraded 读取拒绝率，必须 100% |
| Property Privacy | response/log/error 中 formal properties key/value 泄漏数，必须为 0 |
| Latency | PostgreSQL p50/p95，分别记录 1-hop 和 2-hop |

v0.6 不和 dense retrieval 做质量融合对比，因为两个接口输入合同不同。可以对同一批关系问题记录
dense-only baseline，供后续是否启动 vector+graph fusion 决策，但不把它混入 v0.6 排名逻辑。

### 15.3 Release gate

- Scope Safety 必须 100%；
- Determinism 必须 100%；
- 所有 gold Relation 必须有 publication membership；
- Evidence Coverage 对有 Evidence 的 gold Relation 必须 100%；
- property privacy fixture 必须证明 response、log 和 error 对所有嵌套 properties key/value 为零泄漏；
- 质量与性能阈值必须在 M5 首次 calibration 后冻结到
  `eval/graph_retrieval/release_policy_v1.json`；
- calibration artifact 不计入 release run，policy 冻结后必须执行至少三次独立 post-freeze release run；
- PostgreSQL integration 和 performance gate 不得以环境缺失为由跳过后宣布 release passed。

### 15.4 M5 frozen release artifacts

M5 必须生成并提交以下固定产物：

```text
eval/graph_retrieval/gold_v1.json
eval/graph_retrieval/release_v1.jsonl
eval/graph_retrieval/manifests/release_v1.json
eval/graph_retrieval/results/<calibration-run-id>.json
eval/graph_retrieval/release_policy_v1.json
eval/graph_retrieval/results/<post-freeze-run-1-id>.json
eval/graph_retrieval/results/<post-freeze-run-2-id>.json
eval/graph_retrieval/results/<post-freeze-run-3-id>.json
eval/graph_retrieval/release_evidence_v1.json
```

`release_policy_v1.json` 必须是严格 schema、canonical JSON 可哈希且人工批准的不可变策略，至少记录：

- `policy_id`、graph retrieval contract version 和 normalization version；
- release dataset manifest SHA-256 与 content SHA-256；
- evaluation config SHA-256，包括 direction、hops、limits 和 Evidence locator 选项；
- 被选中 calibration artifact 的相对路径和 canonical SHA-256；
- Seed accuracy、Node Recall、Relation Recall/Precision、Evidence Coverage、Determinism、Scope Safety、
  PostgreSQL p95 和 property privacy 的冻结阈值；
- `properties_exposed=false` 隐私合同；
- 人工批准标识、UTC 时间和批准依据。

每个 post-freeze result artifact 必须记录唯一 `run_id`、独立数据库标识、policy canonical SHA-256、相同的
dataset/config hashes、各门禁的 numerator/denominator/metric，以及整个有序 case response 集合的
`canonical_response_set_sha256`。三个 run 的该 response-set hash 必须完全一致，每个 run 必须独立通过
全部冻结阈值；不得用三次平均值掩盖单次失败。

Dataset manifest 必须绑定 `release_v1.jsonl`、`gold_v1.json` 的 canonical hashes、case counts 和固定
contract/config identity。Calibration artifact 必须记录完整指标、numerator/denominator、dataset/config
hashes 和 candidate thresholds，但不得标记为 post-freeze，也不得计入三次 release runs。

`release_evidence_v1.json` 绑定 policy 和恰好三份 post-freeze artifact 的路径及 canonical hashes。离线
verifier 必须拒绝路径逃逸、重复 run/database、hash 不一致、阈值降低、properties 泄漏、非 UTC 时间、
少于三次 run 或任何单次 gate 失败。

任何 dataset、config、contract、normalization、阈值或 properties privacy policy 变化，都需要新 calibration、
新 release policy version 和三次新的 post-freeze runs；既有 artifact 保持不可变。

## 19. Rollout 与 rollback

### 19.1 Rollout

1. 部署代码，保持 `GRAPH_RETRIEVAL_ENABLED=false`。
2. 确认 Migration head 仍为 `0023`，无需 schema upgrade。
3. 选择一个非生产 Library，确认 v0.5 current publication 为 healthy active。
4. 运行 exact seed、1-hop、2-hop、ambiguity、truncation 和 Evidence locator smoke。
5. 运行 non-skipped PostgreSQL correctness/performance gate。
6. 开启 v0.6，观察 duration、truncation、timeout 和 publication recheck failures。
7. 在生产 Library 扩大使用前冻结并通过关系评测 policy。

### 19.2 Application rollback

设置：

```text
GRAPH_RETRIEVAL_ENABLED=false
```

效果：

- `/v06/graph/query` 返回 `503 graph_retrieval_disabled`；
- v0.5 publication 数据和运维 API 保留；
- v0.4 extraction、旧 retrieval、Chat、Dify 和 Qdrant 继续服务；
- 不需要 schema downgrade 或数据清理。

### 19.3 Data incident

如果 publication degraded：

1. 不启用 diagnostic fallback；
2. 保持 v0.6 fail closed；
3. 使用 v0.5 运维 API 查看 sanitized degradation reason；
4. 修复 Evidence/formal/schema 问题；
5. 计划并激活新的 clean publication，或执行合格 rollback plan；
6. 客户端使用新 `publication_id` 重试。

## 20. 被否决的替代方案

### 20.1 v0.6 先做完整审核 UI

否决。v0.4 已把完整治理 UI 留给 v0.8；当前优先需要验证 active publication 的消费价值。审核服务可以在
后续独立设计，但不能和首个 graph retrieval release 混成一个不可独立验收的版本。

### 20.2 修改旧 `/retrieval` 加 graph 字段

否决。旧接口承担 Dify 和现有业务兼容，直接修改会把实验图能力变成全局行为变化，也无法表达明确的
publication fence 和 subgraph response。

### 20.3 直接上 GraphRAG

否决。当前还没有结构检索 baseline、关系问题 release dataset 和图/向量融合评测。先证明 published graph
可以确定、正确、可追溯地返回子图。

### 20.4 使用 Neo4j/OpenSPG/KAG

否决。当前 publication 上限和查询上限允许 PostgreSQL 完成首版邻域遍历。外部存储会引入双写、版本切换、
权限同步、Evidence 同步和 rollback 一致性问题，价值尚未由性能数据证明。

### 20.5 用 alias/fuzzy/LLM 猜 seed

否决。Alias 未进入 manifest v1；fuzzy/LLM 又需要新的 ranking、歧义和评测合同。首版 exact-only 让错误
可解释，并为后续 entity linking 提供清晰 baseline。

### 20.6 在 v0.6 使用 temporal fields

否决。`valid_from`/`valid_to` 未进入 manifest v1 item hash。直接使用 live value 会让同一 publication 的
结果随未被 reconciliation 捕获的字段变化。必须先升级 manifest contract。
