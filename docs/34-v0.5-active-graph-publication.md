# v0.5 Active Graph Publication

v0.5 adds an explicit, versioned publication boundary for formal graph facts. A publication is an immutable manifest of
eligible Entities and Relations for one Library and one ontology version. Activation switches the current manifest
atomically; reconciliation can later mark it degraded when its formal rows, ontology, schema, constraints, or supporting
Evidence are no longer valid.

This release does not connect publication membership to retrieval, Chat, Dify, Qdrant payloads, a review UI, or
GraphRAG. Those paths retain their pre-v0.5 behavior.

## Feature Gate

Apply Alembic revision `0023` while `GRAPH_PUBLICATION_ENABLED=false`. The flag blocks plan, activate, cancel, and
rollback commands with `503 publication_disabled`; it does not hide existing publication audit rows from authorized
read endpoints.

The publication policy is fixed at process startup by these settings:

| Setting | Default | Purpose |
|---|---:|---|
| `GRAPH_PUBLICATION_REQUIRE_ENTITY_EVIDENCE` | `true` | Require eligible support for extracted Entities. |
| `GRAPH_PUBLICATION_EXTRACTED_ENTITY_MIN_CONFIDENCE` | `0.85` | Fail-closed confidence floor for extracted Entities. |
| `GRAPH_PUBLICATION_EXTRACTED_RELATION_MIN_CONFIDENCE` | `0.85` | Fail-closed confidence floor for extracted Relations. |
| `GRAPH_PUBLICATION_MAX_ITEMS_PER_RUN` | `10000` | Bound a newly planned manifest. |
| `GRAPH_PUBLICATION_POLICY_VERSION` | `v1` | Version policy snapshots used for rechecks. |
| `GRAPH_PUBLICATION_MANIFEST_VERSION` | `v1` | Version canonical item and manifest hashes. |

Startup rejects confidence values outside `[0, 1]`, a non-positive item limit, or blank policy and manifest versions.
Changing policy inputs changes the policy snapshot and can produce a different manifest.

## Roles And Endpoints

All endpoints are scoped by Library slug. Cross-Library publication IDs return `404` and cannot be operated on.

| Method and path under `/libraries/{slug}/v05/graph-publications` | Permission | Purpose |
|---|---|---|
| `POST /plan` | `insert` | Dry-run or persist an initial/manual plan. |
| `GET /` | `read` | List publication records with stable pagination. |
| `GET /active` | `read` | Read the current active or degraded publication. |
| `GET /{publication_id}` | `read` | Inspect one sanitized publication record. |
| `GET /{publication_id}/items` | `read` | Inspect sanitized manifest membership. |
| `POST /{publication_id}/activate` | `admin` | Recheck and atomically activate a planned manifest. |
| `POST /{publication_id}/cancel` | `insert` | Cancel a publication that is still planned. |
| `POST /{publication_id}/rollback` | `admin` | Dry-run or plan a rollback manifest from history. |

Planning supports `initial_seed` and `manual_plan`, optional draft inclusion, dry-run, parent fencing, and command replay.
Activation should include the manifest hash returned by planning so a stale operator decision fails closed. Raw command
keys are never returned; persistence and audit correlation use their SHA-256 hashes.

## Publication Lifecycle

| State | Meaning | Operator action |
|---|---|---|
| `planned` | Immutable membership exists but is not current. | Inspect counts and blocked reasons, then activate or cancel. |
| `activating` | Activation started and may be safely retried by the fenced service. | Retry the same command; do not edit rows manually. |
| `active` | Current healthy publication for its Library/ontology scope. | Monitor Evidence and formal graph health. |
| `degraded` | Current membership is retained for diagnosis but is not healthy. | Publish a clean replacement or plan an eligible rollback. |
| `superseded` | A later publication became current. | Keep for audit and possible rollback planning. |
| `cancelled` | A planned publication was cancelled. | Create a new plan if publication is still required. |
| `failed` | Activation failed and the graph switch was rolled back. | Inspect the sanitized error code, correct the cause, and re-plan. |

There can be at most one current `active` or `degraded` publication for each Library and ontology version. Publication
rows and item rows are retained as the audit history when a later snapshot supersedes them.

## Rollout

1. Back up the database and apply migration `0023` with publication commands disabled.
2. Confirm `alembic heads` reports only `0023 (head)`.
3. Run a dry plan for one non-production Library and inspect entity, relation, and blocked counts.
4. Enable publication commands in the non-production environment and persist the same plan with parent fencing.
5. Inspect the manifest hash, item count, ontology scope, and sanitized blocked diagnostics.
6. Activate with the expected manifest hash and verify exactly one current publication in that scope.
7. Verify healthy Entity and Relation reads return the complete active membership.
8. Exercise Evidence staleness and confirm the current publication becomes degraded and healthy helpers return no facts.
9. Exercise rollback dry-run; then either activate an eligible rollback plan or publish a clean replacement.
10. Enable production use only after the non-skipped PostgreSQL acceptance gate passes.

Dry-run planning and rollback persist nothing. Persisted planning is idempotent by command key and can reuse an existing
manifest. Activation repeats are idempotent after a successful switch.

## Health And Reconciliation

`GET /active` returns both `active` and `degraded` current records. The `healthy` field is true only for `active`.
Publication-aware healthy helpers require all of the following:

- the publication is `active`;
- every expected publication item is `active`;
- every referenced formal Entity or Relation is also `active`;
- returned membership counts exactly match the publication counts.

Any mismatch fails closed instead of returning a partial healthy graph. Diagnostic helpers require an explicit
`include_degraded=true`; normal healthy helpers return no rows for a degraded publication.

Evidence/document stale hooks and active contradictions reconcile in the transaction that caused the change. The
bounded reconciliation scanner covers drift in formal rows, Entity/Relation Types, relation constraints, schemas, and
ontology status. Degradation is one-way for a snapshot. Recovery requires activating a newly eligible clean publication.
The admin operations status reports aggregate active and degraded publication counts.

Operator checks:

```sql
SELECT library_id, ontology_version_id, count(*)
FROM graph_publications
WHERE status IN ('active', 'degraded')
GROUP BY library_id, ontology_version_id
HAVING count(*) <> 1;
```

The query must return no rows. For each current publication, compare `entity_count + relation_count` with its item count,
and treat a non-null degraded-item count or a stale `last_reconciled_at` as an incident signal.

## Rollback

Application rollback starts by setting `GRAPH_PUBLICATION_ENABLED=false`. This stops publication mutations while leaving
legacy retrieval, Chat, Dify, Qdrant, and v0.4 extraction behavior available. Keep revision `0023` and publication rows in
place on a data-bearing system unless a separately approved backup and data-loss plan permits a schema downgrade.

Data rollback is a two-step operation: plan a new publication from a historical snapshot with
`POST /{publication_id}/rollback`, then activate the returned planned publication. Rollback performs the same complete
eligibility and Evidence recheck as normal activation. If the historical snapshot is no longer eligible, rollback fails
closed; create and activate a clean publication from the current valid graph instead. Never flip formal statuses or
publication statuses manually.

## Scope And Privacy

Publication responses and audit targets contain identifiers, hashes, counts, status, bounded reason codes, and
timestamps only. They exclude source text, quote text, Evidence text snapshots, Context, prompts, raw Provider output,
Candidate payloads, formal properties, detailed error messages, credentials, and raw command keys.

The release adds no graph search, graph QA, GraphRAG, review UI/API, Neo4j/OpenSPG/KAG integration, Qdrant payload change,
or Chat/Dify/Provider behavior change. v0.5 publication membership is an operational graph boundary for future consumers;
it is not itself a retrieval integration.
