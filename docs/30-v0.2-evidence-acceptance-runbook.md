# v0.2 Evidence Acceptance Runbook

This runbook is the M5 release gate for the v0.2 Evidence Foundation. It is
intended for a disposable release-validation environment, not production.

## Scope

M5 closes the v0.2 evidence work by proving:

- old tests pass
- new v0.2 tests pass
- real PostgreSQL/Qdrant integration acceptance is represented and runnable
- old /retrieval compatibility acceptance remains Dify-style compatible
- migration dry-run passes
- rollback dry-run passes
- v0.3 can design entity_mentions(evidence_id) and relation_evidence(evidence_id)

## Required Environment

Run normal unit and contract tests from the M5 worktree. For real service
acceptance, set disposable service URLs only:

```powershell
$env:VECTOR_KB_PG_TEST_DSN = "postgresql+asyncpg://postgres:<password>@127.0.0.1:5432/vector_kb_v02_acceptance"
$env:VECTOR_KB_QDRANT_TEST_URL = "http://127.0.0.1:6333"
```

Rules:

- Never point `VECTOR_KB_PG_TEST_DSN` at production or shared staging data.
- Use an empty PostgreSQL database that can be dropped.
- Use a Qdrant instance or collection namespace reserved for acceptance.
- Clear the environment variables after the acceptance window.

## Gate 1: old tests

Gate id: `old_tests`

```powershell
..\..\.venv\Scripts\python.exe -m pytest tests -q -k "not v02" -p no:cacheprovider
```

Pass criteria: the full non-v0.2 regression suite passes. The narrower Dify
compatibility slice is still called out separately in Gate 6 because it is a
release compatibility contract.

## Gate 2: new v0.2 tests

Gate id: `new_v02_tests`

```powershell
..\..\.venv\Scripts\python.exe -m pytest tests\test_v02_m1_schema_models.py tests\test_v02_m1_backfill.py tests\test_v02_m2_write_path.py tests\test_v02_m3_worker_publication.py tests\test_v02_m4_folders_sync_evidence.py tests\test_v02_m5_acceptance_closure.py -q -p no:cacheprovider
```

Pass criteria: schema, backfill, write path, worker publication, folders/sync,
evidence APIs, and M5 closure tests all pass.

## Gate 3: migration dry-run

Gate id: `migration_dry_run`

Use a disposable clone of the release database. Confirm the target database
starts at `0017` or the expected pre-v0.2 version, then run:

```powershell
alembic upgrade 0018
alembic current
```

Pass criteria:

- `alembic current` reports `0018`.
- The v0.2 tables exist: `document_revisions`, `document_revision_files`,
  `document_blocks`, `evidence_units`, `chunk_blocks`, `chunk_evidence`,
  `folders`, `sync_sources`, and `migration_backfill_state`.
- Nullable-first columns exist on `documents`, `chunks`, and `embedding_jobs`.
- Compatibility fields still exist: `documents.current_revision`,
  `embedding_jobs.document_revision`, and `Qdrant payload.document_revision`.

## Gate 4: rollback dry-run

Gate id: `rollback_dry_run`

Run this only in the disposable validation database used for the migration
dry-run:

```powershell
alembic downgrade 0017
alembic current
```

Pass criteria:

- `alembic current` reports `0017`.
- v0.2 tables are removed.
- Pre-v0.2 compatibility columns remain in place.

## Gate 5: real PostgreSQL/Qdrant integration acceptance

Gate id: `real_postgresql_qdrant_acceptance`

Set both service variables:

```powershell
$env:VECTOR_KB_PG_TEST_DSN = "postgresql+asyncpg://postgres:<password>@127.0.0.1:5432/vector_kb_v02_acceptance"
$env:VECTOR_KB_QDRANT_TEST_URL = "http://127.0.0.1:6333"
```

Run:

```powershell
..\..\.venv\Scripts\python.exe -m pytest tests\test_v02_m1_backfill_pg_integration.py tests\test_v02_m5_real_stack_acceptance.py -q -p no:cacheprovider
```

Then run the deployment smoke path against the same disposable stack:

```powershell
alembic upgrade 0018
python scripts\v02_acceptance_manifest.py
```

Pass criteria:

- PostgreSQL migration and backfill integration passes.
- The env-gated real stack test creates a real Qdrant collection and point.
- A document can be embedded into Qdrant, retrieved, and traced through
  `metadata.evidence_id` and `metadata.document_revision_id`.
- Delete/tombstone behavior hides the document before physical Qdrant cleanup.

## Gate 6: old /retrieval compatibility acceptance

Gate id: `dify_retrieval_compatibility`

Run:

```powershell
..\..\.venv\Scripts\python.exe -m pytest tests\test_dify_contract.py tests\test_v02_m5_acceptance_closure.py::test_dify_response_shape_keeps_v02_provenance_additive -q -p no:cacheprovider
```

Pass criteria:

- `/retrieval` still returns only the Dify top-level response shape:
  `{records:[{content, score, title, metadata}]}`.
- v0.2 fields such as `evidence_id`, `document_revision_id`, and
  `document_revision` are additive metadata fields only.
- Existing Dify clients can ignore unknown metadata keys.

## Gate 7: v0.3 evidence handoff

Gate id: `v03_evidence_handoff`

M5 does not implement the graph layer. It must prove that v0.3 can design graph
tables around evidence anchors without depending on chunk IDs.

The intended v0.3 table direction is:

```text
entity_mentions(evidence_id) -> evidence_units.id
relation_evidence(evidence_id) -> evidence_units.id
```

Run:

```powershell
..\..\.venv\Scripts\python.exe -m pytest tests\test_v02_m5_acceptance_closure.py::test_v03_handoff_tables_bind_to_evidence_id_without_chunk_dependency -q -p no:cacheprovider
```

Pass criteria: the handoff manifest references `evidence_units.id` directly and
does not require `chunk_id` in either simulated table.

## Release Decision

Release can proceed only when all local gates pass and the operator has recorded
the real PostgreSQL/Qdrant integration acceptance result for the target
environment. If the real service gate is unavailable, M5 code can be merged, but
the release remains blocked until that gate is run in a disposable stack.
