# v0.9 Supported Deployment Runbook

This is the supported installation, upgrade, backup, restore, and rollback
contract for `private` and `hosted` deployments. Kubernetes, multi-region
active-active, and billing are outside this contract.

## Profiles

Set `DEPLOYMENT_PROFILE=private` for a customer-controlled installation or
`DEPLOYMENT_PROFILE=hosted` for the managed profile.

Both profiles fail startup unless:

- `APP_DEBUG=false`, `ALLOW_PUBLIC_REGISTRATION=false`, and
  `ORGANIZATION_AUTHORIZATION_ENABLED=true`;
- `JWT_SECRET` is non-default, `DB_PASSWORD` is non-empty, and
  `COOKIE_SECURE=true`;
- immutable revision storage is enabled and valid;
- Qdrant and embedding URLs are structurally valid.

Hosted additionally requires remote document storage and HTTPS Qdrant,
embedding, and object-storage endpoints. Credentials belong only in the runtime
secret store. Never put them in an image, command line, backup manifest, or Git.

Organization capabilities `public_api_v1`, `mcp_adapter`, and
`external_graph_sync` are disabled when no rollout row exists. Creating an
Organization never enables them.

## Fresh installation

1. Provision an empty PostgreSQL database, Qdrant, embedding service, and
   versioned object-storage bucket. Local storage is supported only by the
   private profile.
2. Populate runtime secrets and validate the process environment:

   ```powershell
   python -c "from app.config import settings,validate_supported_deployment_startup; validate_supported_deployment_startup(settings)"
   ```

3. Apply schema changes before starting any process:

   ```powershell
   alembic upgrade head
   alembic current
   ```

   The expected release head is `0060`.

4. Initialize storage, the first Organization, and its administrator. The
   command first verifies object storage, embedding, and Qdrant, then commits all
   identity rows in one database transaction:

   ```powershell
   python scripts/bootstrap_admin.py --organization-slug acme-private `
     --organization-name "Acme Private" --organization-profile private `
     --email admin@example.com --username admin
   ```

   Interactive execution can omit the environment variable and uses a
   non-echoing confirmation prompt. Automation may inject
   `BOOTSTRAP_ADMIN_PASSWORD` directly from its secret store. Re-running the exact command is safe;
   partial or mismatched state is rejected for operator review.

5. Start the Import Worker (`python -m app.workers.importer --watch`),
   retention/cleanup workers, embedding worker, optional enabled
   capability workers, and API. Wait for `GET /health/ready` to return HTTP 200.
   `GET /health/live` only proves the API process is alive.
6. When MCP is enabled, start `python -m app.mcp_adapter` as a separate managed
   process after API readiness succeeds. Keep Streamable HTTP bound to loopback
   and expose `/mcp` only through an authenticated TLS reverse proxy.

Public self-signup is not mounted in supported profiles. Administrators create
accounts through the Organization member API.

## Monitoring

Public readiness output contains only component states and stable failure codes.
It never returns service URLs, model identities, exception strings, queries,
document text, Evidence quotes, or credentials.

`GET /admin/operations/deployment` is superuser-only and reports:

- 24-hour request and failure counts;
- aggregate input/output tokens as a cost proxy;
- pending/failed embedding capacity;
- enabled Organization rollout counts.

Use `/admin/operations/status` for worker heartbeat and queue diagnostics. Treat
three consecutive readiness failures, any continuously growing failed queue, or
missing required workers as an incident.

## Backup

Pause mutating API traffic, disable all Organization rollouts, and drain workers
before taking a coordinated backup.

1. Run `scripts/backup_pg.ps1` using PostgreSQL custom format.
2. Export an object inventory from `document_revision_files`. It must include
   `storage_provider`, `endpoint_ref`, `bucket`, `object_key`, `object_version`,
   `content_sha256`, and `size_bytes`, then copy/version the referenced objects.
3. Snapshot every active Qdrant collection and write an inventory containing
   collection, snapshot name, size, and checksum. External-lifecycle
   collections remain the external owner's responsibility.
4. Bind the three artifacts:

   ```powershell
   python scripts/deployment_backup_manifest.py create `
     --postgresql backups/vector_kb.dump `
     --object-inventory backups/objects.json `
     --qdrant-inventory backups/qdrant.json `
     --output backups/manifest.json
   python scripts/deployment_backup_manifest.py verify `
     --manifest backups/manifest.json
   ```

Encrypt and copy the complete set off-host. The manifest intentionally contains
no `.env`, credentials, object contents, document text, or Evidence quotes.
Retain daily sets for 14 days and monthly sets according to the owning
Organization's policy. Never delete the last verified pre-upgrade set.

PostgreSQL is authoritative for documents, immutable revisions, Evidence,
Publications, external mappings, identity, and rollout state. Object storage is
authoritative for immutable source bytes. Qdrant is required for fast recovery,
but managed collections can be rebuilt from PostgreSQL and source objects.

## Restore drill

Use an isolated database, bucket prefix, and Qdrant namespace.

1. Verify the manifest before creating or changing the target database.
2. Restore PostgreSQL with `scripts/restore_pg.ps1`, then run
   `alembic upgrade head`.
3. Restore immutable objects and verify every inventory size/hash/version.
4. Restore Qdrant snapshots. If a managed snapshot is unavailable, rebuild that
   collection only after PostgreSQL and objects pass verification.
5. Start workers, then API. Require readiness HTTP 200.
6. Compare counts for Organizations, documents, revisions, revision files,
   Evidence units, graph Publications/items, external fact mappings, and
   enabled rollouts. Perform one read-only retrieval per restored Organization.
7. Destroy the disposable environment and record the manifest digest, release
   commit, duration, and result. Do not record customer content.

Run a restore drill at least monthly and before changing storage providers.

## Upgrade

1. Verify a fresh backup set and record the current application commit and
   Alembic revision.
2. Disable v0.9 Organization rollouts and drain all workers.
3. Deploy code without starting workers or API.
4. Run `alembic upgrade head`; verify `0060`.
5. Start workers, then API; require readiness.
6. Enable capabilities one Organization at a time with the current rollout
   `expected_version`. Watch failure, token, and queue aggregates before the
   next Organization.

## Rollback

Prefer application rollback while leaving additive schema `0060` in place:

1. Disable Organization rollouts and drain workers.
2. Stop API and workers.
3. Restore the previous application release.
4. Start its workers and API, then verify its supported health checks.

This runbook does not support an in-place schema downgrade from `0060`. A failed
migration or uncertain data state requires restore to a new database from the
verified coordinated backup, not manual revision stamping or in-place repair.
