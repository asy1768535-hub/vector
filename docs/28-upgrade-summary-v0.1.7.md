# 28 · 升级说明（`vectorDatabase-main` → `v0.1.7-internal-pilot`）

> **对比基线**
>
> - 旧版本：`vectorDatabase-main.zip`
> - 新版本：`vectorDatabase-0.1.7-internal-pilot.zip`
>
> 本文按两个交付包的**实际目录、代码、迁移、脚本、测试与文档**对比整理，用来回答四个问题：
> **做了什么、有什么用、为什么要做、下一步还能做什么。**
>
> 说明：仓库内少数旧文档仍保留 `v0.1.4` 等历史标记；本文以**压缩包实际内容**为准，按 `v0.1.7-internal-pilot` 口径总结。

## 一、升级一句话总结

这次升级的本质，不是“多加了几个接口”，而是把一个**能跑的向量知识库原型**，补成了一个更接近**可试运行、可交付、可恢复、可解释**的内部知识检索底座。

如果用一句更业务化的话来讲：

- 旧版本解决的是“能不能把文本放进去并检索出来”。
- 新版本解决的是“真实文档能不能稳定进来、旧数据会不会串、删改会不会脏、出了问题能不能查、上线后能不能运维、结果质量能不能继续优化”。

## 二、升级规模概览

从压缩包结构看，这次升级不是小修补，而是一次完整的能力扩展：

- 数据库迁移从 **`0001~0003`** 扩展到 **`0001~0016`**（其中 `0012` 已回退并由 `0015` 收编，`0016` 增加文档原文来源表）。
- 服务能力从以 `embedding / ingest / retrieval` 为主，扩展到 **OCR、Rerank、Query Rewrite、Hybrid、Cleanup、Rebuild、Heartbeat、Chat、FAQ、评测** 等多个模块。
- 运维脚本从 **4 个**扩展到 **16 个**，新增验收、评测、自检、备份恢复、启动状态等脚本。
- 测试文件从 **7 个**扩展到 **48 个**，覆盖面从基础单测扩展到 PG 集成、闭环、一致性、OCR、Hybrid、Chat、运维能力。
- 文档从原来的核心说明，扩展到 **一致性、OCR、本地模型接入、运行状态、备份恢复、上线清单**等可交付材料。

这意味着版本重心已经从“功能可用”转向“上线可控”。

## 三、这次到底做了什么

下面按能力域来讲，每一项都回答“做了什么、有什么用、为什么要做”。

| 能力域 | 做了什么 | 有什么用 | 为什么要做 |
|---|---|---|---|
| 文档摄入 | 从基础文本摄入，扩展到 **TXT / MD / JSON / CSV / DOCX / XLSX / PDF**，并支持 **DOCX 图片 OCR、PDF 扫描页 OCR、表格感知切块** | 真实业务文档终于能直接进库，不再只适合演示文本 | 真实场景里的知识往往在 Word、Excel、扫描 PDF 里，不补这一层，系统只能做样板项目 |
| 文档身份与幂等 | 引入 **`external_id` / `content_hash`** 身份规则，避免重复文档与误更新 | 同一文档重复导入、覆盖更新、内容去重更稳定 | 原型阶段常见问题是“重复导入一堆相似文档，后面根本分不清哪份是当前版本” |
| 更新一致性 | 引入 **revision + job generation**，更新后旧向量可按代际立即不可见 | 文档改完后，检索结果更像“当前版本”，而不是新旧内容混杂 | 向量库是异步写入的，不做 revision，更新与删除很容易出现脏读 |
| 删除一致性 | 从直接删 Qdrant，升级为 **tombstone + cleanup outbox + cleanup worker** | 删除动作可以“逻辑立即生效、物理异步清理、失败还能重试” | 直接删向量库一旦中途失败，就会留下“库里看不见、检索还能搜到”这类隐患 |
| 重建机制 | 新增 **rebuild operation 三阶段状态机** | embedding 模型变了、Qdrant 丢了、向量要重算时有标准流程 | 没有重建机制，越到后期越不敢改模型、不敢清库、不敢恢复 |
| 检索增强 | 在 Dense 检索上增加 **可选 Rerank、score_threshold、visibility filter、source enrichment** | 检索结果更准，能过滤过期/越权/已删内容，还能回补源正文 | 原型阶段“能搜到”不等于“搜得准”，更不等于“搜出来的内容可信且可解释” |
| 检索策略 | 新增 **Query Rewrite、Hybrid Retrieval、关键词检索模块** | 对简称、同义词、标题词、弱语义问题更友好 | 真实用户输入往往不规范，只靠单次 dense 召回，效果会很不稳定 |
| 业务问答 | 新增 **Chat API、Chat History、Library FAQ**，并支持智能问答角标查看召回切片、原文定位、多段高亮和来源校验 | 系统开始具备“站内问答”与 FAQ 场景承接能力，回答依据也能在页面内追溯到原文位置 | 上层系统并不总是接 Dify，很多时候直接需要一个轻量问答入口；进入试运行后，问答结果必须能解释、能核验 |
| 后台与体验 | 管理后台从基础页面演进到更完整的 **库管理、文档、权限、任务、运行状态、聊天日志** 等视图，并做了大量重设计与本地资源收敛 | 更适合交付给管理员和实施同事使用，不再只是给开发自己调接口 | 内部系统上线后的第一批问题，往往不是算法问题，而是“谁来配、怎么看、怎么查、哪里出错了” |
| 运行状态 | 新增 **service_heartbeats、运行状态页、任务状态聚合** | 能看见 API、Embedding Worker、Cleanup Worker 是否在线，任务是否堆积 | 没有进程级可观测性，系统一旦卡住，现场同事只能靠猜 |
| 自检与安全 | 增加 **启动安全校验、`/health` 扩展、自检脚本、本地 AI 服务检查脚本** | 部署前能先发现密钥默认值、模型地址错误、OCR/Rerank 依赖缺失等问题 | 原型系统最怕“能启动但不真能用”，这类问题必须前置暴露 |
| 备份恢复 | 新增 **PG 备份脚本、恢复脚本、Qdrant 备份说明、恢复演练文档** | 出故障时不是“从头来”，而是有可执行恢复路径 | 系统一旦进入真实使用，恢复能力比新增一个页面更重要 |
| 验收与评测 | 新增 **六步闭环验收脚本、检索评测 harness、数据集格式说明** | 可以用证据来证明“能用”“删改一致”“效果是否提升” | 没有验收脚本和评测尺子，版本升级只能靠主观感觉判断好坏 |
| 工程质量 | 测试从基础单测扩展到 **OCR、Hybrid、Chat、Cleanup、Heartbeat、PG 集成** 等多层验证 | 让升级不只是堆功能，而是具备可回归、可交付的可信度 | 系统越接近上线，越不能靠人工点点页面来保障质量 |

## 四、这些升级分别解决了什么实际问题

### 1. 从“只适合演示文本”升级为“能吃真实业务文档”

旧版本更偏向基础文本型向量库，适合快速验证检索链路。  
新版本把 DOCX、XLSX、PDF、OCR 都补上后，才真正开始接近真实部门资料的形态。

这带来的直接价值是：

- 可以接入法务、制度、办案、内部知识、运维手册等非纯文本资料。
- 扫描件和混合 PDF 不再天然成为盲区。
- Excel、表格型材料不必人工转成纯文本后再导入。

### 2. 从“能更新删除”升级为“更新删除后结果可信”

这部分是本次升级里最关键、也最有底座价值的改动之一。

做向量库最容易被忽视的问题不是“写进去”，而是：

- 更新后，旧内容会不会还被搜到？
- 删除后，检索是不是马上就消失？
- 中途失败后，会不会数据库和向量库状态不一致？

新版本通过 revision、cleanup outbox、visibility filter、rebuild operation，把这些问题从“靠运气”变成“有机制兜底”。这类工作对演示效果不显眼，但对长期使用极其关键。

### 3. 从“能检索”升级为“可持续调优的检索”

Dense 检索是起点，不是终点。新版本把以下调优手段补齐了：

- rerank
- score threshold
- query rewrite
- hybrid retrieval
- FAQ 补充召回
- 智能问答角标、召回切片查看、原文定位、多段高亮与来源校验
- 评测脚本与指标输出

这样做的价值不是某一次查询分数更高，而是团队后面终于能回答这些问题：

- 为什么这个查询命中不好？
- 开启 rerank 值不值？
- query rewrite 是否真的提升了效果？
- embedding 模型切换后，效果是升还是降？

没有这套能力，后续优化只能拍脑袋。

### 4. 从“能部署”升级为“敢试运行”

一个能试运行的系统，必须能回答四类问题：

1. 现在是不是活着？
2. 出问题时怎么看？
3. 数据丢了怎么恢复？
4. 发版后怎么证明链路没坏？

新版本在这四个问题上都补了东西：

- 运行状态页与心跳表回答“活着没”
- `/health`、自检脚本、任务统计回答“哪里坏了”
- 备份恢复 runbook 回答“坏了怎么回来”
- acceptance 脚本与检索评测回答“发版后是不是还对”

这标志着版本已经从研发内测走向实施交付。

### 5. 从“开发可用”升级为“管理员可用”

旧版本后台偏开发视角，更多是把接口拼成页面。  
新版本明显加强了管理员体验，包括：

- 页面重设计
- 菜单权限
- 图标与本地静态资源
- 运行状态
- 聊天日志
- 更完整的导入、任务、权限矩阵、库管理能力

这意味着后续很多操作不再必须让开发介入，管理人员可以自己完成。

## 五、为什么这次必须这样做

如果把这次升级放在产品演进逻辑里看，原因其实很清楚：

### 1. 原型能证明方向，但不能承接真实使用

原型阶段最重要的是“跑通”。  
试运行阶段最重要的是“稳定、可信、可运维”。

这两个目标完全不同，所以必须补：

- 一致性
- 观测性
- 恢复能力
- 真实文档支持
- 验收与评测

### 2. 向量库真正难的不是“检索”，而是“数据生命周期”

在业务里，知识并不是静止的：

- 会导入
- 会更新
- 会删除
- 会重建
- 会迁移模型
- 会恢复故障

这次升级的很多工作，表面看不是“新功能”，其实是在补知识生命周期管理。没有这层，系统越用越乱。

### 3. 内部系统比开源 Demo 更需要交付保障

内部项目上线后，最常见的不是“算法精度不够”，而是：

- 文档导不进去
- 结果里有旧内容
- 权限串了
- worker 挂了没人知道
- 服务器迁移后恢复不起来

所以必须优先把“可交付性”补齐，而不是只做算法增强。

## 六、这次升级带来的整体价值

可以把这次升级的价值概括为五句话：

1. **可接入真实资料了**：不再局限于纯文本演示数据。
2. **结果更可信了**：更新、删除、重建有了一致性保障。
3. **效果可优化了**：检索链路有了 rerank、rewrite、hybrid 和评测尺子。
4. **更敢上线了**：有状态监控、自检、验收、备份恢复材料。
5. **更能交付了**：后台、脚本、文档、测试都在往实施型项目靠拢。

## 七、下一步还可以做什么

如果继续往前走，建议分成三层优先级。

### A. 优先做：把试运行版进一步产品化

- 增加 **Casbin Watcher / 策略跨副本同步**，支撑多 API 副本部署。
- 补 **正式 Dockerfile / Compose / Helm**，降低部署成本。
- 接入更标准的 **日志、指标、告警**，例如 Prometheus/Grafana。
- 把运行状态从“手动刷新”升级为“定时刷新或推送”。
- 为关键脚本补一套更明确的服务器操作手册。

### B. 继续做：把检索效果进一步做实

- 基于真实部门样本沉淀 **正式评测集**，而不是只靠合成样本。
- 部署并验证 **本地 reranker**，减少对外部云服务依赖。
- 持续迭代 **query rewrite / hybrid / FAQ** 的召回策略。
- 强化 **表格、标题、编号、附件型文档** 的解析与召回。
- 对 OCR 文档做更细的版面处理，提升扫描件质量。

### C. 后续可做：把它从“检索底座”推向“知识服务平台”

- 增加更正式的 **tenant / 部门隔离模型**。
- 增加 **SSO / LDAP / 企业认证**。
- 增加 **文档原件留存与版本管理**。
- 继续强化 **答案引用、证据高亮、可追溯解释**，例如跨版本来源审计与更细粒度的证据链展示。
- 增加 **调用限流、审计报表、权限审批流**。
- 更深入接入 **Dify / FastGPT / 办公系统 / Agent 编排链路**。

## 八、适合对外怎么表述

如果这份升级说明要给领导、实施方或合作团队看，可以直接用下面这段摘要：

> 本次版本升级，重点不是单点新功能，而是把向量知识库从“原型可用”推进到“内部试运行可交付”。  
> 版本新增了真实文档摄入能力（DOCX/XLSX/PDF/OCR）、检索增强能力（Rerank/Rewrite/Hybrid/FAQ）、数据一致性机制（revision/outbox/rebuild）、运行与恢复能力（心跳监控/验收脚本/备份恢复），以及更完整的管理后台与测试体系。  
> 它解决的是知识库项目最容易在上线后暴露的问题：文档难摄入、更新删除不干净、效果难优化、问题难定位、故障难恢复。  
> 下一阶段建议在多副本部署、正式容器化、标准监控、真实评测集和本地 reranker 验证上继续推进。

## 九、附：本次升级最值得强调的 8 个点

- 支持真实业务文档，不再只适合纯文本。
- 更新、删除、重建具备一致性设计，不容易出现脏检索结果。
- 检索链路从单纯 dense 扩展为可调优体系。
- 引入 Cleanup Worker，补齐异步物理清理闭环。
- 引入运行状态与心跳机制，能看见服务是否在线。
- 引入备份恢复与验收脚本，部署可交付性明显提升。
- 管理后台更完整，管理员能自己完成更多操作。
- 测试、文档、脚本一起升级，版本可信度高很多。
