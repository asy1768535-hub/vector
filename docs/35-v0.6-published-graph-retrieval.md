# v0.6 Published Graph Retrieval Operator Guide

## Status And Boundary

v0.6 exposes one read-only endpoint:

```text
POST /libraries/{slug}/v06/graph/query
```

It reads only the healthy active v0.5 publication for the requested Library and Ontology. It does not expose formal `properties`, source text, quotes or raw Evidence content. M5 calibration and post-freeze artifacts are release inputs; final release acceptance remains M6.

## Required Configuration

Deploy with the accepted M1 limits and validate them at startup:

```text
GRAPH_RETRIEVAL_ENABLED=false
GRAPH_RETRIEVAL_MAX_SEEDS=10
GRAPH_RETRIEVAL_MAX_HOPS=2
GRAPH_RETRIEVAL_MAX_NODES=100
GRAPH_RETRIEVAL_MAX_RELATIONS=200
GRAPH_RETRIEVAL_MAX_EVIDENCE_PER_FACT=20
GRAPH_RETRIEVAL_TIMEOUT_SECONDS=3.0
```

Keep the feature disabled until the selected calibration, frozen release policy, three independent post-freeze runs and M6 acceptance are complete. No Migration `0024`, graph index or external graph service is required.

## Evaluation Gates

Validate the immutable dataset offline:

```powershell
.\.venv\Scripts\python.exe scripts/graph_retrieval_eval.py validate-dataset
```

Calibration requires a clean tracked implementation tree and a disposable PostgreSQL admin DSN. The database name must start with `vkt_v06_m5_eval_` and must not already exist:

```powershell
$env:VECTOR_KB_PG_TEST_DSN = '<disposable PostgreSQL admin DSN>'
.\.venv\Scripts\python.exe scripts/graph_retrieval_eval.py calibrate `
  --run-id <approved-calibration-run-id> `
  --database-id <vkt_v06_m5_eval_calibration_name> `
  --allow-create-drop-eval-db
```

The runner upgrades to `0023`, evaluates every case three times, builds a 10,000-item publication, records six 30-sample latency populations after five warm-ups, extracts sanitized EXPLAIN aggregates, proves timeout rollback/connection reuse, drops the database and only then writes a new canonical result file.

After human Gate B approval, verify the manually frozen policy before any post-freeze run:

```powershell
.\.venv\Scripts\python.exe scripts/graph_retrieval_eval.py verify-policy
```

Each post-freeze run uses a new run ID and database ID:

```powershell
.\.venv\Scripts\python.exe scripts/graph_retrieval_eval.py post-freeze `
  --run-id <approved-post-freeze-run-id> `
  --database-id <vkt_v06_m5_eval_post_freeze_name> `
  --allow-create-drop-eval-db
```

After exactly three independent runs and creation of the reviewed evidence bundle:

```powershell
.\.venv\Scripts\python.exe scripts/graph_retrieval_eval.py verify-release
```

Verify any artifact file hash independently with `Get-FileHash -Algorithm SHA256`. Canonical SHA values are semantic hashes over parsed canonical JSON and are verified by the CLI loaders.

## Staged Rollout

1. Keep `GRAPH_RETRIEVAL_ENABLED=false` globally and select a non-production Library with a healthy active publication.
2. Deploy the accepted build and configuration, restart the API process, then enable v0.6 only in the intended environment.
3. Exercise exact ID and exact name seeds, Evidence on/off, one-hop/two-hop and bounded truncation cases.
4. Compare result-code, duration, returned-count, truncation and publication-recheck events against the frozen policy.
5. Expand Library coverage only after the canary Library remains within its p95 and error budgets.

The feature flag is process configuration. Changing it requires the normal configuration deployment and API restart; it requires no schema or data operation.

## Observability And Alerts

`graph_retrieval.completed` logs contain only a server request ID, fixed result code, status, resolved scope IDs, query limits/mode, aggregate counts, truncation flags and duration. Metric events use these stable names:

```text
graph_retrieval_requests_total
graph_retrieval_duration_seconds
graph_retrieval_nodes_returned
graph_retrieval_relations_returned
graph_retrieval_truncated_total
graph_retrieval_publication_recheck_failures_total
```

Build dashboards for request rate/error ratio, p50/p95 duration by result/hop/Evidence mode, returned node/relation distributions and truncation rate. Alert on sustained p95 above the frozen scenario threshold, any invariant failure, repeated publication recheck failure, or a material truncation increase.

Investigate by fixed `result_code` and server request ID. Do not add request bodies, seed/canonical names, candidates, properties, Evidence IDs, source text, SQL, parameters, validation details, exceptions or credentials to logs or metric labels.

## Client Retry Contract

Clients must not retry invalid requests, permission failures, not-found seeds or ambiguity without changing input. For `publication_changed`, refresh the active publication expectation and retry with bounded backoff. A timeout retry is a caller decision with bounded backoff; the server never retries automatically. Publication unavailable/invariant failures require operator investigation rather than an unbounded client loop.

## Incident Response

- High p95: stop rollout, compare the environment fingerprint and frozen per-scenario threshold, then inspect sanitized EXPLAIN aggregates. Do not raise the three-second timeout or add an index inside M5.
- High truncation: inspect caller limits and graph degree using aggregate events. Do not log or export the underlying private facts.
- Invariant failure: disable v0.6, reconcile or replace the affected v0.5 publication, and re-enable only after healthy publication reads pass.
- Publication recheck failure: treat it as a publication switch race; clients may refresh once with bounded backoff.
- Disposable database left behind after an interrupted local run: verify its exact `vkt_v06_m5_eval_` name and remove it with the approved PostgreSQL administration procedure. Never point the runner at a production database.

## Disable And Rollback

Set `GRAPH_RETRIEVAL_ENABLED=false`, deploy configuration and restart the API. The v0.6 route then returns the fixed disabled error without executing graph queries. Existing `/retrieval`, Chat, Dify, Qdrant and v0.5 publication read paths remain available and unchanged.

If code rollback is required, return to the accepted M4 build with the feature disabled. No schema downgrade, publication mutation or graph-data cleanup is needed because M5 adds no table, column, index or Migration `0024`.
